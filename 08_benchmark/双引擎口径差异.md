## 3. ⭐ 发现并解释清楚的口径差异：MySQL 的 DECIMAL 除法只有 4 位小数

第一次比对时，比率列出现最大 **5e-5** 的差异（17/14,912/81/2,906 行），
而**计数与金额列全部 0.0 差异**。查根因（这一步很关键 —— 不能靠放宽容差糊过去）：

```sql
-- MySQL：
SHOW VARIABLES LIKE 'div_precision_increment';   -- → 4
SELECT bad_rate FROM ads_risk_segment WHERE dim_type='grade' ORDER BY dim_value;
--   A → 0.060400      ← 注意末尾两位是 0：实际只有 4 位小数
```

**根因**：MySQL 的 **DECIMAL 除法**受 `div_precision_increment`（默认 **4**）限制 ——
除法结果最多保留 4 位小数。所以 `ROUND(SUM(is_bad)/COUNT(*), 6)` 里的 `ROUND(...,6)`
**已经是空操作**：算出来的值在第 4 位小数上就被量化了。
而 Spark 用 double 除法 + `ROUND(...,6)`，给的是完整 6 位。

| 侧 | 真实分布 | 存储值 |
|---|---|---|
| MySQL | 0.0604xx | `0.060400`（4 位小数量化） |
| Spark | 0.0604xx | `0.060429`（6 位） |

**为什么只有比率列有差异、金额和利率列没有**：差异只在"目标列精度 > MySQL 除法精度"时出现。
`avg_int_rate` 目标列是 4 位小数 ≤ MySQL 除法精度 → 两侧**完全一致（0.0）**。

### 3.1 两层判定（不是"把容差放大"）

`compare_ads.py` 对比率列做了两层校验，两层都严格：

| 层 | 判据 | 实测 |
|---|---|---|
| ① 差异上界 | `|hive − mysql| ≤ 5e-5`（4 位小数量化误差的一半，**可证明的上界**） | 超上界行数 **0** |
| ② 平局判据 | 量化到 4 位小数后不等的行，**必须全部落在平局点上**（`hive×10⁴` 的小数部分 ≈ 0.5）；非平局的不等行必须为 **0** | 非平局 **0** |

**为什么会有平局点**：真实比率正好落在 4 位小数的半单位边界时
（例如 `1/32 = 0.03125` → ×10⁴ = **312.5**），
MySQL 用**精确十进制 half-up** 进位 → `0.0313`；
而 Spark 的 double 可能差一丝、向下舍 → `0.03125`。
这是**表示精度**问题，不是算错 —— 实测这些行的 `hive×10⁴` 小数部分全部是 `0.5`：

| 表 | 列 | 量化不等行数 | 其中落在平局点 | 非平局 |
|---|---|---|---|---|
| `ads_vintage_lc` | `bad_rate` | 84 | **84** | **0** |
| `ads_delinq_monthly_lc` | `delinq_rate` | 15 | **15** | **0** |
| `ads_delinq_monthly_lc` | `bad_rate` | 12 | **12** | **0** |

> 🔑 **这一段是整份报告最有价值的部分**：
> 差异不是"差不多就行"，而是**被完整解释、且解释本身可被验证**（平局判据）。
> 面试时可以说："双引擎比对出现 5e-5 的差异，我查到根因是 MySQL 的
> `div_precision_increment=4` 把 DECIMAL 除法量化到 4 位小数；
> 然后我不是放宽容差，而是把'差异 ≤ 量化上界'和'不等行必须落在平局点上'两条都写成断言。"
>
> **另一种选择**（也写在这里，便于以后决策）：如果要求两侧**逐位相同**，
> 就在 Hive 侧显式复现 MySQL 的量化语义：`ROUND(CAST(SUM(x)/COUNT(*) AS DECIMAL(38,4)), 6)`。
> 本项目的选择是**保留 Spark 的完整精度**（数据更好），差异用可验证的规则判定。

## 4. 实现层面的差异（DDL / 函数 / 类型）

| 维度 | MySQL | Hive/Spark | 为什么这么选 |
|---|---|---|---|
| 主键约束 | `PRIMARY KEY` | 无（靠 ETL + 校验保证唯一） | Hive 不强制主键，唯一性必须自己验 |
| 分区 | 无（索引 + 范围查询） | `PARTITIONED BY (issue_month / snapshot_month)` | 目录级裁剪比行级过滤省 IO（E1 量化） |
| 存储格式 | InnoDB 行存 | ORC 列存 + SNAPPY | 宽表少列查询收益大（E3 量化） |
| **整数/小数除法** | DECIMAL，**scale 受 `div_precision_increment=4` 限制** | `SUM(int)/COUNT(*)` → **double**，可给 6 位 | ⭐ 本节 §3 的核心差异 |
| 日期运算 | `DATE_ADD/DATE_SUB` + `STR_TO_DATE` | `add_months` / `date_format` + `to_date` | 函数名不同，语义逐一对齐 |
| **单引号里 `\t`** | — | `INTO OUTFILE FIELDS TERMINATED BY '\t'` | 转义规则不同，导出时已处理 |
| 空值语义 | NULL 参与排序/分组的方式一致 | 同 | ⚠️ JOIN 与 GROUP BY 中 NULL 行为不同，第 16 步会讲 |
| 时区 | `TZ=Asia/Shanghai` | `spark.sql.session.timeZone=Asia/Shanghai` | 批流对账要用（阶段四 M3 已实现，见 `09_realtime/`） |
