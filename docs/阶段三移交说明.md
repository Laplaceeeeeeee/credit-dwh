## 3. 关键决策（新会话不要推翻，都有实测理由）

| 决策 | 理由（实测） |
|---|---|
| **缩容不降架构**：保留外部 Hive Metastore，只压 Spark 侧资源 | Docker VM 内存不足，但 HMS 是"元数据/存储/计算三层分离"的认知核心 |
| **用 Spark 内置 Hive client 2.3.9 直连 HMS 3.1.3** | 正文里的 `jars=maven` 会走 Ivy 首次解析，**7 分钟没跑完且缓存落在容器可写层**；内置 client 4.4 秒返回 |
| **导出统一走 `SELECT ... INTO OUTFILE` + `docker cp`** | GB 级结果集流经 `docker exec` **把 Docker daemon 卡死**（所有 API 500）；OUTFILE 方式 44.7M 行/3.35 GB 只用 125 秒 |
| **比率列容差 5e-5 + "平局判据"** | MySQL `div_precision_increment=4` 让 DECIMAL 除法只有 4 位小数；Spark 给 6 位 → 差 5e-5。**没有放宽容差糊过去**，而是两条可验证断言 |
| **装载用 `REPARTITION(20, 分区列)`** | 文件数 ≈ 任务数 × 每个任务持有的分区值数；不控制会写出上千个小文件。实测 139/141 分区各得 **1 个文件** |
| **测量三件套**：harness + 事件日志 + 数文件 | 手工抄 4040 UI 不可复现；`spark.ui.keepAlive` 在 Spark 3.5 **根本不存在** |
| **命名约定**：机读产物用 ASCII 名与 ASCII 表头，人读报告用中文名 | 验收脚本/CI/`Import-Csv` 要稳定读取；PowerShell 5.1 对无 BOM 脚本的编码处理有坑 |
| **`07_bigdata/hive/0X_*.sql` 是"单一事实来源"** | 实验定义写在 SQL 里（`-- @case/-- @conf/-- @var/-- @reps`），harness 与人工重跑用同一段 SQL |

## 7. 最容易再踩的坑（完整 51 条见 v3 附录 B）

| 现象 | 对策 |
|---|---|
| Docker daemon 所有 API 返回 **500** | GB 级结果集流经 `docker exec` 会卡死 daemon；改用 `INTO OUTFILE` + `docker cp`；重启 Docker Desktop 可恢复 |
| `spark.eventLog.dir` 报 **FileNotFound** | Spark **不会自动建目录**，先 `New-Item -ItemType Directory -Force 08_benchmark\_spark_events` |
| `executor` 起不来 / 内存不足 | Docker VM 7.64 GB：先 `docker stop credit-dwh-mysql`；worker 已限 2g |
| CTAS 报 `Partition column types may not be specified` | CTAS 里写 `PARTITIONED BY (col)`，**不要带类型** |
| 写分区表报 `Dynamic partition strict mode` | `--conf hive.exec.dynamic.partition.mode=nonstrict`（这条报错**反证** Spark 确实读该参数） |
| `measure_files.sh` 把分区表数成 0 个文件 | 分区表 Hive-serde 写路径的文件**没有 `.orc` 扩展名**（叫 `part-*.c000`），要按 `part-*` 统计并排除 `.crc` |
| 事件日志解析：task 耗时全 0 / 找不到 SQL 事件 | `Executor Run Time` 在 **Task Metrics** 里（毫秒）；SQL 事件名带命名空间前缀；未压缩日志名是 `app-*` |
| `MetaException: Unable to create database path` | Metastore 容器要以 **`user: root`** 运行（默认 hive 用户对 root 所属卷无写权限） |
| `ss \| grep 9083` 报 NOT LISTENING | `apache/hive` 镜像**没装 ss/netstat**（假阴性）→ 用宿主 TCP 连接或 `grep 237B /proc/net/tcp{,6}` |
| `spark.sql("USE db; SELECT ...")` 报语法错 | PySpark 的 `spark.sql()` **只接受单条语句** → 用 `spark.catalog.setCurrentDatabase()` |
| 双引擎比率列差 5e-5 | MySQL `div_precision_increment=4`；用"差异 ≤5e-5 + 平局判据"两条断言，别放宽容差 |
| 打印 ✅ 抛 `UnicodeEncodeError: 'gbk'` | 脚本开头 `from src.utils import setup_console_encoding` |
| `.sh` 报 `bad interpreter` | `.sh` 必须 **LF** 换行 |
| `docker compose` 报内存不足 | 不用 Kafka/Flink 时 `docker stop bd-*`（阶段三实验只需 4 个容器） |
| ⭐ CI 里 `pytest` 报 `No module named 'src'`（本地却没事） | 裸 `pytest` 不把仓库根加进 `sys.path` → `pytest.ini` 加 **`pythonpath = .`**；本地也用与 CI 相同的命令（B-46） |
| ⭐ CI 里 `ruff check ... 09_realtime/` 报错 | **ruff 对不存在的路径直接报错**（不是跳过）→ CI 只写真实存在的目录（B-47） |
| ⭐ `pip install` 十几分钟没进展 | 本机 PyPI 直连吞吐极低（清华源这次也卡）→ 用 `-i https://mirrors.aliyun.com/pypi/simple`（实测 60 秒装完，B-48） |
| ⭐ `git push` 报 `Failed to connect to 127.0.0.1 port 7897` | 本机 git 配了本地代理 `http.proxy=127.0.0.1:7897`，**代理没开时 git 仍去连它**；开代理后若仍失败，是代理没有可用出口节点（B-49） |

## 10. 已知的诚实缺口（面试要如实说）

1. **E4 每个配置只跑了 1 次**（`--reps 1`）→ 10 桶 vs 20 桶、AQE 各方案的 0.2–0.4 s 差异需 3 次取中位；
2. **E5 阶梯只有 3 个点**，交叉点靠外推；且 **MySQL 容器未限 cpus、Spark 限了 4 核**，两侧资源未严格可比；
3. **MySQL 第一次 15 s 的冷缓存效应**只标注了现象，没有专门设计实验隔离；
4. **`dim_date` 只建到 2008-01-01 起**，覆盖不到最早 6 个月的 **603 笔**贷款（阶段三不依赖它）；
5. **实时链路与批流对账未做**（第 19 步）—— 目前**不能**在简历上写"做过实时"。
   `docs/SLA与监控.md` 里的批流对账**只有规则没有实现**；血缘图里
   `ads_loan_daily_realtime` 是**虚线 + 标注"规划中"**，那张表**并不存在**。
6. **工程化已做（第 18 步），但要说准**：口径层有 **34 条**回归单测 + CI
   （ruff / pytest / 血缘一致性校验），但——
   - **ETL 脚本（阶段二 8 个）没有测试**，也没有覆盖率统计；
   - **CI 不连数据库**，所以它**不跑任何数据链路**（这是刻意取舍，也是局限）；
   - **没有调度器、没有告警通道**，`sla_check.py` **未实现**（SLA 文档给的是**判据**不是自动化任务）；
   - ruff 只开了"真错"类规则，**代码风格尚未统一**。
   所以可以写"把核心口径抽成纯函数并做成 CI 回归"，
   **不能**写"有完善的单测覆盖 / 有全链路数据监控"。
7. **⚠️ 阶段三的提交全都还没推上 GitHub（重要，别以为 CI 已绿）**：
   本地**领先 `origin/main` 一整段**（阶段三第 12–18 步的提交 + `JianLi.md`），
   而本地记录的 `origin/main` 仍停在阶段二的 `89c28d3` ——
   也就是说 **GitHub 上还没有阶段三的任何代码，更不会有 CI 绿勾**。
   `git push` 失败的根因是**本机代理把 `github.com` 分流成了直连**（TLS 被重置），
   而 `api.github.com` / `pypi.org` / `raw.githubusercontent.com` 走代理都是通的 ——
   所以**节点没全坏，是规则问题**（完整排查见附录 **B-49** 与验收记录 §5）。
   补绿勾：开代理（必要时切 **Global 模式**）→ `git push origin main` → 看 Actions 的 `CI / lint-and-test`。
