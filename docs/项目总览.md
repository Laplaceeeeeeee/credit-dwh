## 1. 一句话定位

把一份 **226 万行**的公开信贷放款流水（LendingClub），加工成一套能回答三个风控问题的数据底座，
**并且用一整套机制证明它没做错**。

| # | 业务问题 | 靠什么回答 |
|---|---|---|
| 1 | 这笔贷款会不会逾期？ | 申请时点事实表 + 表现期事实表 → 风险分层指标表 |
| 2 | 哪批客户质量在恶化？ | 月末快照事实表 → Vintage 矩阵（**对齐账龄**后比较批次）|
| 3 | 风控策略改完有没有效果？ | 迁徙率矩阵 + 产品维 —— ⚠️ **本数据只能部分回答**，见 §7 |

**做的是数据工程/数仓，不是机器学习建模。**

## 2. 架构总览

```
LendingClub 原始 CSV（374 MB）
   │  ① 探查与清洗：剔 33 行散布页脚、剔 14 个整列为空的字段
   ▼
干净 Parquet（337.6 MB / 2,260,668 行 × 137 列）
   │
   │  ② 阶段二 · MySQL 四层数仓（13 张表）
   │     四层加工链：ODS → DWD → DWS → ADS
   │        ODS  ods_loan_raw            原样落地，留证/回滚点
   │        DWD  dwd_loan_fact           申请时点事实表（严禁表现期字段）
   │        DWD  dwd_loan_perf_fact      表现期事实表（is_bad / is_terminal）
   │        DWS  dws_loan_snapshot_m     月末快照（一笔贷款 × 一个观测月）
   │        ADS  ads_risk_segment / ads_vintage / ads_roll_rate / ads_delinq_monthly
   │     维表层（3 张，与 DWD 平级扇出，不计入"层"）
   │        dim_applicant（粒度=一笔贷款，因 member_id 整列缺失无法建客户维）
   │        dim_product / dim_date
   │     运维表（2 张，不承载业务数据）
   │        etl_watermark / dq_check_result
   │
   │  ③ 阶段三 · 迁到 Hive/Spark（同一套口径）
   │     外部 Hive Metastore + Spark 执行 + ORC 列存 + 按放款月分区
   │     双引擎逐行对账 + 5 个对照实验 + 工程化收口
   │
   │  ④ 阶段四 · 实时链路 + 湖仓
   ▼
MySQL dwd_loan_fact --(Flink CDC 抓 binlog)--> Kafka（debezium-json 变更日志）
    --> 一个 Flink 作业（EXECUTE STATEMENT SET，三个 sink 共享源）
          ├─ Paimon rt_loan_fact_latest   主键表：镜像最新状态（含 sink_ts 供测延迟）
          ├─ Paimon rt_loan_change_1min   1 分钟滚动窗口（事件时间 + Watermark）
          └─ Paimon rt_loan_month_agg     按放款月维护的 upsert 指标表 ← 对账的实时侧
    --> 读取：Flink batch（对账导出）／ Spark 只读直读（快照隔离 + 时间旅行）
```

## 3. 术语与口径约定（**本项目统一按这一节说话**）

### 3.1 层数怎么数

| 类别 | 内容 | 数量 |
|---|---|---|
| **四层加工链** | ODS 1 + DWD 2 + DWS 1 + ADS 4 | **8 张** |
| **维表层（DIM）** | 3 张维表 | **3 张** |
| **运维表（OPS）** | 水位表 + 质量结果表（不承载业务数据） | **2 张** |
| **合计** | | **13 张** |

> ⚠️ **不要说"六层数仓"**。血缘图里的 `layer` 字段有 6 个取值（ODS/DWD/DIM/DWS/ADS/OPS），
> 但"层"指的是**数据加工深度**：ODS→DWD→DWS→ADS 是单向加工链。
> **DIM 不在链上**（维表是描述性属性，本项目里与 DWD 平级扇出）；**OPS 根本不是数仓的一部分**。
>
> 另注：DIM 算不算一层是**公司惯例问题**（有四层/五层/三层几种叫法）。
> 讲的时候要说清"我们用四层口径"，不要只给一个数字。

### 3.2 关键口径

| 口径 | 定义 | 为什么这么定 |
|---|---|---|
| **不良** | `Charged Off` + `Default` + 政策外核销，共 **269,360** 笔 | 口径写在 `src/config.py`，全局唯一 |
| **不良率** | 不良笔数 / **终态**笔数 = **19.9807%**（269,360 / 1,348,099） | 分母必须排除 `Current`（占 38.85%，结果未定）；含进去会低估到 **11.9155%**（差 8 个百分点） |
| **加权平均利率** | 按 `funded_amnt` 加权 = **13.3824%** | 简单平均会让 1 千元与 4 万元贷款同权 |
| **Vintage 比较** | 必须**对齐账龄 MOB** 后再比 | 老批次账龄长、暴露更充分，直接比累计值不公平 |
| **迁徙率 DPD 档位** | 按规则从 `loan_status` 推导 | 本数据无逐月还款记录，档位是推导值，文档已标注假设 |
| **金额容差（对账）** | **0.00** | 两侧都是精确十进制求和，差异本身就该是问题信号，不该被容差吞掉 |
| **比率容差（双引擎）** | **5e-5 + 平局判据** | MySQL `div_precision_increment=4` 的量化语义差异，有明确根因才给容差 |

## 4. 三阶段产出与关键实测数字

### 4.1 阶段二 · MySQL 四层数仓

| 项 | 实测 |
|---|---|
| 数据规模 | 2,260,668 行 × 137 列；放款跨度 **2007-06 ~ 2018-12（139 个月）** |
| 表数量 | **13 张**（四层主干 8 + 维表 3 + 运维 2）|
| 数据质量校验 | **8 条规则 11 项校验全通过** |
| 月末快照表 | **4,471 万行**（`mob <= 24`）|
| 快照写入吞吐 | 主键顺序优化后 **5,379 → 38,032 行/秒**；480 万行灌数 **26 分钟 → 4.2 分钟** |
| 风险分层单调性 | A 级 **6.04%** → G 级 **49.67%**（约 8.2 倍跨度）|
| 迁徙率关键节点 | `DPD_31_120 → DPD_120_PLUS` = **50.87%** |

**数据事实（实测，`data/clean/clean_meta.json`）**：
物理 2,260,702 行 = 表头 1 + **页脚 33（散布在文件中部）** + 真实 2,260,668；字段 151 → 保留 137（剔除 14 个整列为空）。

### 4.2 阶段三 · Hive/Spark

| 项 | 实测 |
|---|---|
| 双引擎一致性 | 关键指标 **7/7 一致，最大差异 0.0**；4 张 ADS **逐行一致**（18 / 24,768 / 108 / 3,105 行，键未匹配 0）|
| 比率列差异 | 最大 **5e-5**，归因为 MySQL `div_precision_increment=4`；用"容差上界 + **平局判据**"两条断言覆盖 |
| E1 分区裁剪 | 扫描文件 **139 → 1**、字节 **48.54 MB → 0.88 MB**；**非分区表同谓词对照仍读 47.87 MB** → 证明省的是 IO 不是计算 |
| E2 小文件 | 文件数 **2400 → 12**，查询 **2.22 s → 0.28 s（7.9×）**，任务数 75 → 4 |
| E3 列存格式 | 体积 Text/Parquet/ORC = **151.68 / 28.85 / 34.37 MB**；少列查询 **0.95 / 0.33 / 0.32 s（3.0×）**，全列收窄到 **2.4×**；⚠️ 本次 **Parquet 比 ORC 小 16%**（有一列是唯一字符串）→ 推翻"ORC 一定更小"的成见 |
| E4 数据倾斜 | 最大 key 占比 **47.63%**、倾斜比 **4.29**、最长÷中位 task **4.48**；加盐 **5/10/20 桶 = 7.58 / 2.39 / 2.00 s**（5 桶无效；10 vs 20 差异在噪声内）；**AQE 管不了聚合倾斜（7.31 s）**；`REBALANCE` 提示 **1.75 s 最快** |
| E5 引擎选型 | 226 万行：MySQL 端到端 **3.94 s** vs Spark 应用内 1.52/1.13/1.08 s；**Spark 固定开销 3.94 s → 端到端 5.07 s**；**推荐 MySQL 单机**，切换点外推约 **270 万行** |
| 工程化 | 口径回归单测 **34 条**（不依赖数据库）｜ruff **0 error**｜**25 节点血缘**（规划中 0）｜**四类 SLA** |

### 4.3 阶段四 · 实时链路 + 湖仓

版本矩阵（查制品锁定，全部实拉实跑）：
Flink **1.20.5** · Paimon **1.4.2** · Flink CDC **3.6.0-1.20** · Kafka **4.3.1** · Paimon-Spark **3.5_2.12:1.4.2**
> ⚠️ 刻意**不用**最新的 `flink:2.3.0` —— Paimon 只发布到 `paimon-flink-2.2`，照抄"最新 tag"必然撞墙。

| 里程碑 | 关键数字 |
|---|---|
| **M1 链路通** | 端到端延迟 **≈310 ms**（MySQL `NOW(3)` → Paimon `sink_ts`）；226 万行全量快照 **34 秒** |
| **M2 正确性** | 故障演练：`pause` TaskManager → JM 在 **50.4 秒**判定失效（= `heartbeat.timeout` 50 s）→ 恢复后 **5.1 秒** RUNNING、**10 秒**内补发停机期间的变更；**抓出并修复 `latest-offset` 静默丢数据** |
| **M3 批流对账** | **139 个放款月，笔数差 0、金额差 0.00**；总笔数 2,260,668、总额 34,004,208,600.00 两侧完全一致 |
| **M4 湖仓查询** | Spark 直读**同一份** Paimon 存储；同一次查询里最新快照 **2,260,669** 与 `VERSION AS OF` 历史快照 **2,260,668** 并存；**可见性延迟 ≈9.8 s** |

**两个延迟必须分清**：
- **310 ms** = 变更到达 Kafka（入队）
- **9.8 s** = 变更**可被查询引擎看到**（Paimon 快照提交绑定在 Flink checkpoint 上，配置 10 s 间隔）

**事件时间语义（实测边界）**：

| 用例 | 记录级（主键表） | 窗口级 |
|---|---|---|
| `op_ts` 落在**已关闭**窗口（迟到 3 分钟） | **收到了** | **未计入**（窗口定稿后不被改写）|
| 按墙上时钟"晚 90 秒"、但 Watermark 未越过 | 收到了 | **正常计入** |

> **记录不会丢，但窗口会丢迟到数据；而"迟到"是相对 Watermark 判定，不是相对墙上时钟。**

## 5. 核心设计决策与理由

| # | 决策 | 理由 | 明确接受的代价 |
|---|---|---|---|
| 1 | **申请时点 / 表现期物理分表** + 字段黑名单自动校验 | 信贷数据经典陷阱：`loan_status` 等是放款后才知道的，混用会造成**数据泄漏**；防线靠机制不靠自觉 | 多一张表、多一次 join |
| 2 | **月末快照事实表**替代 SCD2 拉链表 | 本数据是放款时点静态快照，无真实属性变更序列，硬做 SCD2 只能造假 | 不覆盖"属性中途变化"的场景 |
| 3 | **申请人画像维**替代客户维 | `member_id` 整列为空，不拼伪客户 ID（会造成错误关联）| **客户级分析不可做** |
| 4 | **快照表主键 `(snapshot_month, loan_id)`** | 与逐月写入同序 → 聚簇索引顺序追加 | 与"按贷款查该笔各月"的访问模式相反 |
| 5 | **226 万行推荐 MySQL 单机** | 实测端到端 MySQL 3.94 s < Spark 5.07 s（Spark 固定开销 3.94 s）| 结论只对"单 JOIN + 分组聚合"形态成立 |
| 6 | **实时链路选 Flink 1.20.5 而非最新** | Paimon 只发布到 `paimon-flink-2.2`（制品实测）| 版本较旧 |
| 7 | **CDC → Kafka → Flink → Paimon**（中间过 Kafka）| 解耦出多个消费方；拿到"消息队列"这个实时岗标配 | 多一跳延迟、多一个容器 |
| 8 | **Kafka 存变更日志（debezium-json）而非最新状态** | 下游能自己决定"要事件流还是要状态"；存最新状态会丢掉过程 | 下游需自己处理 changelog 语义 |
| 9 | **Paimon 而非 Iceberg** | 需要主键更新 + 流读 + changelog（信贷表按 `loan_id` 反复更新）| ⚠️ **没做 Iceberg 对照实验** |
| 10 | **`scan.startup.mode = initial`** | `latest-offset` 会在重启时**静默跳过**停机期间的变更（M2 故障演练抓出的缺陷）| 位点丢失时会退回全量快照（慢，但不丢）|
| 11 | **仓库以 `:ro` 只读挂载给 Spark** | 读者不该写湖；也避免两引擎竞争写同一张表 | Spark 不能写 |
| 12 | **口径抽成纯函数**（`src/metrics.py`）| 只有这样口径才能进 CI（CI 不连数据库）| ETL 脚本本身没有单测覆盖 |

**`latest-offset` 缺陷的完整证据链**（阶段四最有价值的产出）：
故障演练中，TaskManager 停机 50.6 秒期间插入的 3 笔记录，恢复后**整段丢失且不报错**。
Debezium 日志实测：`Snapshot ended ... currentBinlogPosition=6294` ——
重启时它取了**当前** binlog 位置当起点，而停机期间的变更在该位置之前。
**更危险的是不确定**：同一份配置两次演练，一次丢、一次没丢。
修复后用**只改这一个参数的对照实验**验证：Kafka 偏移 2,260,668 → 2,260,671，3 笔全部补上。

## 7. 诚实边界汇总（**面试与交接都必须先看这一节**）

### 7.1 数据本身的限制（不是实现问题，改不了）

- **只有已放款样本、没有拒绝客群** → 幸存者偏差；**批准率指标已删除**（分母不存在）；
  **"策略效果"只能部分回答**（能证明"某批 C–E 级占比从 X% 升到 Y%"，不能证明"是准入放松导致"）
- **只有最终状态、没有逐月还款记录** → 迁徙率的 DPD 档位是**按规则推导**的，已标注假设
- **没有真正的日粒度** → `issue_date` 一律是"当月 1 日"，**批流对账按放款月做，不是日**
- **`member_id` 整列为空** → 客户级分析不可做

### 7.2 实现与验证的缺口（可补，但没做）

| 缺口 | 说明 |
|---|---|
| **E4 每组只跑 1 次** | 10 桶 vs 20 桶那 0.39 s 差异**不下结论**（落在单次测量噪声内）|
| **E5 交叉点是外推** | 约 270 万行；且 MySQL 未限核而 Spark 限 4 核，**两侧资源不严格可比** |
| **exactly-once 没做对照实验** | 只验证了端到端结果正确；**没有关掉 Kafka 事务/Paimon 两阶段提交来对比**；且 Paimon 主键去重会**掩盖**重复写入，所以"主键表无重复行"**不能**作为 exactly-once 证据 |
| **故障演练只测了 INSERT** | 未测停机期间的 UPDATE / DELETE |
| **未测 DDL 变更（加列）后的链路行为** | |
| **未验证快照失败后的重试与恢复** | 实时侧依赖全量快照能成功；binlog 历史超 30 天就补不回来 |
| **时间旅行只验了 snapshot id** | 未验 Paimon 的 tag / branch |
| **只验了 Spark 读** | 未验 Spark 写 Paimon，也未验多写者并发 |
| **可见性延迟只测 1 个点** | "≈checkpoint 间隔"是**由机制推出的解释**，不是实测曲线 |
| **迟到数据的两个用例是手工注入 Kafka 的** | 不是真实业务流量（CDC 无法回填 binlog 时间）|
| **实时侧只覆盖放款月笔数/金额** | Vintage、迁徙率、分层不良率**没有实时侧对应物** |
| **ETL 脚本（阶段二 8 个）没有单测** | 只有口径层有 34 条；也无覆盖率统计 |
| **CI 不连数据库** | 因此**不跑任何数据链路**（刻意取舍，也是局限）|
| **无调度器、无告警通道** | SLA 四类里只有判据与手动脚本，**不是自动化任务** |
| **`dim_date` / `dim_product` 是无下游或未进 ADS 的诚实空白** | `dim_date` 还够不到最早 6 个月的 603 笔贷款 |

### 7.3 规模与环境的限制（**不要声称**）

- **单机**：1 个 Kafka broker、1 个 JobManager、1 个 TaskManager（4 slot）、Docker VM 7.64 GB
- **不是集群**、**无高可用**、**没有做过任何吞吐/压力测试**
- **没有真实业务实时源**（源是真实 binlog，但业务场景是历史库的回放式写入）
- **只用 Spark（`local[*]`）验证湖仓直读**，**没和 StarRocks / Doris / Trino 对比**
- **没做同查询的引擎性能对比** → **不能声称"湖仓查询更快"**
- **数据规模 226 万行 / 约 6.8 GB** → 面试官问"多大数据量"时如实回答这个数字


> ⚠️ **两条内存规则方向相反，不要照抄**：
> 阶段三是"跑 Spark 重任务前停 MySQL"；
> **阶段四是 CDC 需要 MySQL 活着，该停的是 Hive/Spark 那四个容器。**
>
> ⚠️ **`docker exec` 必须加 `-u flink`**：默认是 root，而 Flink 守护进程是 uid 9999，
> DDL 以 root 建出的 warehouse 目录会让 TaskManager 写不进去（详见 B-12）。
