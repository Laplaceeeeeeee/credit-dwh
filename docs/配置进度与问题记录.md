## 三、发现并修复的问题

### 问题 1：`skipfooter` 与 `chunksize`/`nrows` 互斥 🔴 致命

**现象**：指导书里 6 个代码块使用 `pd.read_csv(..., chunksize=X, skipfooter=1, engine="python")`，
**在 pandas 2.2.2 与 3.0.5 上均直接抛错**：

```
ValueError: 'skipfooter' not supported for iteration      # 与 chunksize
ValueError: 'skipfooter' not supported with 'nrows'       # 与 nrows
```

**影响**：所有分块读取脚本（EDA、ODS、DWD、DWS）**一行都跑不起来**。

**修复**：新增 `src/prepare_raw.py`，**只做一次**页脚剔除，产出干净 Parquet；
后续所有脚本读 Parquet（C 引擎），不再碰 `skipfooter`。

**副作用（正面）**：读取速度从 python 引擎的 20–40 分钟降到 **79 秒**。

---

### 问题 2：页脚不是 1 行，而是散布全文的 33 行 🔴 严重

**现象**：`skipfooter=1` 只删最后一行，另外 **32 行**混进数据：

```
行  421096  Total amount funded in policy code 1: 6417608175,,,,...
行  421097  Total amount funded in policy code 2: 1944088810,,,,...
行  528962  ...（间隔约 10~23 万行出现一次，共 16 对）
行 1651666  Loans that do not meet the credit policy,,,,...     ← 章节标题
行 2260700  Total amount funded in policy code 1: 1465324575,,,,...
行 2260701  Total amount funded in policy code 2: 521953170,,,,...
```

**根因**：这个文件**不是一份单纯导出**，而是**多个年度分段拼接**而成，
段间夹着章节标题与 `policy code 1/2` 汇总行。

**连锁后果**：这些非数字值落在 `id` 列，导致 pandas 把 `id` 推断成字符串，
分块写入时触发 schema 不一致：
`ValueError: Table schema does not match schema used to create file`

**修复**：全文件扫描，按"`id` 首字段必须是纯数字"判定并剔除全部 33 行。
页脚原文留证在 `data/clean/footer_line.txt`。

**这也解释了行数之谜**：2,260,702 − 1 − 33 = **2,260,668**，
正好等于指导书里"2,260,700 − 32"的数字 —— 那 32 行**本质就是页脚行**，此前归因错了。

---

### 问题 3：`member_id` 整列为空（+ 13 个全空列）

**实测**：`member_id` 在 226 万行里**非空值为 0**。
全空列共 **14 个**（含 `member_id`、7 个 `sec_app_*`、`revol_bal_joint` 等），已整体剔除。

**影响**：**无法建客户维**，"一人多贷"分析不可做。

**修复**：`dim_customer` 改为 **`dim_applicant`（申请人画像维）**，
粒度 = 一笔贷款，主键 = `loan_id`。
**明确不采用**用 `annual_inc + addr_state` 拼"伪客户 ID"的做法。

---

### 问题 4：MySQL 保留字 `year_month`

**现象**：
```
ERROR 1064 (42000): You have an error in your SQL syntax ... near 'year_month CHAR(7)'
```

**修复**：DDL 中**所有列名统一加反引号**，从根上免疫保留字问题。

### 问题 5：MySQL 端口不一致

compose 映射 `3307:3306`，而 `config.py` 连 `3306`。
**修复**：`config.py` 默认端口改为 **3307**。

### 问题 6：控制台 GBK 编码导致 emoji 崩溃

**现象**：`UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'`
—— 脚本里大量 `✅ ❌ ⚠️`，一 print 到终端就崩。

**修复**：`src/utils.py` 导入时调用 `setup_console_encoding()`，
自动 `reconfigure(encoding="utf-8")`。

### 问题 7：分块读取的 dtype 漂移

**现象**：`verification_status_joint` 在第 1 块是 string、第 2 块是 double，
写 Parquet 时报 schema 不匹配。

**修复**：用首块探测 schema 并**固定 dtype**，后续所有块带同一 dtype 读取。

而文件按年份排序，所以子集偏向**早期放款**：

| loan_status | 子集（前 20 万行） | 全量（226 万行） |
|---|---|---|
| Fully Paid | 70.50% | 47.63% |
| Charged Off | 17.55% | 11.88% |
| Current | **11.32%** | **38.85%** |

> 🔑 **含义**：子集里 `Current` 只占 11%，因为早期贷款基本都已结清。
> **比例型指标（不良率、Vintage）必须用全量算**，子集只适合调流程。
> 最后出简历数字前，把 `config.MAX_ROWS` 改成 `None` 重跑即可。
