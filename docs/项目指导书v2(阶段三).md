### 11.2 ⭐ 环境方案选择：为什么推荐方案 A

**方案 B（完整 Hadoop）的问题**：
- HDFS NameNode + DataNode + Hive Metastore + HiveServer2 + YARN RM + NM + Spark = **7 个常驻组件**，空转就吃 8–12 GB
- 组件越多，**环境问题越多**，很多人 2 周都跑不通（这正是阶段二提醒过的"陷入环境搭建"陷阱）
- **面试官不会因为你装了 YARN 而加分** —— 他们问的是分区裁剪、数据倾斜、选型依据

**方案 A（轻量）的取舍**：

| 用 | 不用 | 换来的 |
|---|---|---|
| **Spark 3.5（内置 Hive 支持）** | ❌ 独立 HiveServer2 | Hive DDL / 分区表 / ORC / Hive SQL 语法**全部保留** |
| **Hive Metastore（MySQL 后端）** | ❌ 独立 Hive on MR | 表元数据、`spark-sql` 交互、元数据一致语义 |
| **本地卷（Docker volume）** | ❌ HDFS | 免去 NameNode 运维；分区目录布局**完全一致** |
| **spark-sql / PySpark** | ❌ `hive -e` CLI | 同一套 SQL，语法兼容 |

> 🔑 **关键认知**：`spark.sql.catalogImplementation=hive` + Hive Metastore
> = **你在用 Hive 的元数据与表格式，只是执行引擎换成了 Spark**。
> 分区裁剪、小文件、ORC/Parquet、数据倾斜 —— **这五个实验一个都不少**。
>
> 面试时如实说："我用 Spark 作为执行引擎、Hive Metastore 管理元数据" ——
> 这**比含糊地说"我用了 Hive"更专业**。

**如果你内存 ≥ 20 GB 想上方案 B**：见 **附录 D**。
但**建议先用方案 A 把 5 个实验做完**，再考虑升级环境 —— 顺序反了容易烂尾。

### 12.1 导出阶段二的结果

**`07_bigdata/export_to_hive.py`**：

```python
"""把阶段二的 MySQL 表导出为 Parquet 文件，供 Hive/Spark 导入。

设计要点：
1. 只导出【需要的列】—— 阶段二有 151 列，Hive 侧只需关键字段
2. 用 Parquet 作为交换格式 —— 列存、带 schema、比 CSV 快得多
3. 分批导出，避免大表一次性读进内存
"""
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(ROOT))

import pandas as pd
from src.utils import get_logger, get_engine

log = get_logger("export_to_hive")
OUT = ROOT / "07_bigdata" / "exchange"
OUT.mkdir(parents=True, exist_ok=True)

# 表 -> 需要导出的列（必须与 Hive DDL 严格对应）
EXPORTS = {
    "dwd_loan_fact": [
        "loan_id", "loan_amnt", "funded_amnt", "term_months", "int_rate",
        "grade", "sub_grade", "emp_length_years", "home_ownership", "annual_inc",
        "verification_status", "purpose", "addr_state", "dti",
        "fico_low", "fico_high", "issue_date", "issue_month",
    ],
    "dwd_loan_perf_fact": [
        "loan_id", "loan_status", "is_terminal", "is_bad", "dpd_bucket",
        "total_rec_prncp", "total_rec_int", "recoveries", "out_prncp",
        "total_pymnt", "last_pymnt_d", "mob_final",
    ],
    "dws_loan_snapshot_m": [
        "loan_id", "snapshot_month", "snapshot_date", "issue_month", "mob",
        "months_since_last_pymnt", "dpd_bucket", "is_delinquent",
        "is_bad_month", "out_prncp", "total_rec_prncp", "loan_amnt", "grade",
    ],
    "dim_applicant": [
        "loan_id", "annual_inc", "income_band", "home_ownership",
        "emp_length_years", "addr_state", "fico_low", "fico_band", "dti",
    ],
}


def export_table(table: str, cols: list[str], chunksize: int = 200_000):
    eng = get_engine()
    out_dir = OUT / table
    out_dir.mkdir(parents=True, exist_ok=True)

    total, part = 0, 0
    for chunk in pd.read_sql(f"SELECT {', '.join(cols)} FROM {table}",
                             eng, chunksize=chunksize):
        chunk.to_parquet(out_dir / f"part-{part:05d}.parquet", index=False)
        total += len(chunk)
        part += 1
        log.info(f"{table}: 已导出 {total:,} 行（{part} 个文件）")

    log.info(f"✅ {table} 导出完成：{total:,} 行 -> {out_dir}")


if __name__ == "__main__":
    for t, c in EXPORTS.items():
        export_table(t, c)
```

### 12.2 Hive DDL（⭐ 与 MySQL DDL 的关键差异）

**`07_bigdata/hive/01_ddl.sql`**：

```sql
CREATE DATABASE IF NOT EXISTS credit_dwh_lc
COMMENT '信贷数仓 - Hive/Spark 大数据层（与 MySQL 层同口径）';

USE credit_dwh_lc;

-- ============================================================
-- ⭐ Hive/Spark 与 MySQL 的 DDL 差异（面试会问）
--   1. 不设 PRIMARY KEY 约束 —— Hive 不强制主键，唯一性靠 ETL 保证
--   2. 不用 AUTO_INCREMENT 代理键 —— 直接用 loan_id 业务键
--   3. DECIMAL 精度显式声明，且不宜过大（影响列存效率）
--   4. PARTITIONED BY 的列不能出现在字段列表里（分区是目录结构）
--   5. 用 STORED AS ORC/PARQUET 指定列存格式
-- ============================================================

-- ---------- 申请时点事实表（按放款月分区）----------
DROP TABLE IF EXISTS dwd_loan_fact_lc;
CREATE TABLE dwd_loan_fact_lc (
  loan_id             STRING        COMMENT '贷款ID',
  loan_amnt           DECIMAL(14,2) COMMENT '申请金额',
  funded_amnt         DECIMAL(14,2) COMMENT '放款金额',
  term_months         INT           COMMENT '期限月数',
  int_rate            DECIMAL(8,4)  COMMENT '利率（已去%）',
  grade               STRING        COMMENT '信用评级',
  sub_grade           STRING        COMMENT '子评级',
  emp_length_years    INT           COMMENT '工作年限',
  home_ownership      STRING        COMMENT '住房情况',
  annual_inc          DECIMAL(16,2) COMMENT '年收入',
  verification_status STRING        COMMENT '收入核验',
  purpose             STRING        COMMENT '借款用途',
  addr_state          STRING        COMMENT '州',
  dti                 DECIMAL(10,4) COMMENT '债务收入比',
  fico_low            DECIMAL(8,2)  COMMENT 'FICO下限',
  fico_high           DECIMAL(8,2)  COMMENT 'FICO上限',
  issue_date          DATE          COMMENT '放款日期'
)
PARTITIONED BY (issue_month STRING COMMENT '放款月 YYYY-MM')
STORED AS ORC
TBLPROPERTIES ('orc.compress' = 'SNAPPY');


-- ---------- 表现期事实表 ----------
DROP TABLE IF EXISTS dwd_loan_perf_fact_lc;
CREATE TABLE dwd_loan_perf_fact_lc (
  loan_id         STRING,
  loan_status     STRING,
  is_terminal     INT,
  is_bad          INT,
  dpd_bucket      STRING,
  total_rec_prncp DECIMAL(14,2),
  total_rec_int   DECIMAL(14,2),
  recoveries      DECIMAL(14,2),
  out_prncp       DECIMAL(14,2),
  total_pymnt     DECIMAL(14,2),
  last_pymnt_d    DATE,
  mob_final       INT
)
STORED AS ORC;


-- ---------- 月末快照事实表（按观测月分区）----------
DROP TABLE IF EXISTS dws_loan_snapshot_lc;
CREATE TABLE dws_loan_snapshot_lc (
  loan_id                 STRING,
  snapshot_date           DATE,
  issue_month             STRING,
  mob                     INT,
  months_since_last_pymnt INT,
  dpd_bucket              STRING,
  is_delinquent           INT,
  is_bad_month            INT,
  out_prncp               DECIMAL(14,2),
  total_rec_prncp         DECIMAL(14,2),
  loan_amnt               DECIMAL(14,2),
  grade                   STRING
)
PARTITIONED BY (snapshot_month STRING)
STORED AS ORC;


-- ---------- 申请人画像维 ----------
DROP TABLE IF EXISTS dim_applicant_lc;
CREATE TABLE dim_applicant_lc (
  loan_id          STRING,
  annual_inc       DECIMAL(16,2),
  income_band      STRING,
  home_ownership   STRING,
  emp_length_years INT,
  addr_state       STRING,
  fico_low         DECIMAL(8,2),
  fico_band        STRING,
  dti              DECIMAL(10,4)
) STORED AS ORC;
```

> 🔑 **面试必答的 DDL 差异**（这段话要能顺口说出来）：
> "Hive 表不强制主键，唯一性靠 ETL 保证 —— 所以我在导入后专门跑了一次主键去重校验。
> 分区列不放在字段列表里，因为分区本质上是**目录结构**，不是行数据。
> 而 ORC 列存下分区裁剪的收益比行存更明显 —— 这一点我在实验 E1 里量化过。"

### 13.2 ⚠️ 顺带修正一个阶段二的遗留细节

阶段二我们用 `MAX(...) OVER (ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`
解决了"累计不良重复计数"。**在 Spark 上有个更简洁的等价写法**，这次两种都写上并记录差异：

```sql
-- 写法 1（阶段二用的，标准 SQL，Hive/Spark 都支持）
MAX(is_bad_month) OVER (
  PARTITION BY issue_month, loan_id ORDER BY mob
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
) AS ever_bad

-- 写法 2（更简洁，语义相同）
MAX(is_bad_month) OVER (
  PARTITION BY issue_month, loan_id ORDER BY mob
) AS ever_bad
```

> 🔑 **这是一个很好的面试细节**：能说出"窗口默认帧是 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`
> 而不是 `ROWS`，当 `mob` 有重复值时两者语义不同" ——
> 这一句就能证明你真的理解窗口函数，而不是背语法。

USE credit_dwh_lc;

DROP TABLE IF EXISTS ads_vintage_lc;
CREATE TABLE ads_vintage_lc (
  issue_month  STRING,
  grade        STRING,
  mob          INT,
  bad_rate     DECIMAL(10,6),
  exposure_cnt BIGINT
) STORED AS ORC;

-- ⭐ 累计不良率：用窗口函数取"曾核销"标志，避免同一笔被逐月重复计数
INSERT OVERWRITE TABLE ads_vintage_lc
SELECT
    issue_month,
    grade,
    mob,
    ROUND(SUM(ever_bad) / COUNT(*), 6) AS bad_rate,
    COUNT(*)                           AS exposure_cnt
FROM (
    SELECT
        issue_month,
        COALESCE(grade, 'UNKNOWN') AS grade,
        mob,
        loan_id,
        MAX(is_bad_month) OVER (
            PARTITION BY issue_month, loan_id ORDER BY mob
        ) AS ever_bad
    FROM dws_loan_snapshot_lc
    WHERE mob BETWEEN 1 AND 24
) t
GROUP BY issue_month, grade, mob;

-- 口径自检：累计不良率必须随 MOB 单调不减（应为 0 行）
SELECT COUNT(*) AS violation_rows FROM (
    SELECT issue_month, grade, mob, bad_rate,
           LAG(bad_rate) OVER (PARTITION BY issue_month, grade ORDER BY mob) AS prev_rate
    FROM ads_vintage_lc
) x
WHERE prev_rate IS NOT NULL AND bad_rate < prev_rate;

```python
"""把 Hive 侧 ADS 表导出为 CSV，与 MySQL 侧逐行比对。"""
import subprocess
import shutil
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(ROOT))

import pandas as pd
from src.utils import get_logger, read_sql

log = get_logger("compare_ads")
OUT = ROOT / "08_benchmark"

PAIRS = [
    ("风险分层", "ads_risk_segment_lc",
     "dim_type,dim_value,loan_cnt,bad_cnt,bad_rate",
     "ads_risk_segment", "dim_type,dim_value,loan_cnt,bad_cnt,bad_rate",
     ["dim_type", "dim_value"]),
    ("Vintage", "ads_vintage_lc",
     "issue_month,grade,mob,bad_rate,exposure_cnt",
     "ads_vintage", "issue_month,grade,mob,bad_rate,exposure_cnt",
     ["issue_month", "grade", "mob"]),
    ("迁徙率", "ads_roll_rate_lc",
     "from_month,from_bucket,to_bucket,cnt,rate",
     "ads_roll_rate", "from_month,from_bucket,to_bucket,cnt,rate",
     ["from_month", "from_bucket", "to_bucket"]),
]


def spark_to_df(table: str, cols: str) -> pd.DataFrame:
    """导出 Hive 表为 CSV 并读成 DataFrame。"""
    hive_dir = f"/workspace/08_benchmark/_exp_{table}"
    sql = (f"USE credit_dwh_lc; "
           f"INSERT OVERWRITE DIRECTORY '{hive_dir}' "
           f"USING csv OPTIONS ('header'='true') "
           f"SELECT {cols} FROM {table};")
    subprocess.run(["docker", "exec", "bd-spark",
                    "/opt/bitnami/spark/bin/spark-sql", "-e", sql],
                   capture_output=True, text=True, encoding="utf-8")

    local_dir = ROOT / "08_benchmark" / f"_exp_{table}"
    if local_dir.exists():
        shutil.rmtree(local_dir)
    parts = list(local_dir.glob("*.csv")) if local_dir.exists() else []
    if not parts:
        return pd.DataFrame()
    return pd.concat([pd.read_csv(p) for p in parts], ignore_index=True)


def main():
    all_ok = True
    for name, ht, hc, mt, mc, keys in PAIRS:
        log.info(f"--- 比对 {name} ---")
        a = spark_to_df(ht, hc)
        b = read_sql(f"SELECT {mc} FROM {mt}")

        if a.empty:
            log.error(f"❌ {name}: Hive 侧无数据")
            all_ok = False
            continue

        # ⚠️ NULL 安全的连接：直接 = 会漏掉 NULL 行，造成"看似一致"的假象
        for k in keys:
            a[k] = a[k].fillna("__NULL__")
            b[k] = b[k].fillna("__NULL__")

        m = a.merge(b, on=keys, suffixes=("_lc", "_my"))
        log.info(f"  行数: Hive={len(a):,}  MySQL={len(b):,}  匹配={len(m):,}")
        if len(m) != len(b):
            log.error("  ❌ 行数不匹配，存在未匹配的 key")
            all_ok = False

        for col in [c for c in mc.split(",") if c not in keys]:
            ca, cb = f"{col}_lc", f"{col}_my"
            if ca not in m.columns or cb not in m.columns:
                continue
            diff = (pd.to_numeric(m[ca], errors="coerce")
                    - pd.to_numeric(m[cb], errors="coerce")).abs()
            n_bad = int((diff > 1e-6).sum())
            log.info(f"  {'✅' if n_bad == 0 else '❌'} {col}: "
                     f"最大差异={diff.max():.8f} 不一致行数={n_bad}")
            if n_bad:
                all_ok = False
                log.error(f"     样例:\n{m[diff > 1e-6].head(3).to_string()}")

    log.info("=" * 60)
    log.info("✅ 全部一致：口径在两种引擎上完全对齐" if all_ok
             else "❌ 存在不一致，必须在进入性能实验前修复")
    sys.exit(0 if all_ok else 1)


if __name__ == "__main__":
    main()
```

> 原因是分区本质上是文件系统上的**目录结构**，过滤条件下推后 Spark 直接跳过不匹配的目录，
> **根本不读取那些文件**。ORC 列存进一步让每个文件内部只读需要的列 ——
> 两层裁剪叠加，所以「列存 + 分区」的组合收益远大于单纯的行级过滤。"

### 14.3 实验 E2：小文件合并

**为什么要做**：小文件是 Hive/Spark 生产的头号杀手（每个文件对应一个 task）。

**先制造小文件（复现问题）**：

```sql
USE credit_dwh_lc;
SET spark.sql.shuffle.partitions = 200;   -- 故意调大，制造大量小文件

DROP TABLE IF EXISTS tmp_small_files;
CREATE TABLE tmp_small_files
PARTITIONED BY (issue_month STRING)
STORED AS ORC
AS
SELECT /*+ REPARTITION(200) */ *
FROM dwd_loan_fact_lc
WHERE issue_month BETWEEN '2017-01' AND '2017-12';
```

**对照组（合并后）**：

```sql
DROP TABLE IF EXISTS tmp_big_files;
CREATE TABLE tmp_big_files
PARTITIONED BY (issue_month STRING)
STORED AS ORC
AS
SELECT /*+ COALESCE(8) */ *
FROM dwd_loan_fact_lc
WHERE issue_month BETWEEN '2017-01' AND '2017-12';
```

> 🔑 **`REPARTITION` vs `COALESCE` 的区别（面试会问）**：
> - `REPARTITION(n)`：**会触发完整 shuffle**，可以增加也可以减少分区，数据分布均匀
> - `COALESCE(n)`：**尽量不 shuffle**，只能减少分区，靠合并相邻分区实现，更快但可能不均
> 我在这里用 `COALESCE` 是因为目标只是减少文件数，不需要重分布。

**量化小文件**：

```powershell
docker exec bd-spark bash -c "
  base=/opt/bitnami/spark/warehouse/credit_dwh_lc.db
  for t in tmp_small_files tmp_big_files; do
    n=\$(find \$base/\$t -name '*.orc' 2>/dev/null | wc -l)
    s=\$(du -sh \$base/\$t 2>/dev/null | cut -f1)
    echo \"\$t: \$n 个文件, 总计 \$s\"
  done
"
```

**记录表**：

| 组别 | 总文件数 | 平均文件大小 | 查询耗时 | 任务数 |
|---|---|---|---|---|
| Baseline（200 分区） | `__` | `__` KB | `__` s | `__` |
| Treatment（8 分区） | `__` | `__` MB | `__` s | `__` |

**结论模板**：

> "小文件的问题不在总数据量，而在**每个文件都要起一个 task**。
> 200 个 shuffle 分区 → X 个文件 → X 个 task，其中大部分 task 只处理几十 KB，
> **调度开销远大于计算开销**。合并到 Y 个文件后任务数降到 Y，耗时从 A 降到 B。
> 实践经验阈值是**单文件 128–256 MB** —— 太大则单 task 内存压力大、并行度不足；
> 太小则调度浪费。"

### 14.4 实验 E3：列存格式对比

**建三张同结构、不同格式的表，灌同一份数据**：

```sql
USE credit_dwh_lc;

DROP TABLE IF EXISTS fmt_text;
CREATE TABLE fmt_text (loan_id STRING, loan_amnt DECIMAL(14,2), grade STRING,
                       int_rate DECIMAL(8,4), issue_month STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE;

DROP TABLE IF EXISTS fmt_parquet;
CREATE TABLE fmt_parquet (loan_id STRING, loan_amnt DECIMAL(14,2), grade STRING,
                          int_rate DECIMAL(8,4), issue_month STRING)
STORED AS PARQUET;

DROP TABLE IF EXISTS fmt_orc;
CREATE TABLE fmt_orc (loan_id STRING, loan_amnt DECIMAL(14,2), grade STRING,
                      int_rate DECIMAL(8,4), issue_month STRING)
STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

INSERT OVERWRITE TABLE fmt_text    SELECT loan_id, loan_amnt, grade, int_rate, issue_month FROM dwd_loan_fact_lc;
INSERT OVERWRITE TABLE fmt_parquet SELECT loan_id, loan_amnt, grade, int_rate, issue_month FROM dwd_loan_fact_lc;
INSERT OVERWRITE TABLE fmt_orc     SELECT loan_id, loan_amnt, grade, int_rate, issue_month FROM dwd_loan_fact_lc;
```

**两种查询各跑三遍**（体现列存优势的边界）：

```sql
-- 宽查询：只取 2 列 → 列存优势最明显
SELECT grade, COUNT(*) FROM fmt_text    GROUP BY grade;
SELECT grade, COUNT(*) FROM fmt_parquet GROUP BY grade;
SELECT grade, COUNT(*) FROM fmt_orc     GROUP BY grade;

-- 全列查询：取所有列 → 列存优势收窄
SELECT COUNT(*) FROM fmt_text    WHERE grade = 'A';
SELECT COUNT(*) FROM fmt_parquet WHERE grade = 'A';
SELECT COUNT(*) FROM fmt_orc     WHERE grade = 'A';
-- ⚠️ 想更明显的话，把 SELECT * 的结果写出去，让引擎真的读所有列
```

**统计存储体积**：

```powershell
docker exec bd-spark bash -c "
  base=/opt/bitnami/spark/warehouse/credit_dwh_lc.db
  for t in fmt_text fmt_parquet fmt_orc; do
    echo \"\$t: \$(du -sh \$base/\$t | cut -f1)\"
  done
"
```

**记录表**：

| 格式 | 存储体积 | 压缩比 | 少列查询耗时 | 全列查询耗时 |
|---|---|---|---|---|
| TextFile | `__` MB | 1.0×（基准） | `__` s | `__` s |
| Parquet | `__` MB | `__`× | `__` s | `__` s |
| ORC | `__` MB | `__`× | `__` s | `__` s |

**结论模板**：

> "ORC 存储体积是 TextFile 的 1/Z，少列查询快 W 倍 —— 因为列存只读需要的列，
> 而 TextFile 必须扫描整行。两者的差距在**宽表 + 少列查询**时最大；
> 当查询要取全部列时，列存优势会明显收窄。
> ORC 与 Parquet 的差异主要来自编码策略（ORC 的 RLE / 字典编码对低基数列更友好），
> 在我们这种 `grade` / `purpose` 这类低基数列较多的场景下 ORC 略优。"

| Fully Paid | 1,076,751 | **47.6%** |
| Current | 878,317 | **38.9%** |
| Charged Off | 268,559 | 11.9% |

**这是数据倾斜的教科书形态：两个超级 key + 一长串小 key。**

**`08_benchmark/e4_skew_analysis.sql`**：

```sql
USE credit_dwh_lc;

-- ① key 分布：找出热点 key 及其占比、倾斜比
SELECT
    p.loan_status,
    COUNT(*)                                       AS cnt,
    ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4)     AS pct,
    ROUND(COUNT(*) / (SUM(COUNT(*)) OVER ()
                      / COUNT(DISTINCT p.loan_status)), 2) AS skew_ratio
FROM dwd_loan_perf_fact_lc p
GROUP BY p.loan_status
ORDER BY cnt DESC;
```

> 🔑 **`skew_ratio`（倾斜比）= 该 key 占比 ÷ 平均占比。**
> **比值 > 2 算倾斜，> 5 是严重倾斜。**
> `Fully Paid` 会达到 4.3 左右（47.6% ÷ (100%/9类)）—— 具体以实测为准。

### 15.2 第二步：复现问题（看到倾斜的"症状"）

倾斜的症状**不是"慢"，而是 task 耗时严重不均**。

**`08_benchmark/e4_baseline.sql`**：

```sql
USE credit_dwh_lc;

-- ⚠️ 关键：先把 AQE 关掉，否则 Spark 3.x 会自动处理倾斜，你看不到问题
SET spark.sql.adaptive.enabled = false;
SET spark.sql.adaptive.skewJoin.enabled = false;
SET spark.sql.shuffle.partitions = 20;   -- 故意给小并行度，放大倾斜现象

DROP TABLE IF EXISTS e4_baseline_result;
CREATE TABLE e4_baseline_result STORED AS ORC AS
SELECT
    p.loan_status,
    f.grade,
    f.purpose,
    COUNT(*)                       AS loan_cnt,
    ROUND(SUM(f.funded_amnt), 2)   AS total_amnt,
    SUM(f.funded_amnt * f.int_rate) AS rate_numerator,   -- 为加权平均保留分子
    SUM(p.is_bad)                  AS bad_cnt
FROM dwd_loan_fact_lc f
JOIN dwd_loan_perf_fact_lc p ON f.loan_id = p.loan_id
GROUP BY p.loan_status, f.grade, f.purpose;

-- ⭐ 注意：这里存的是 rate_numerator 而不是 avg_rate
--    因为后面加盐两阶段聚合要在最后才做除法（见 15.3 的陷阱说明）
```

② 找到对应的 SQL Query → 点进 Stage
③ 看 "Tasks" 表格的 Duration 列

```

> 🔑 **"最长/中位数"这个比值就是倾斜的量化指标。**
> 接近 1 = 无倾斜；> 5 = 严重倾斜。
> **面试时说出这个比值，比说"很慢"强一百倍。**

### 15.3 第三步：加盐两阶段聚合

**思路**：

```
问题：所有 Fully Paid 的数据都 hash 到同一个 reducer → 一个 task 干 47% 的活
解法：给 key 加随机后缀，把一份大 key 拆成 N 份 → 分散到 N 个 reducer
      局部聚合后去掉后缀 → 再全局聚合一次
```

**`08_benchmark/e4_salted.sql`**：

```sql
USE credit_dwh_lc;

-- ⚠️ 必须与 baseline 保持一致，否则不是公平对比
SET spark.sql.adaptive.enabled = false;
SET spark.sql.adaptive.skewJoin.enabled = false;
SET spark.sql.shuffle.partitions = 20;

-- ⭐ 改这个值来跑不同桶数：5 / 10 / 20
SET salt.buckets = 10;

DROP TABLE IF EXISTS e4_salted_result;
CREATE TABLE e4_salted_result STORED AS ORC AS
WITH salted AS (
    -- 第一阶段输入：给每行打上随机盐
    SELECT
        f.loan_id,
        f.grade,
        f.purpose,
        f.funded_amnt,
        f.int_rate,
        p.loan_status,
        p.is_bad,
        CAST(FLOOR(RAND() * CAST('${salt.buckets}' AS INT)) AS INT) AS salt
    FROM dwd_loan_fact_lc f
    JOIN dwd_loan_perf_fact_lc p ON f.loan_id = p.loan_id
),
stage1 AS (
    -- 局部聚合：(loan_status, grade, purpose, salt) 才是 key，大 key 被拆散
    SELECT
        loan_status,
        grade,
        purpose,
        salt,
        COUNT(*)                    AS part_cnt,
        SUM(funded_amnt)            AS part_amnt,
        SUM(funded_amnt * int_rate) AS part_rate_num,
        SUM(is_bad)                 AS part_bad
    FROM salted
    GROUP BY loan_status, grade, purpose, salt
)
-- 第二阶段：去盐，全局聚合
SELECT
    loan_status,
    grade,
    purpose,
    SUM(part_cnt)  AS loan_cnt,
    ROUND(SUM(part_amnt), 2)      AS total_amnt,
    SUM(part_rate_num)            AS rate_numerator,
    SUM(part_bad)  AS bad_cnt
FROM stage1
GROUP BY loan_status, grade, purpose;
```

**🚨 加权平均的陷阱（两阶段聚合最常见的错误）**：

局部聚合时**不能**先算 `AVG(int_rate)` —— 因为各桶的数据量不同，简单平均会让小桶与大桶同权。
**必须保留 `SUM(int_rate * funded_amnt)` 分子与 `SUM(funded_amnt)` 分母，最后再相除。**

```sql
-- ✅ 正确
ROUND(SUM(rate_numerator) / NULLIF(SUM(total_amnt), 0), 4) AS avg_rate

-- ❌ 错误（各桶同权，结果偏）
AVG(part_avg_rate)
```

> 🔑 这个细节写进文档并能在面试中讲出来，是"真的做过两阶段聚合"的强证据。

### 15.4 第四步：验证正确性（实验有效性的前提）

**加盐前后结果必须完全一致**，否则"优化"是错的。

```sql
-- ⭐ 逐行比对：不一致行数必须全为 0
SELECT
    COUNT(*) AS total_rows,
    SUM(CASE WHEN a.loan_cnt  <> b.loan_cnt  THEN 1 ELSE 0 END) AS cnt_mismatch,
    SUM(CASE WHEN ABS(a.total_amnt - b.total_amnt) > 0.01 THEN 1 ELSE 0 END) AS amnt_mismatch,
    SUM(CASE WHEN a.bad_cnt   <> b.bad_cnt   THEN 1 ELSE 0 END) AS bad_mismatch,
    SUM(CASE WHEN ABS(a.rate_numerator - b.rate_numerator) > 0.01 THEN 1 ELSE 0 END) AS rate_mismatch
FROM e4_baseline_result a
FULL OUTER JOIN e4_salted_result b
  ON  a.loan_status = b.loan_status
  AND a.grade       = b.grade
  -- 🚨 关键：NULL 安全连接。直接 = 会漏掉 NULL 行，产生"看似一致"的假象
  AND COALESCE(a.purpose, '__NULL__') = COALESCE(b.purpose, '__NULL__');
```

> 🚨 **特别注意 `COALESCE(...) = COALESCE(...)`**：
> 如果 `purpose` 有 NULL，直接 `=` 连接会**静默漏掉这些行**，
> 得到"看起来一致"的假结论。**NULL 在 JOIN 中的行为是数据开发的经典坑** ——
> 这个细节写进文档、面试讲出来，非常有说服力。

| salt = 5 | `__` s | `__` s | `__` 倍 | `__` s | ✅ |
| **salt = 10** | `__` s | `__` s | `__` 倍 | `__` s | ✅ |
| salt = 20 | `__` s | `__` s | `__` 倍 | `__` s | ✅ |

**要得出的结论（面试杀手锏）**：

> "我先把 AQE 关掉复现了倾斜：`loan_status` 里 Fully Paid 占 47.6%，
> hash 之后全落到一个 reducer，最长 task 是中位数的 X 倍，整个 Stage 被这一个 task 拖住。
>
> 然后我用加盐两阶段聚合，跑了 5/10/20 三组桶数：
> - 5 桶时最长/中位数降到 A 倍，但桶数太少、单桶仍偏大

> 因为两阶段聚合里 NULL 在 JOIN 与 GROUP BY 中的行为不同，很容易在这里出错。"

> "Spark 3.x 的 AQE 能自动处理倾斜，所以**在新版本上我会优先用 AQE** ——

> ① Spark 2.x 或 Hive on MR 上没有 AQE；

> ③ **AQE 的 skewJoin 只处理 JOIN 倾斜，GROUP BY 造成的倾斜它管不了** ——

### 16.1 PySpark 重写关键链路

**为什么还要写 PySpark**：`spark-sql` 证明你会 SQL，`PySpark` 证明你能写工程化的数据处理代码。

**`07_bigdata/spark/vintage_job.py`**：

```python
"""PySpark 版 Vintage 计算 —— 与 Hive SQL 版结果必须一致。

设计要点（面试会问）：
1. 用 DataFrame API 而不是 SQL 字符串 —— 便于复用与单测
2. 窗口函数显式声明帧 —— 避免默认帧（RANGE）的语义歧义
3. 显式设置 shuffle 分区数 —— 让性能可控、可复现
"""
from pyspark.sql import SparkSession, Window
from pyspark.sql import functions as F


def build_spark(app_name: str = "vintage_job") -> SparkSession:
    return (SparkSession.builder
            .appName(app_name)
            .config("spark.sql.catalogImplementation", "hive")
            # ⭐ 生产习惯：显式设置，不依赖默认值
            .config("spark.sql.shuffle.partitions", "20")
            .config("spark.sql.adaptive.enabled", "true")
            .enableHiveSupport()
            .getOrCreate())


def calc_vintage(spark: SparkSession, mob_max: int = 24):
    """计算 Vintage 矩阵：放款批次 × 账龄 → 累计不良率。

    ⭐ 核心：用窗口函数取"曾核销"标志，避免同一笔贷款被逐月重复计数。
    """
    snap = (spark.table("credit_dwh_lc.dws_loan_snapshot_lc")
            .filter((F.col("mob") >= 1) & (F.col("mob") <= mob_max)))

    # ⚠️ 显式声明 ROWS 帧：默认帧是 RANGE，mob 有重复值时语义不同
    w = (Window
         .partitionBy("issue_month", "loan_id")
         .orderBy("mob")
         .rowsBetween(Window.unboundedPreceding, Window.currentRow))

    snap = snap.withColumn("ever_bad", F.max("is_bad_month").over(w))

    return (snap
            .groupBy("issue_month", "mob")
            .agg(F.count(F.lit(1)).alias("exposure_cnt"),
                 F.sum("ever_bad").alias("bad_cnt"))
            .withColumn("bad_rate",
                        F.round(F.col("bad_cnt") / F.col("exposure_cnt"), 6))
            .select("issue_month", "mob", "bad_rate", "exposure_cnt"))


def main():
    spark = build_spark()
    spark.sparkContext.setLogLevel("WARN")
    try:
        vintage = calc_vintage(spark)
        (vintage.write.mode("overwrite").format("orc")
         .saveAsTable("credit_dwh_lc.ads_vintage_spark"))

        cnt = spark.table("credit_dwh_lc.ads_vintage_spark").count()
        print(f"✅ ads_vintage_spark 写入完成：{cnt:,} 行")
        vintage.orderBy("issue_month", "mob").show(10, truncate=False)
    finally:
        spark.stop()


if __name__ == "__main__":
    main()
```

# 引擎选型结论

## 1. 本项目的量级下，我推荐哪个引擎？

**推荐：MySQL（单机）**

| 维度 | MySQL | Spark |
|---|---|---|
| 226 万行跑批耗时 | `__` s | `__` s |
| 资源占用 | 1 个容器约 1 GB | master+worker 约 5 GB |
| 运维复杂度 | 低 | 中（多组件、需调参） |
| 冷启动开销 | 无 | 每次作业约 `__` s |

在 226 万行这个量级，**MySQL 的绝对耗时并不比 Spark 差，但资源占用与运维成本低一个量级**。
所以我推荐单机。

## 2. 切换阈值在哪？

基于 E5 阶梯测试：
- 10 万 ~ 100 万行：MySQL 略优或持平
- 100 万 ~ `__` 万行：Spark 开始追平 / 反超
- **约 `__` 万行以上：Spark 明显更优**

原因：Spark 有固定的**作业启动开销**（约 `__` s），数据量小时该开销占比过高；
数据量增大后，**并行的收益开始超过固定开销** —— 两条曲线的交叉点就是阈值。

## 3. 除了数据量，还有哪些因素会让我选 Spark？

1. **数据源本身就在 HDFS / 对象存储上** —— 避免数据搬迁
2. **需要复杂的多轮迭代计算** —— Spark 内存计算优势明显
3. **需要与实时链路共用一套 SQL 口径** —— Structured Streaming 与批处理同 API
4. **数据量会在可预见时间内增长** —— 提前建好可扩展链路
5. **已在用 Hive 元数据管理** —— 复用元数据与权限体系

## 4. 我的方案在这个量级下的"过度设计"与"必要设计"

诚实地说：
- **过度设计**：为一个 226 万行的数据集搭 Hive 集群，从成本角度看并不必要
- **必要设计**：**分层建模、口径字典、数据质量校验、增量加工、调度** ——
  这些与数据量无关，是数据治理的必需品

我做这个项目的目的是**验证同一套口径在不同引擎上的表现并得出选型依据**，
而不是声称"我的数据量需要分布式"。
```

```python
"""把历史放款数据回放进 Kafka，模拟实时事件流。

⭐ 诚实声明：这不是真实实时数据，是用历史数据回放来验证实时链路的架构。

import json
import sys
import time
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(ROOT))

from kafka import KafkaProducer
from src.utils import get_logger, read_sql

log = get_logger("replay")
TOPIC = "loan_issue_events"


def main(limit: int | None = 200_000):
    producer = KafkaProducer(
        bootstrap_servers=["localhost:29092"],
        value_serializer=lambda v: json.dumps(v, default=str).encode("utf-8"),
        key_serializer=lambda k: str(k).encode("utf-8"),
    )

    log.info("读取历史数据 ...")
    df = read_sql("""
        SELECT f.loan_id, f.loan_amnt, f.funded_amnt, f.grade, f.sub_grade,
               f.int_rate, f.issue_date, f.issue_month, f.purpose, f.addr_state
        FROM dwd_loan_fact f
        ORDER BY f.issue_date
    """)
    if limit:
        df = df.head(limit)
    log.info(f"共 {len(df):,} 条待回放")

    t0, sent = time.time(), 0
    for row in df.itertuples(index=False):
        producer.send(TOPIC, key=row.loan_id, value={
            "event_type": "LOAN_ISSUED",
            "event_time": f"{row.issue_date}T00:00:00+08:00",  # ⭐ 显式带时区

            "loan_amnt": float(row.loan_amnt or 0),
            "funded_amnt": float(row.funded_amnt or 0),
            "grade": row.grade,
            "int_rate": float(row.int_rate or 0),
            "purpose": row.purpose,
            "addr_state": row.addr_state,
        })
        sent += 1
        if sent % 10000 == 0:
            el = time.time() - t0
            log.info(f"已发送 {sent:,} 条，耗时 {el:.1f}s，速率 {sent/el:.0f} 条/秒")

    producer.flush()
    log.info(f"✅ 回放完成：{sent:,} 条，总耗时 {time.time()-t0:.1f}s")


if __name__ == "__main__":
    main()

**Flink 作业**（`09_realtime/flink_daily_metrics.py`）：

```python
"""Flink 实时指标：当日放款笔数与金额。

⭐ 只覆盖三个核心技术点（不贪多）：
   1. Event Time 语义 + Watermark（处理乱序 / 延迟数据）
   2. 滚动窗口聚合
   3. 输出到下游（幂等写入由下游主键 UPSERT 保证）
"""
import json
from datetime import datetime

from pyflink.common import Duration, WatermarkStrategy
from pyflink.common.serialization import SimpleStringSchema
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.datastream.connectors.kafka import (
    KafkaSource, KafkaOffsetsInitializer)
from pyflink.datastream.window import TumblingEventTimeWindows


def parse_ts(event_json: str) -> int:
    """从事件里取 event_time，转成毫秒时间戳（Flink 要求）。"""
    e = json.loads(event_json)
    return int(datetime.fromisoformat(e["event_time"]).timestamp() * 1000)


def main():
    env = StreamExecutionEnvironment.get_execution_environment()
    env.set_parallelism(2)
    # ⭐ 开启 checkpoint 才能谈 Exactly-Once
    env.enable_checkpointing(10_000)

    source = (KafkaSource.builder()
              .set_bootstrap_servers("kafka:9092")
              .set_topics("loan_issue_events")
              .set_group_id("flink-daily-metrics")
              .set_starting_offsets(KafkaOffsetsInitializer.earliest())
              .set_value_only_deserializer(SimpleStringSchema())
              .build())

    ds = env.from_source(
        source,
        # ⭐ 核心：Event Time + Watermark（允许 5 秒乱序）
        WatermarkStrategy
        .for_bounded_out_of_orderness(Duration.of_seconds(5))
        .with_timestamp_assigner(lambda e, _: parse_ts(e)),
        "kafka-loan-events")

    # 解析 -> (放款日, 1 笔, 金额) -> 按日 keyBy -> 滚动 1 天窗口
    parsed = (ds.map(lambda s: json.loads(s))
                .map(lambda e: (e["event_time"][:10], 1, e["funded_amnt"])))

    result = (parsed
              .key_by(lambda x: x[0])
              .window(TumblingEventTimeWindows.of(Duration.of_days(1)))
              .reduce(lambda a, b: (a[0], a[1] + b[1], a[2] + b[2])))

    result.print()
    env.execute("loan_daily_metrics")


if __name__ == "__main__":
    main()
```

#### 17.1.4 ⭐ 批流对账（本主线最有价值的产出）

**`09_realtime/batch_stream_reconcile.py`**：

```python
"""批流一致性对账：同一天的放款指标，离线链路 vs 实时链路逐日比对。

⭐ 为什么这一步最有价值：
   大多数候选人做离线就只做离线、做实时就只做实时，
   很少有人验证两条链路算出的数字是否一致 —— 而这正是生产环境最容易出事故的地方。
"""
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(ROOT))

import pandas as pd
from src.utils import get_logger, read_sql

log = get_logger("reconcile")

TOLERANCE_CNT = 0            # 笔数必须完全一致
TOLERANCE_AMNT_PCT = 0.0001  # 金额差异率容忍 0.01%


def main():
    log.info("=" * 70)
    log.info("批流一致性对账")
    log.info("=" * 70)

    batch = read_sql("""
        SELECT issue_date AS biz_date,
               COUNT(*) AS batch_cnt,
               ROUND(SUM(funded_amnt), 2) AS batch_amnt
        FROM dwd_loan_fact
        WHERE issue_date >= '2018-01-01'
        GROUP BY issue_date ORDER BY biz_date
    """)

    try:
        stream = read_sql("""
            SELECT biz_date, SUM(loan_cnt) AS stream_cnt,
                   ROUND(SUM(funded_amnt), 2) AS stream_amnt
            FROM ads_loan_daily_realtime
            GROUP BY biz_date ORDER BY biz_date
        """)
    except Exception as e:
        log.error(f"读取实时结果表失败：{e}")
        log.error("请先跑通实时链路；若已放弃实时链路，本脚本可跳过")
        return

    m = batch.merge(stream, on="biz_date", how="outer", indicator=True)
    m["cnt_diff"] = (m["batch_cnt"] - m["stream_cnt"]).abs()
    m["amnt_diff_pct"] = ((m["batch_amnt"] - m["stream_amnt"]).abs()
                          / m["batch_amnt"].replace(0, pd.NA))

    only_stream = m[m["_merge"] == "right_only"]
    mismatch_cnt = m[m["cnt_diff"] > TOLERANCE_CNT]
    mismatch_amnt = m[m["amnt_diff_pct"] > TOLERANCE_AMNT_PCT]

    log.info(f"对账日期数: {len(m)}")
    log.info(f"仅在实时侧: {len(only_stream)}")
    log.info(f"笔数不一致: {len(mismatch_cnt)} | 金额超容忍: {len(mismatch_amnt)}")

    if len(mismatch_cnt) or len(only_stream):
        log.error("❌ 存在差异，按下面清单排查：")
        log.error("   ① ⭐ 时区/日界：UTC vs 北京时间 —— 最常见，占差异的 80%")
        log.error("   ② 迟到数据：Watermark 设置过小，晚到事件被丢弃")
        log.error("   ③ 重复消费：offset 语义不是 Exactly-Once，需下游幂等")
        log.error("   ④ 精度：DECIMAL vs DOUBLE 累加误差")
        log.error(f"\n差异明细:\n{mismatch_cnt.head(10).to_string()}")

    out = ROOT / "09_realtime" / "批流对账明细.csv"
    out.parent.mkdir(parents=True, exist_ok=True)
    m.to_csv(out, index=False, encoding="utf-8-sig")
    log.info(f"明细已写入 {out}")


if __name__ == "__main__":
    main()
```

#### 17.2.1 先把口径抽成纯函数（为单测做准备）

**`src/metrics.py`**：

```python
"""指标口径的纯函数实现 —— 阶段二的口径字典在代码层的唯一来源。

⭐ 为什么单独抽出来：只有无副作用的纯函数才能被单元测试覆盖。
   这是一次有价值的重构，也是"我为了让口径可测试而重构"的面试素材。
"""
from src import config


def is_bad_status(status: str | None) -> bool:
    """是否不良。不良 = Charged Off + Default（含政策外核销）。"""
    if status is None:
        return False
    return status.strip() in config.BAD_STATUSES


def is_terminal_status(status: str | None) -> bool:
    """是否为终态（已结清或已核销）。

    ⭐ 算不良率必须限定终态，否则 Current 会稀释分母
       —— 这是阶段二实测过的坑：19.98% 会被算成 11.9%。
    """
    if status is None:
        return False
    return status.strip() in config.TERMINAL_STATUSES


def dpd_bucket_of(status: str | None) -> str:
    """loan_status -> DPD 档位。未知状态返回 UNKNOWN，不抛异常。"""
    if status is None:
        return "UNKNOWN"
    return config.DPD_MAP.get(status.strip(), "UNKNOWN")


def weighted_avg_rate(pairs) -> float | None:
    """加权平均利率。pairs = [(金额, 利率), ...]

    ⭐ 必须按金额加权 —— 简单平均会让小额与大额贷款同权。
    """
    total_amt = sum(a for a, _ in pairs if a is not None)
    if not total_amt:
        return None
    return sum(a * r for a, r in pairs if a is not None and r is not None) / total_amt
```

        assert is_terminal_status("Late (31-120 days)") is False

    def test_grace_period_非终态(self):
        assert is_terminal_status("In Grace Period") is False

    def test_fully_paid_是终态(self):
        assert is_terminal_status("Fully Paid") is True

    def test_不良率分母必须排除非终态(self):
        """⭐ 回归测试：当初算错成 11.9% 就是因为漏了这条"""
        statuses = ["Fully Paid", "Charged Off", "Current", "Current"]
        terminal = [s for s in statuses if is_terminal_status(s)]
        bad = [s for s in statuses
               if is_terminal_status(s) and is_bad_status(s)]
        rate = len(bad) / len(terminal)
        assert rate == pytest.approx(0.5)      # 1/2
        assert rate != pytest.approx(0.25)     # 明确排除错误口径


class Test加权平均利率:
    def test_按金额加权而非简单平均(self):
        # 1000元@10% + 100元@20%
        # 简单平均 = 15%；按金额加权 = (1000*10 + 100*20)/1100 ≈ 10.909%
        got = weighted_avg_rate([(1000, 10.0), (100, 20.0)])
        assert got == pytest.approx(10.909, abs=0.001)
        assert got != pytest.approx(15.0)      # 明确排除简单平均

    def test_分母为零返回None而不是崩(self):
        assert weighted_avg_rate([]) is None
        assert weighted_avg_rate([(0, 10.0)]) is None

    def test_含None不抛异常(self):
        assert weighted_avg_rate([(1000, None)]) is None

## 1. 三类 SLA 指标

| SLA 类型 | 定义 | 阈值 | 违反后果 |
|---|---|---|---|
| **新鲜度** | 表在每天 08:00 前产出 | ≤ 08:00 | 下游报表无法按时出数 |

### 2.1 新鲜度检查
```sql

SELECT 1 FROM etl_watermark
WHERE job_name = 'dws_snapshot'
  AND DATE(last_run_time) = CURDATE()
  AND TIME(last_run_time) <= '08:00:00';

### 2.2 数据量波动检查
```sql
SELECT CURDATE() AS check_date,
       t.cnt AS today_cnt,
       ROUND(a.avg_cnt, 0) AS avg7_cnt,
       ROUND(t.cnt / a.avg_cnt, 3) AS ratio,
       CASE WHEN t.cnt / a.avg_cnt NOT BETWEEN 0.8 AND 1.2
            THEN 'ALERT' ELSE 'OK' END AS status
FROM (SELECT COUNT(*) cnt FROM ods_loan_raw) t
CROSS JOIN (SELECT COUNT(*) * 1.0 avg_cnt FROM ods_loan_raw) a;
```

### 2.3 指标越界检查
```sql
-- 不良率环比波动 > 30% 告警（口径被改错的强信号）
SELECT cur.issue_month,
       cur.bad_rate AS cur_rate,
       prev.bad_rate AS prev_rate,
       ROUND((cur.bad_rate - prev.bad_rate) / prev.bad_rate, 3) AS chg,
       CASE WHEN ABS((cur.bad_rate - prev.bad_rate) / prev.bad_rate) > 0.3
            THEN 'ALERT' ELSE 'OK' END AS status
FROM ads_delinq_monthly cur
JOIN ads_delinq_monthly prev
  ON prev.issue_month = DATE_FORMAT(
       DATE_SUB(CONCAT(cur.issue_month, '-01'), INTERVAL 1 MONTH), '%Y-%m')
WHERE cur.mob = 6;
```

## 附录 B：阶段三排错手册（18 条）

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| **B-1** | `docker info` 报 `npipe:////./pipe/dockerDesktopLinuxEngine ... cannot find the file specified` | **Docker Desktop 没启动** | 启动 Docker Desktop，等托盘图标变绿再执行命令 |
| **B-2** | Spark 容器反复重启（OOMKilled） | 内存不足 | 降 `SPARK_WORKER_MEMORY` 到 2G；Docker Desktop → Settings → Resources 提高内存上限；或走 B-9 降级 |
| **B-3** | `spark-submit` 报 `No such file or directory: /workspace/...` | 在容器内用了 Windows 路径，或目录没挂载 | 容器内一律用 `/workspace/...`；确认 compose 里 `./:/workspace` 已挂载 |
| **B-4** | `Table or view not found`，或表建完重启就没了 | Metastore 没起来，或用了 Spark 内嵌 Derby（单会话） | 检查 `bd-metastore` 容器状态与 9083 端口；确认 `spark.hadoop.hive.metastore.uris=thrift://metastore:9083` |
| **B-5** | Metastore 说 `Table not found` 但文件明明存在 | **Spark 与 Metastore 挂了不同的 warehouse volume** | 两者必须挂**同一个 volume**（本指导书用 `spark_warehouse`） |
| **B-6** | `INSERT OVERWRITE ... PARTITION` 报动态分区错误 | 没开动态分区 | 加 `SET hive.exec.dynamic.partition=true; SET hive.exec.dynamic.partition.mode=nonstrict;` |
| **B-7** | Spark UI 的 4040 打不开 | 应用结束后 UI 就关闭了 | 启动时加 `--conf spark.ui.keepAlive=true`；或用事件日志（见 B-12） |
| **B-8** | 一致性校验报数值不一致但差异极小 | DECIMAL 精度定义不同（如 `DECIMAL(8,4)` vs `DECIMAL(10,6)`） | 统一精度；比对时用 `ABS(a-b) < 1e-6` 容差 |
| **B-9** | ⭐ **环境搭了 10 小时还不通** | Hadoop/Spark 单机 Docker 环境出了名的难搞 | **立即降级**：① 跳过 Metastore，用 Spark 内嵌 Derby；② 还不行就**只装 Spark 单容器**（`bitnami/spark:3.5`，`local[*]` 模式 + 本地目录存表）。**分区表 / ORC / 倾斜实验全部照做**，只是存储从 Metastore 换成本地目录。**实验本身不受影响** |
| **B-10** | 倾斜实验看不到倾斜现象 | **Spark 3.x 的 AQE 默认开启，自动处理了** | 实验时必须显式关闭：`SET spark.sql.adaptive.enabled=false; SET spark.sql.adaptive.skewJoin.enabled=false;` |
| **B-11** | 加盐后结果与 baseline 不一致 | ① 加权平均在两阶段里先算了 AVG；② NULL 在 JOIN 里没处理 | ① 局部聚合保留 `SUM(rate*amnt)` 与 `SUM(amnt)`，最后相除；② 连接用 `COALESCE(a.purpose,'__NULL__') = COALESCE(b.purpose,'__NULL__')` |
| **B-12** | 想事后分析 task 耗时分布但 UI 关了 | 没保留历史 | 提交时加 `--conf spark.eventLog.enabled=true --conf spark.eventLog.dir=/tmp/spark-events`，再用 history server 查看 |
| **B-13** | Kafka 消费不到消息 | listener 配置错 / topic 名不对 | 容器内连 `kafka:9092`，宿主与本地脚本连 `localhost:29092`；用 `kafka-topics.sh --list` 确认 topic |
| **B-14** | Debezium 连接器状态 FAILED | ① binlog 没开或不是 ROW；② `database.server.id` 冲突 | 确认 MySQL 启动参数含 `--log-bin --binlog-format=ROW --server-id=1`；查 `http://localhost:8083/connectors/<name>/status` 的 trace |
| **B-15** | Flink 作业提交失败 / 类找不到 | pyflink 版本与集群不匹配 | 版本必须严格对齐；**再卡 8 小时就降级**：用 Python + kafka-python 实现同样的窗口聚合，把 Flink 原理讲清楚即可 |
| **B-16** | ⭐ 批流对账差异巨大（整天的数都对不上） | **时区/日界问题** —— 占这类差异的 80% | Kafka 事件时间用 UTC、离线用北京时间；**统一为 `+08:00`** 后差异消失 |
| **B-17** | 批流对账差异小但持续存在 | 迟到数据被 Watermark 丢弃 | 调大 `for_bounded_out_of_orderness(Duration.of_seconds(N))`，或做 T+1 重算对账 |
| **B-18** | `docker compose` 报内存不足 | 同时起了阶段二和阶段三所有容器 | 做阶段三实验时**停掉阶段二容器**：`docker compose -f docker-compose.yml stop` |

      CLUSTER_NAME: credit

    container_name: bd-datanode

      SERVICE_PRECONDITION: "namenode:9870"
      CORE_CONF_fs_defaultFS: hdfs://namenode:9000

  # ---------- HiveServer2 ----------
  hive-server:
    image: apache/hive:4.0.0
    container_name: bd-hiveserver2
    environment:
      SERVICE_NAME: hiveserver2

      IS_RESUME: "true"
      SERVICE_OPTS: >-
        -Djavax.jdo.option.ConnectionURL=jdbc:mysql://metastore-db:3306/metastore?createDatabaseIfNotExist=true&useSSL=false&allowPublicKeyRetrieval=true
        -Djavax.jdo.option.ConnectionUserName=root

    ports: ["10000:10000", "10002:10002"]
    volumes: [spark_warehouse:/opt/hive/data/warehouse]
