## 第一部分 · 数仓架构词

### ⭐ 数仓 / 数据仓库（Data Warehouse）

**一句话**：把公司各个系统的数据汇总、清洗、整理后，专门用来做分析的数据库。

**类比**：厨房。原始食材（业务数据）先入库分拣、洗净、切配，最后才能上灶做菜（出报表）。

**和普通数据库的区别**：业务库（如 MySQL 里跑的系统）是为了**快速处理单笔交易**（下一单、改一条）；数仓是为了**一次算一大批、做汇总分析**。混在一起会把线上系统拖死。

---

### ⭐ ODS / DWD / DWS / ADS（四层架构）

**一句话**：数据从原始到能用的四个"加工车间"。

**类比 —— 用做菜理解**：

| 层 | 全称 | 类比 | 本项目对应表 |
|---|---|---|---|
| **ODS** | Operational Data Store<br>操作数据层 | **菜市场买回来的原样食材**，不洗不切 | `ods_loan_raw` |
| **DWD** | Data Warehouse Detail<br>明细数据层 | **洗净切配好的净菜**，一行一个事实 | `dwd_loan_fact`<br>`dwd_loan_perf_fact` |
| **DWS** | Data Warehouse Summary<br>汇总数据层 | **按主题装好的半成品** | `dws_loan_snapshot_m` |
| **ADS** | Application Data Store<br>应用数据层 | **直接能上桌的菜** | `ads_vintage` 等 4 张 |

**为什么要分层**：**解耦**。业务逻辑变了只改 DWD，口径变了只改 ADS，**ODS 永远不动**。这样每层都能被独立验证，出问题能快速定位在哪一层。

---

### ⭐ 事实表 / 维度表

**一句话**：事实表存"发生了什么"（数字），维度表存"谁、什么时候、在哪"（描述）。

**类比**：记账。

- **事实表** = 流水账的每一行：「2026-01-05，客户A，买了 300 元」
- **维度表** = 客户名单、商品目录、日历

**本项目**：

- 事实表：`dwd_loan_fact`（一行 = 一笔贷款）
- 维度表：`dim_applicant`（申请人画像）、`dim_product`（产品）、`dim_date`（日历）

**为什么要分开**：维度信息（比如客户的年收入）只存一份，事实表里存一个 ID 指过去。否则 226 万行里重复存 226 万次年收入，浪费空间且容易不一致。

---

### ⚠️ 星型模型 / 雪花模型

**一句话**：维度表要不要再往下拆。**不拆 = 星型；继续拆 = 雪花**。

**类比**：

- **星型**：客户表里直接写「城市 = 北京」，一步到位
- **雪花**：客户表写「城市ID = 1」，另建一张城市表写「1 = 北京」，多跳一次

**为什么本项目选星型**：分析场景**查询快、结构好懂**。雪花省一点空间，但每次查询要多 JOIN 几层，得不偿失。

---

### ⭐ 粒度（Granularity）

**一句话**：一行数据代表什么。**建表前必须先定粒度**。

**类比**：说"我卖了 100 件"和"我卖了 100 单"，含义完全不同。

**本项目**：

| 表 | 粒度 |
|---|---|
| `dwd_loan_fact` | 一行 = **一笔贷款** |
| `dws_loan_snapshot_m` | 一行 = **一笔贷款 × 一个观测月末** |
| `ads_vintage` | 一行 = **一个放款批次 × 一个账龄** |

**粒度定错会怎样**：某个指标算出来"翻倍了"——其实是 JOIN 之后行数膨胀，不是业务真的翻倍。

---

### ⭐ 快照事实表（周期快照）

**一句话**：每隔固定时间（如每月末）给所有业务对象拍一张"状态照"。

**类比**：**每月底给公司所有资产拍一张库存照片**。想知道"3 月末公司有多少钱没收回"，翻那张照片即可。

**本项目**：`dws_loan_snapshot_m`
每笔贷款在每个观测月末都有一行，记录当时的：
- 账龄 `mob`
- 逾期档位 `dpd_bucket`
- 未偿本金 `out_prncp`

**为什么需要它**：借款状态是**连续变化**的。只看"最终状态"（已结清/已核销），无法回答"它在第 6 个月时表现如何"。快照表专门解决这个问题。

---

### ⚠️ 拉链表（SCD2）/ 缓慢变化维

**一句话**：记录"属性随时间怎么变"的表。SCD = Slowly Changing Dimension。

**类比**：员工调岗记录。普通表只记"现在在哪个部门"；拉链表记「2023 年在 A 部门，2025 年调到 B 部门」。

**拉链表的典型字段**：

| 字段 | 含义 |
|---|---|
| `start_date` | 这条记录从哪天生效 |
| `end_date` | 到哪天失效（当前有效的填 `9999-12-31`） |
| `is_current` | 是不是最新那条 |

**⚠️ 本项目为什么不用它**：

本数据集是**放款时点的静态快照**——`annual_inc`（年收入）、`grade`（评级）都只有"申请那一刻"的值，
**没有历史切片**。也就是说：**根本拿不到"这个客户 3 年前收入多少"的数据**。

硬做拉链表只能**造几条假数据**演示。一旦面试官问"你的 SCD2 数据从哪来的"，就崩了。

所以我们改用**月末快照表** —— 同样是标准数仓模式，但**数据是真实的、可校验的**。

> 🔑 **面试话术**："我原本打算做客户属性拉链表，但发现这份数据是放款时点的静态快照，
> 不存在真实的属性变更序列，硬做出来是假的。我改成了月末快照事实表。"

## 第二部分 · 数据处理词

### ⭐ ETL / ELT

**一句话**：E（抽取）→ T（转换）→ L（加载）。数据从源头搬到数仓的过程。

**类比**：

- **ETL**：先把菜洗好切好（转换），再放进冰箱（加载）
- **ELT**：先把整箱菜放进冰箱（加载），要用时再洗切（转换）—— 靠数仓自己的算力

**本项目偏 ETL**：Python 先清洗（`dwd_clean.py`），再写入 MySQL。

---

### ⭐ 清洗（Data Cleaning）

**一句话**：把脏数据修成能用的。**数仓最耗时的一环**。

**本项目实际清洗了什么**：

| 脏在哪 | 怎么洗 |
|---|---|
| 文件里混了 **33 行页脚** | 全文件扫描剔除 |
| `term` 是 `'36 months'` 文本 | 提取成数字 `36` |
| `issue_d` 是 `'Dec-2018'` 文本 | 解析成日期 `2018-12-01` |
| `emp_length` 是 `'10+ years'` | 转成 `10`；`n/a` 转成空值 |
| 14 列**整列为空** | 整列剔除 |
| 主键被当成数字 | 强制存成字符串 |

---

### ⭐ 数据质量校验（DQ / Data Quality）

**一句话**：用**自动化规则**检查数据对不对，而不是靠人眼看。

**类比**：工厂流水线上的**质检关卡**。产品不合格就报警停机，而不是等客户投诉。

**本项目 8 项规则**：

| 规则 | 检查什么 | 白话解释 |
|---|---|---|
| 行数守恒 | ODS = DWD | 进来的和出去的一样多，没丢也没多 |
| 主键唯一 | 无重复 | 一笔贷款不能出现两次 |
| **汇总一致性** | ADS = DWD 重算 | 报表的数 = 明细加起来，必须对得上 |
| 金额非负 | `loan_amnt > 0` | 不能有负的贷款 |
| 枚举合法 | 状态值在已知集合内 | 不能冒出没见过的状态 |
| 时间合理 | 放款日期 ≤ 今天 | 不能有未来的贷款 |
| 分区完整性 | 月份无空洞 | 不能缺了某个月 |
| **无未来信息** | 申请表无表现期字段 | ⭐ 防止数据泄漏（见下方） |

> 🔑 **为什么强调"代码化"**：把规则写成**能跑的脚本**（`src/dq_check.py`），
> 而不是写在文档里。这样每次跑数据都会自动检查，不靠人记。

---

### ⭐ 幂等（Idempotent）

**一句话**：**同样的操作跑一次和跑十次，结果完全一样**。

**类比**：电梯的"1 楼"按钮。按一次到 1 楼，按十次还是到 1 楼 —— 不会变成"到 10 楼"。

**为什么重要**：任务失败了要重跑。如果重跑一次就多一份数据，报表数字就会虚高。

**本项目怎么做的**：

- 重跑前先 `TRUNCATE`（清空）再插入
- 跑两次的结果：行数一样、金额合计一样

**反面例子**：`INSERT` 而不清理 —— 重跑一次，数据变两倍。

---

### ⭐ 增量 vs 全量

**一句话**：**全量** = 每次从头算一遍；**增量** = 只算新来的那部分。

**类比**：

- **全量**：每天把整本书重抄一遍
- **增量**：只抄今天新写的那几页

| | 全量 | 增量 |
|---|---|---|
| 优点 | 简单、不易错 | 快 |
| 缺点 | 慢、浪费资源 | 复杂，要记录"算到哪了" |

**本项目怎么记录进度**：`etl_watermark` 表（**水位表**）

**水位**：记住"上次处理到哪了"。类比：**书签**。下次从书签往后读，而不是从第一页开始。

---

### 调度 / DAG

**一句话**：让任务**按依赖顺序自动跑**。

**类比**：**多米诺骨牌**。必须先推倒第一张，第二张才会倒。

**DAG**（有向无环图）：任务依赖关系图。

**本项目**：`run_pipeline.ps1` 串起 8 步，**顺序不能乱**：

```
预处理 → ODS → DWD → 维表 → 快照 → ADS → 质量校验
```

**为什么不能乱**：ADS 依赖快照，快照依赖 DWD，DWD 依赖 ODS。跳步就会算错。

**工业界工具**：DolphinScheduler、Airflow（本项目目前用脚本，可升级）。

---

### ⭐ 数据血缘（Data Lineage）

**一句话**：一张表的数据**从哪来、到哪去**的溯源图。

**类比**：**食品溯源**。出了质量问题，能顺着链条查到是哪批原料。

**有什么用**：报表数字不对时，能快速定位是哪一层的哪张表出了问题。

**本项目**：用手写 YAML + Mermaid 图记录（轻量方案）。

---

### ⭐ 口径（Metric Definition）

**一句话**：**同一个指标名，到底怎么算**。口径不清 = 同一指标两个数。

**类比**：说"我们公司有 100 人"。

- 算不算实习生？
- 算不算外包？
- 算离职但在走流程的？

**不定清楚，每个人报出的数都不一样。**

**本项目的经典口径问题**：

> **"不良率"怎么算？**

| 口径 | 算法 | 结果 |
|---|---|---|
| ❌ 错误 | 不良笔数 / **全部**笔数 | 11.92% |
| ✅ 正确 | 不良笔数 / **终态**笔数 | **19.98%** |

差 8 个百分点。原因见下方"终态"词条。

**口径字典**：把每个指标的定义写成文档（`03_metrics/指标口径字典.md`），**全公司照这个算**。

## 第三部分 · 关键概念辨析（最容易错的地方）

### ⭐⚠️ 申请时点信息 vs 表现期信息

**这是全项目最重要的概念。**

| | 申请时点信息 | 表现期信息 |
|---|---|---|
| **含义** | 申请那一刻就知道的 | **放款之后才知道**的 |
| **类比** | 体检报告（进门时拍的） | 一年后的复查结果 |
| **例子** | 借款金额、评级、年收入、用途 | 是否逾期、已还多少、剩余本金 |
| **本项目字段** | `loan_amnt`、`grade`、`annual_inc`、`purpose`、`dti` | `loan_status`、`out_prncp`、`total_rec_prncp` |
| **存在哪张表** | `dwd_loan_fact` | `dwd_loan_perf_fact` |

**⚠️ 混用会怎样**：

假设你要分析"**什么样的人容易逾期**"。如果用了 `out_prncp`（剩余未还本金）这个字段——

- 已经核销的人，剩余本金可能是 0
- 按时还完的人，剩余本金也是 0

于是模型会得出"剩余本金低的人风险低"——**完全是废话，而且方向是错的**。

**这种情况叫**：

### ⭐ 数据泄漏（Data Leakage）

**一句话**：**不小心把"答案"当成了"线索"**。

**类比**：考试前老师不小心把标准答案发给了你。你考了满分，但**并不代表你学会了**。

**在信贷里的具体表现**：用"放款后才知道的信息"去预测"放款时该不该批"。

**为什么危害大**：指标会**好得反常**，但上线后完全没用。

**本项目怎么防（三道防线）**：

| 防线 | 做法 | 为什么有效 |
|---|---|---|
| **一** | **物理分表** —— 表现期字段只进另一张表 | 从结构上不可能混用 |
| **二** | 代码白名单 —— 只挑申请时点字段 | 主动选择，而非被动排除 |
| **三** | **自动校验** —— 扫表结构，发现表现期字段就报错 | 不靠人记，靠机器查 |

> 🔑 **面试话术**："我不是靠自觉避免数据泄漏，是靠**表结构约束和自动化校验**。"

---

### ⭐⚠️ DPD / 逾期 / 不良 / 核销

这四个词经常被混用，必须分清。

| 词 | 含义 | 通俗解释 |
|---|---|---|
| **逾期（Delinquent）** | 该还没还 | 迟到了 |
| **DPD** | Days Past Due，逾期天数 | 迟到多少天 |
| **不良（Bad）** | 已经确认收不回来 | 判定为坏账 |
| **核销 / 坏账（Charge-off）** | 银行认亏，从账上划掉 | 这笔钱当丢了 |

**递进关系**：

```
正常还款 → 逾期几天 → 逾期很久 → 判定不良 → 核销
   ↑                                    ↑
  Current                        Charged Off
```

**本项目对应**：

| 状态 | 含义 |
|---|---|
| `Fully Paid` | 全部还清 |
| `Current` | **正在正常还款**（既没逾期，也没结束） |
| `Late (16-30 days)` | 逾期 16-30 天 |
| `Late (31-120 days)` | 逾期 31-120 天 |
| `Charged Off` | **已核销**（坏账） |

**DPD 分档（DPD Bucket）**：把逾期天数分成几档，方便统计。

```
CURRENT → DPD_1_30 → DPD_31_120 → DPD_120_PLUS → CHARGED_OFF
```

类比：**迟到分档** —— 准时 / 迟到 10 分钟 / 迟到半小时 / 迟到两小时 / 不来了。

---

### ⭐⚠️ 终态 vs 非终态（为什么不良率必须限定终态）

**终态**：这笔贷款**已经有最终结果了**——要么还清了，要么核销了。

**非终态**：还在还款中，**结果未定**。

| 状态 | 是否终态 | 为什么 |
|---|---|---|
| Fully Paid | ✅ 终态 | 已还清，有结果了 |
| Charged Off | ✅ 终态 | 已核销，有结果了 |
| **Current** | ❌ **非终态** | **还在还，不知道最后会怎样** |
| Late (31-120 days) | ❌ 非终态 | 逾期中，还没定论 |

**⚠️ 为什么算不良率不能把 Current 放进分母**：

**类比**：一个班 100 人考试，已经交卷的 50 人里 10 人不及格。

- ✅ **正确**：不及格率 = 10 / 50 = **20%**
- ❌ **错误**：不及格率 = 10 / 100 = **10%** ← 把还没交卷的也算成及格了！

`Current` 就是**还没交卷的人**。他们**仍在正常还款**，
把他们放进分母，等于把"还没到期的贷款"当成"没出问题的贷款"，**系统性低估风险**。

**本项目实测差异**：

```
✅ 限定终态:   269,360 / 1,348,099 = 19.98%
❌ 不限定:     269,360 / 2,260,668 = 11.92%
                              ↑ 低估了 8 个百分点
```

> 🔑 **面试被问"不良率怎么算"，答"不良笔数/总笔数"是不及格的。**
> 必须说清**分母要限定终态**及原因。

---

### ⭐⚠️ Vintage / MOB

**Vintage**：把**同一时期放款**的贷款归成一批，比较它们的表现。

**类比**：**葡萄酒的年份**。2015 年的酒和 2018 年的酒，产地工艺都不同，不能混着评价。

**MOB**：Month on Book，**账龄**——这笔贷款已经放了几个月。

```
MOB = 观测月 − 放款月
```

**为什么要做 Vintage 分析**：

假设想比较"2015 年放款"和"2018 年放款"哪批客户质量差。

- ❌ **直接比总逾期率**：2015 年的肯定高——因为它**已经放了 3 年**，该出问题的都暴露了；
  2018 年的才放半年，很多问题还没显现
- ✅ **对齐账龄比**：都看"第 6 个月时的逾期率" —— 这才公平

**Vintage 矩阵**：行 = 放款批次，列 = 账龄，格子 = 逾期率。

```
放款批次    MOB3    MOB6    MOB12
2015-07    0.0%    0.0%    1.31%
2015-08    0.0%    0.0%    1.73%
2015-09    0.0%    0.0%    2.15%
```

> 🔑 **面试话术**："直接比较不同月份的逾期率会**误导**，
> 因为老批次账龄长、暴露更充分。Vintage 分析把账龄对齐，才能公平比较。"

**⚠️ 本项目的坑**：MOB3/MOB6 显示 0% —— **不是算错了**。
因为核销状态是**规则推导**的（推定核销月 = 最后还款月 + 6），
所以早期账龄还没到核销时点。这时候要看 `DPD_120_PLUS`（严重逾期）作为前置信号。

---

### ⭐ 迁徙率（Roll Rate）

**一句话**：这个月处于某档位的贷款，**下个月跑到哪个档位**去了。

**类比**：**学生成绩的分层流动**。这个月及格的，下个月有多少变成不及格了？

**本项目矩阵**：

| 期初 | → 期末 | 比例 |
|---|---|---|
| Current | Current | 96.5% |
| Current | DPD_1_30 | 3.5% |
| DPD_31_120 | DPD_120_PLUS | 52.7% |

**用途**：预测未来不良、评估催收效果。

**⚠️ 本项目的局限**：档位是按"距最后还款月数"**规则推导**的，
所以"只恶化不好转"部分来自规则本身，**不是真实行为**。
正确说法是"方向可信，数值需谨慎"。

---

### ⭐ 滞后（Lag）/ 前置信号

**一句话**：一个指标的变化，**比结果先出现**。

**类比**：**咳嗽是感冒的前兆**。看到咳嗽，就知道可能快感冒了。

**本项目**：`DPD_120_PLUS`（严重逾期）是 `CHARGED_OFF`（核销）的**前置信号**。

因为核销要等程序走完，而严重逾期先出现。所以：

> **MOB < 12 时，只看核销会低估风险。应该把 `DPD_120_PLUS + CHARGED_OFF` 一起看。**

---

## 第四部分 · 技术实现词

### ⭐ Parquet / 列存 vs 行存

**一句话**：**列存**按列存，**行存**按行存。

**类比**：

- **行存**：一本**流水账**，一页记一个人所有信息。想统计"所有人的年龄"，得翻每一页
- **列存**：**按字段分册**，一本全是年龄，一本全是姓名。想统计年龄，只翻那一本

**为什么分析快**：分析常常只取少数几列（如"看不良率"只要 `is_bad` 一列），
列存**只读需要的那几列**，行存必须读整行。

**本项目**：预处理产出的 `loans_full.parquet` 就是列存，338 MB 装下 226 万行 × 137 列。

---

### ⭐ dtype（数据类型）

**一句话**：这一列存的是数字、文本还是日期。

**类比**：Excel 单元格格式。设成"文本"的 `001` 和设成"数字"的 `1` 不是一回事。

**本项目踩的坑**：

| 坑 | 现象 | 为什么危险 |
|---|---|---|
| **分块读取 dtype 漂移** | 同一列在第 1 块是文本、第 2 块变成数字 | 写文件时报 schema 不匹配 |
| **主键存成数字** | `68407277` 变成 `68407277.0` | 比较/拼接出错；长 ID 会**丢精度** |

**结论**：**业务主键一律存成字符串**。

---

### ⚠️ NaN / NA / NULL / 空值

**一句话**：都是"没有值"，但**在不同工具里的行为不同**。

| 写法 | 出现在哪 |
|---|---|
| `NULL` | SQL / 数据库 |
| `NaN` | pandas（浮点型列的缺失） |
| `NA` | pandas（可空整型 Int64 的缺失） |

**⚠️ 最坑的行为差异**（本项目真踩过）：

在 pandas 的 `Int64`（可空整型）里，`NA` 参与比较会得到 `NA`：

```python
s = pd.Series([pd.NA, 5], dtype="Int64")
s >= 1
# 结果：[<NA>, True]   ← NA 那格不是 False，是 NA
```

**为什么危险**：用这个结果去 `mask`（条件替换）时，**`NA` 的位置不会被替换**。

**本项目实例**：有 **148 笔**贷款 `last_pymnt_d` 为空（从未还过款）。
不做处理的话，它们的"距最后还款月数"是 `NA`，
逾期档位推导时**不会覆盖**，于是被静默判成 `CURRENT`（= 正常还款）。

**问题在于**：**从未还过款的贷款，恰恰是最该关注的坏账！**

**解决办法**：比较前先 `fillna(-1)`，把"没值"变成明确的负数。

> 🔑 **教训**：空值不是"0"，也不等于"False"。**空值参与运算的规则要专门验证。**

---

### ⭐ 聚簇索引 / 主键顺序（本项目的性能案例）

**一句话**：数据库里数据的**物理排列顺序**。主键决定它。

**类比**：图书馆书架。

- 书**按编号顺序**摆 → 找书快，**新书上架也快**（放最后就行）
- 书**乱摆** → 找书慢，**新书上架也慢**（得找缝隙塞）

**本项目的性能事故**：

快照表主键原本是 `(loan_id, snapshot_month)`，但数据是**按观测月批量写入**的：

```
先插 2015-08 的全部贷款
再插 2015-09 的全部贷款
...
```

问题：**同一笔贷款的不同月份记录，在索引里离得很远**。
每次插入都要在索引中间"塞"，导致**随机读写 + 页分裂**。

**结果**：吞吐从 40,000 行/秒一路衰减到 **5,000 行/秒**，480 万行要 26 分钟。

**修复**：主键改成 `(snapshot_month, loan_id)`，与插入顺序一致 → 变成**顺序追加**。

| | 修复前 | 修复后 |
|---|---|---|
| 吞吐 | 5,379 行/秒（**持续衰减**） | **38,032 行/秒（恒定）** |
| 480 万行 | 26 分钟 | **4.2 分钟** |

> 🔑 **面试价值高**：这说明你理解"**索引的物理顺序影响写入性能**"，
> 而不只是会写 SQL。

---

### ⚠️ 排序规则（Collation）

**一句话**：数据库**怎么比较字符串**（区分大小写吗？重音符号算不同吗？）。

**类比**：字典的排序规则。`a` 和 `A` 算同一个字母吗？

**本项目踩的坑**：

两张表用了**不同的排序规则**（一张 `utf8mb4_0900_ai_ci`，一张 `utf8mb4_unicode_ci`），
JOIN 时报错：

```
ERROR 1267: Illegal mix of collations (utf8mb4_0900_ai_ci)
            and (utf8mb4_unicode_ci) for operation '='
```

**为什么**：MySQL 8 不会"猜"你想按哪套规则比，**直接拒绝执行**。

**解决**：**全库统一成同一个排序规则**。

---

### ⚠️ 保留字（Reserved Word）

**一句话**：数据库**已经占用了的词**，不能直接当字段名用。

**类比**：给小孩取名不能叫"老师"——会引起歧义。

**本项目实例**：`year_month` 是 MySQL 保留字（`YEAR_MONTH` 是时间间隔单位），
直接用它建表报错：

```
ERROR 1064: You have an error in your SQL syntax ... near 'year_month CHAR(7)'
```

**解决**：**所有列名加反引号** `` `year_month` `` —— 一次性免疫所有保留字问题。

---

### ⭐ skipfooter / 分块读取（chunksize）

**skipfooter**：pandas 读文件时"跳过末尾 N 行"的参数。

**chunksize**：分块读取，一次只处理一部分（避免内存爆掉）。

**类比**：

- `chunksize` = 吃饭一口一口吃（而不是整盘倒进嘴里）
- `skipfooter` = "最后两口别吃"

**⚠️ 本项目的致命问题**：**这两个参数不能同时用**。

```python
pd.read_csv(文件, chunksize=100_000, skipfooter=1)
# ValueError: 'skipfooter' not supported for iteration
```

**后果**：所有分块读取的脚本**一行都跑不起来**。

**更深的问题**：本文件的页脚**有 33 行，而且散布在文件中部**（不是只在末尾）。
就算能用 `skipfooter`，也只能删掉最后一行，另外 32 行照样混进数据。

**最终解决**：**不要每次读取都跳页脚**，而是**先做一次预处理**把它剔干净：

```
原始 gz  →  prepare_raw.py（剔 33 行页脚）  →  干净 Parquet
                                                      ↓
                                          之后所有脚本读这个
```

**顺带的好处**：读取从 **20–40 分钟**降到 **80 秒**。

---

### ⭐ 水位（Watermark）

**一句话**：记录"上次处理到哪了"。

**类比**：**书签**。下次从书签往后读。

**本项目**：`etl_watermark` 表记 `watermark_value`（如最大放款月）+ 上次运行时间 + 处理行数。

**为什么需要**：增量处理的前提是知道"新的从哪开始"。

## 第五部分 · 金融与信贷词

### ⭐ 信贷基础

| 词 | 通俗解释 | 本项目字段 |
|---|---|---|
| **放款 / 授信** | 银行把钱借给你 | `funded_amnt` |
| **本金** | 借的原始金额 | `loan_amnt` |
| **利息 / 利率** | 借钱要付的代价 | `int_rate` |
| **期限** | 借多久 | `term`（36/60 个月） |
| **月供** | 每月还多少 | `installment` |
| **年收入** | 借款人一年挣多少 | `annual_inc` |
| **债务收入比（DTI）** | 每月还债 ÷ 每月收入。**越高越危险** | `dti` |
| **信用评级** | 平台给的信用分档 A–G | `grade` |

**类比一遍**：**贷款就像分期买手机**。手机价 = 本金，分 12 期 = 期限，
每期付的钱 = 月供，多付的部分 = 利息。

---

### ⭐ FICO 分

**一句话**：美国最通用的**个人信用评分**，范围 300–850，**分越高越可靠**。

**类比**：**芝麻信用分**。

| 分档 | 含义 |
|---|---|
| 300–579 | 差 |
| 580–669 | 一般 |
| 670–739 | 良好 |
| 740–799 | 很好 |
| 800–850 | 极好 |

**⚠️ 本项目有两个版本，别混**：

| 字段 | 含义 |
|---|---|
| `fico_range_low` / `fico_range_high` | **申请时**的分数（申请时点信息） |
| `last_fico_range_low` / `last_fico_range_high` | **最后一次拉取时**的分数（表现期信息！） |

带 `last_` 前缀的是**表现期字段**，不能进申请时点表。

---

### ⭐ 通过率 / 批准率（本项目已废弃）

**一句话**：申请的人里，批了多少。

```
批准率 = 批准笔数 / 申请笔数
```

**⚠️ 本项目为什么算不出来**：

我们拿到的文件叫 `accepted_*.csv` —— **只含已批准的贷款**。

也就是说：**分母（申请总数）根本不存在**。

| 数据 | 有没有 |
|---|---|
| 已批准的贷款 | ✅ 226 万笔 |
| 被拒绝的申请 | ❌ 没有（另有文件，但字段极少且无关联键） |

**类比**：想知道"考试通过率"，但只拿到了**及格名单**，没有全部考生名单。

**处理**：**删掉这个指标**，并在文档里记录"已废弃指标"及原因。

> 🔑 **这部分是加分项**：主动说明"我识别出这个指标算不出来，所以删了"，
> 比硬凑一个数字专业得多。

---

### ⭐ 幸存者偏差（Survivorship Bias）

**一句话**：**只看到"活下来的"，就得出错误结论**。

**经典例子**：二战时统计返航飞机的弹孔，发现机翼弹孔最多 →
有人提议加固机翼。但**真正该加固的是发动机**——
因为**发动机中弹的飞机根本飞不回来**，不在统计样本里。

**本项目里的表现**：

我们只有"**已放款**"的客户数据。被**拒绝**的人不在样本里。

**后果**：

- 算出的不良率（19.98%）**只代表"已放款客群"**
- 真实全客群的不良率**会低于**这个数（因为风险高的被拒了）
- **不能外推**到所有申请人

**处理**：所有结论都**限定表述**为"在已放款客群中"。

---

### ⭐ 加权平均（Weighted Average）

**一句话**：不是把每个数简单平均，而是**按重要性（权重）加权**。

**类比**：算绩点。

- **简单平均**：数学 90 分（2 学分）、体育 60 分（1 学分）→ 平均 75 分
- **加权平均**：`(90×2 + 60×1) / 3 = 80 分` ← 学分多的课影响大

**本项目**：**加权平均利率**必须按金额加权。

```sql
-- ✅ 正确
SUM(loan_amnt * int_rate) / SUM(loan_amnt)
-- ❌ 错误
AVG(int_rate)
```

**为什么**：一笔 1,000 元和一笔 40,000 元的贷款，
**简单平均让它们同权**，完全不能反映真实的资金成本。

---

### ⭐ 敞口 / 风险敞口（Exposure）

**一句话**：**可能损失多少钱**。

**类比**：借给朋友的钱里，**还没还的部分**就是敞口。

**本项目**：`out_prncp`（未偿本金）—— 观测月末还没收回的本金。

**为什么要看它**：不良率看"多少笔出问题"，敞口看"**多少钱有风险**"。
一笔 4 万的不良比一笔 1 千的不良严重得多。

---

### ⭐ 期末未偿余额（EAD）

**EAD** = Exposure at Default，**违约时的风险敞口**。

**一句话**：如果现在就出事，银行会损失多少。

**本项目**：`SUM(out_prncp)` 按观测月末汇总。

---

### ⭐ 加权风险分层（Risk Segmentation）

**一句话**：按客户特征分成几组，看各组的风险差异。

**类比**：**按年龄段看体检异常率**——20 岁、40 岁、60 岁各是多少。

**本项目三维分层**（实测单调性完美）：

| 维度 | 结果 |
|---|---|
| **信用评级** | A 5.29% → G 57.94% |
| **FICO 分** | 660-699 23.55% → ≥780 5.49% |
| **年收入** | <3万 23.29% → ≥20万 12.42% |

**为什么看"单调"**：如果 A 比 B 风险还高，说明**分层逻辑或口径错了**。
单调性是最基本的自检。

---
