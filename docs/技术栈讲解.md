## §1 全景：数据从哪来，到哪去

### 1.1 阶段二的链路（单机 MySQL）

```
accepted_2007_to_2018Q4.csv.gz（374 MB，226 万行，151 列）
   │  ① prepare_raw.py     剔除 33 行散布页脚 / 剔 14 个全空列 / 固定 dtype
   ▼
data/clean/loans_full.parquet（338 MB，2,260,668 × 137）  ← pandas + pyarrow
   │
   ├─ ② ods_load.py        → ODS  ods_loan_raw            （原样落地，39 关键列）
   ├─ ③ dwd_clean.py       → DWD  dwd_loan_fact           （申请时点事实表）
   ├─ ④ dwd_derived.py     → DWD  dwd_loan_perf_fact      （表现期事实表）
   ├─ ⑤ dim_build.py       → DIM  dim_applicant/product/date
   ├─ ⑥ dws_snapshot.py    → DWS  dws_loan_snapshot_m     （月末快照，4471 万行）
   ├─ ⑦ ads_metrics.py     → ADS  risk_segment/vintage/roll_rate/delinq_monthly
   └─ ⑧ dq_check.py        → 质量  11 项检查 + dq_check_result 表
                                （任一步失败 → 流水线非 0 退出）
```

### 1.2 阶段三的链路（Spark + Hive Metastore）

```
阶段二的 MySQL（13 张表）
   │  ① export_mysql_tsv.py   流式导出为 TSV（NULL=\N，显式 schema，不经 pandas）
   ▼
07_bigdata/exchange/*.tsv（约 5 GB，一次性）
   │  ② Hive DDL + 装载（Spark 读 TSV → ORC 分区表）
   ▼
credit_dwh_lc 库（Hive/Spark 层）
   ├─ dwd_loan_fact_lc        按 issue_month 分区，ORC
   ├─ dwd_loan_perf_fact_lc
   ├─ dws_loan_snapshot_lc    按 snapshot_month 分区（4471 万行）
   └─ dim_applicant_lc
        │  ③ 复现 4 张 ADS 表 → 与 MySQL 逐行比对（NULL 安全 + 按列容差）
        │  ④ 五个对照实验 E1–E5（分区裁剪/小文件/列存/倾斜/三引擎基准）
        ▼
   08_benchmark/：实验记录 + 引擎选型结论（**阶段三的最终交付**）
```

### 1.3 两条链路怎么衔接（这是"批流一体"的雏形）

| 阶段二的角色 | 阶段三的角色 |
|---|---|
| MySQL 是**唯一**的计算引擎 | MySQL 是**基准组 + 数据源**，Spark 是**实验组** |
| 口径写在一处（`config.py` + 口径字典） | **同一套口径在两种引擎各实现一遍，逐行比对** |
| 优化点是"主键顺序 vs 插入顺序"（InnoDB 聚簇索引） | 优化点是"分区/文件/倾斜"（分布式执行） |

> 🔑 **一句话讲清这个项目的价值**：
> "我不是分别做了两个项目，而是**把同一套口径在两个引擎上落地，
> 用五个对照实验量化差异，最后给出有条件的引擎选型结论**。"

### 2.1 Python 3.11 + venv

**是什么**：项目的开发语言与运行环境。`venv` 是 Python 自带的虚拟环境，把依赖装进项目目录而不是全局。

**项目里怎么用**：
- 所有 ETL 都是可独立运行的模块：`& $PY -m src.dwd_clean`（`-m` 方式能在别处也 import `src.*`）
- 统一入口：`06_ops/shell/run_pipeline.ps1` 按顺序调用 8 个模块
- 公共设施集中在 `src/utils.py`：日志、数据库引擎、读干净数据、写表

**最小例子**：

```powershell
# 建环境（只做一次）
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt pyarrow

# 之后一律用 venv 的解释器（系统 Python 缺 sqlalchemy/pymysql/pyarrow）
.\.venv\Scripts\python.exe -m src.dq_check     # 退出码 0=通过，1=有 ERROR 级失败
```

**典型应用场景**：
- 定时 ETL 脚本（cron / 调度平台里跑的就是这一类）
- 把"取数 → 清洗 → 入库"串成一条可重跑的流水线
- 小工具：导出、校验、生成报告

**面试追问**："为什么不用系统 Python？" → 依赖隔离：这个项目跑在 pandas 2.2 + SQLAlchemy 2.0 上，
换台机器或换个人，`requirements.txt` 一装就一致；全局环境里版本冲突会很难查。

### 2.2 pandas 2.2.2

**是什么**：单机数据处理的事实标准库（表格型数据的读写、清洗、聚合）。

**项目里怎么用**（三处最典型）：

| 用处 | 位置 | 关键点 |
|---|---|---|
| 分块读 226 万行 CSV 并剔除页脚 | `src/prepare_raw.py` | **不用 `skipfooter`**（它与 `chunksize` 互斥），改成按"`id` 必须是纯数字"逐块判定 |
| 清洗与派生（解析 `term`、`int_rate`、`issue_d`） | `src/dwd_clean.py` | 分块解析 + 固定 dtype，避免 `dtype` 漂移 |
| 读回校验与报表 | `src/dq_check.py`、`04_analysis/01_charts.py` | `pd.read_sql` + `to_sql(method="multi")` |

**最小例子**：

```python
import pandas as pd

# ⚠️ 这个项目踩过的最大一个坑就在这里：
#    pandas 的 skipfooter 与 chunksize/nrows 互斥，下面这行会直接抛 ValueError
#    pd.read_csv(p, chunksize=100_000, skipfooter=1, engine="python")

# 正确做法：定义"哪些行不是数据"，逐块过滤
def is_data_row(s: pd.Series) -> pd.Series:
    return s.astype("string").str.fullmatch(r"\d+").fillna(False)

for chunk in pd.read_csv("data/raw/x.csv.gz", chunksize=200_000,
                         dtype={"id": "string"}, engine="c"):
    chunk = chunk[is_data_row(chunk["id"])]   # 页脚行在这里被剔除
    ...
```

**典型应用场景**：
- 单机规模（几十万～几千万行）的清洗、派生、对账
- 读 CSV/Excel/SQL 做临时分析、出图、写报告
- 作为"小数据探索"的快速工具，**结论再拿到 Spark 上验证**

**面试追问**："数据再大 10 倍怎么办？" → 就不是 pandas 的活了：
换 Parquet 列存 + 只读需要的列，或者迁到 Spark（本项目第 13 步做的就是这件事），
pandas 只保留"抽样探查 + 结果比对"的角色。

### 2.3 pyarrow / Parquet（列存）

**是什么**：Parquet 是列式存储格式；pyarrow 是它的 Python 实现（也是 pandas 的 Parquet 引擎）。

**项目里怎么用**：
- 阶段二把清洗结果落成 `data/clean/loans_full.parquet`（338 MB，2,260,668 × 137）——
  **之后所有脚本都读它**，不再回头碰那个有页脚的 gz
- `src/utils.py::read_clean()` 支持**只读部分列**与**按批迭代**（用 `pyarrow.parquet.iter_batches`）
- 列存也是阶段三 E3 实验的对比对象（TextFile vs Parquet vs ORC）

**最小例子**：

```python
import pandas as pd
import pyarrow.parquet as pq

# ① 只读需要的列（列存的核心优势：不读的列根本不碰）
df = pd.read_parquet("data/clean/loans_full.parquet",
                     columns=["id", "loan_amnt", "grade"], engine="pyarrow")

# ② Parquet 原生不支持按行分块，用 pyarrow 的 iter_batches 实现"流式"处理
pf = pq.ParquetFile("data/clean/loans_full.parquet")
for batch in pf.iter_batches(batch_size=200_000, columns=["id", "issue_d"]):
    chunk = batch.to_pandas()
    ...   # 内存占用恒定，不会把 226 万行一次性读进来
```

**典型应用场景**：
- 数仓/数据湖里的**交换格式**（比 CSV 省 3–10 倍空间、带 schema、读取更快）
- 只查少列的大宽表分析（137 列只取 5 列 → 只读 5 列）
- 跨语言共享数据（Python / Spark / Java 都能读）

**面试追问**："Parquet 和 ORC 怎么选？" → 两者都是列存。
Spark 里 ORC 对低基数列（`grade`/`purpose`）的字典/RLE 编码略优；
Parquet 生态更广（Spark、Hive、Presto、pandas 都原生支持）。
**我在 E3 里实测过**：存储体积与"少列查询"耗时都有量化对比。

### 2.4 MySQL 8.0

**是什么**：关系型数据库。本项目里它**就是数仓本体**（不是"顺便存一下"）。

**项目里怎么用**：
- 13 张表：ODS 1 + DWD 2 + DIM 3 + DWS 1 + ADS 4 + 运维 2，DDL 在 `sql/ddl/01_schema.sql`
- 用**索引与主键**承载性能：`dws_loan_snapshot_m` 的主键从 `(loan_id, snapshot_month)`
  改成 `(snapshot_month, loan_id)` 后，写入吞吐 **5,379 → 38,032 行/秒**（480 万行 26 分钟 → 4.2 分钟）
- 用**约束**承载正确性：`PRIMARY KEY` 保证主键唯一、`DECIMAL` 保证金额不丢精度
- 用 `LOAD DATA LOCAL INFILE` 灌 ODS（`--local-infile=1` 是为此开的）

**最小例子**：

```sql
-- ① 主键顺序 = 写入顺序 → 变成聚簇索引的顺序追加（本项目最值钱的一次优化）
CREATE TABLE dws_loan_snapshot_m (
  `loan_id`        VARCHAR(32) NOT NULL,
  `snapshot_month` CHAR(7)     NOT NULL,   -- 数据按月批量写入
  ...
  PRIMARY KEY (`snapshot_month`, `loan_id`)   -- ⭐ 与插入顺序同序
);

-- ② 用 EXPLAIN 确认索引真的被用上（不要猜）
EXPLAIN SELECT SUM(is_bad)/COUNT(*) FROM dwd_loan_perf_fact WHERE is_terminal = 1;
```

**典型应用场景**：
- 百万级～千万级的数据仓库（本项目 226 万行、约 6.8 GB，**单机完全能承载**）
- 需要事务、约束、强一致的小规模分析库
- 作为"**基准组**"：阶段三拿它跟 Spark 对比，得出选型边界

**面试追问**："为什么不用 MySQL 做大数据？" →
**我这个量级本来就不需要分布式**（这是诚实答案）。
真正的分界线在阶段三 E5 里量化出来了：约 `__` 万行以上 Spark 才明显更优，
而且 Spark 每个作业有固定启动开销、资源占用高一个量级。

### 2.5 SQLAlchemy 2.0 + PyMySQL

**是什么**：SQLAlchemy 是 Python 的数据库工具层（统一接口 + 连接池）；
PyMySQL 是纯 Python 的 MySQL 驱动（底层协议实现）。

**项目里怎么用**：全部封装在 `src/utils.py` —— **禁止在业务脚本里手写连接**：

```python
def get_engine(): ...        # 统一从 config.DB 取 host/port/user/password
def read_sql(sql, params):   # 取数 → DataFrame
def run_sql(sql, params):    # 执行（DDL/DML）
def df_to_table(df, table, if_exists, chunksize):   # 写表（method="multi" 批量）
```

**最小例子**：

```python
from src.utils import read_sql, df_to_table

df = read_sql("SELECT grade, COUNT(*) c FROM dwd_loan_fact GROUP BY grade")
df_to_table(df, "ads_tmp", if_exists="replace", chunksize=2000)
# to_sql(method="multi") 会把多行合成一条 INSERT，比逐行插入快一个量级
```

**典型应用场景**：
- ETL 脚本里"取数 → 处理 → 回写"
- 参数化查询（防注入）：`read_sql("... WHERE id = :i", {"i": v})`
- 需要跨数据库时（同一套代码从 MySQL 换到 PostgreSQL，只改连接串）

**面试追问**："为什么不用 ORM？" → 这是个数据项目，SQL 是主体；
ORM 适合"业务增删改查"，而数仓加工更适合**把 SQL 写清楚**（也便于 DBA 审阅与优化）。

### 2.6 SQL：窗口函数、自关联、CASE/NULLIF

**是什么**：数仓开发的核心技能。本项目的**所有指标口径最终都落在 SQL 上**。

**项目里怎么用**（四个典型手法）：

| 手法 | 用在哪 | 解决什么 |
|---|---|---|
| **窗口函数（取"曾发生"标志）** | `ads_vintage`（累计不良率） | 避免同一笔贷款被逐月重复计数 |
| **窗口函数（LAG）** | 口径自检：累计不良率必须随 MOB 单调不减 | 用 SQL 自己做回归校验 |
| **大表自关联** | `ads_roll_rate`（迁徙率：本月档位 → 下月档位） | 状态流转 |
| **`CASE WHEN` / `NULLIF` / `COALESCE`** | 分档、除零保护、NULL 归并 | 让指标在脏数据下也不崩 |

**最小例子**：

```sql
-- ① ⭐ 累计不良率：错误写法 SUM(is_bad_month) 会把同一笔逐月重复计数
MAX(is_bad_month) OVER (
  PARTITION BY issue_month, loan_id ORDER BY mob
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW   -- ⭐ 显式声明帧
) AS ever_bad

-- ② 除零保护
ROUND(SUM(p.is_bad) / NULLIF(COUNT(*), 0), 6) AS bad_rate

-- ③ 自关联做迁徙率：本月 → 下月
SELECT a.dpd_bucket AS from_bucket, b.dpd_bucket AS to_bucket, COUNT(*) AS cnt,
       ROUND(COUNT(*) / SUM(COUNT(*)) OVER (
             PARTITION BY a.snapshot_month, a.dpd_bucket), 6) AS rate
FROM dws_loan_snapshot_m a
JOIN dws_loan_snapshot_m b
  ON b.loan_id = a.loan_id AND b.mob = a.mob + 1
GROUP BY a.snapshot_month, a.dpd_bucket, b.dpd_bucket;
```

**典型应用场景**：
- 风控/运营指标：不良率、Vintage、迁徙率、逾期月报
- 需要"按时间看状态变化"的分析（留存、漏斗、状态机）
- **口径的唯一定义**：一个指标只允许有一份 SQL，其他脚本都复用它

**面试追问**："窗口函数的默认帧是什么？" →
默认是 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（不是 `ROWS`）。
排序键有重复值时两者语义不同（`RANGE` 会把同值行一起纳入帧），
所以我在代码里**显式写 `ROWS`**。

### 2.7 维度建模（星型模型 / 事实表 / 维表 / 周期快照）

**是什么**：数仓的表组织方法论（Kimball 体系）。核心是把"度量"与"描述"分开。

**项目里怎么用**：

| 概念 | 本项目落点 | 关键决策 |
|---|---|---|
| **事实表** | `dwd_loan_fact`（申请时点）、`dwd_loan_perf_fact`（表现期） | ⭐ **物理分表**，用字段黑名单自动校验阻断数据泄漏 |
| **维表** | `dim_applicant`、`dim_product`、`dim_date` | 客户维**降级**为"申请人画像维"（`member_id` 整列为空，不拼伪客户 ID） |
| **周期快照事实表** | `dws_loan_snapshot_m`（月末快照，4471 万行） | 替代 SCD2 拉链表（本数据没有真实属性变更序列，硬做只能造假） |
| **分层** | ODS → DWD → DIM/DWS → ADS | 每层只解决一类问题，出错能快速定位 |

**最小例子**（快照表的"粒度"怎么定）：

```sql
-- 粒度 = 一笔贷款 × 一个观测月末
-- 主键 = (snapshot_month, loan_id)：与"按月批量写入"的顺序同序 → 写入变成顺序追加
PRIMARY KEY (`snapshot_month`, `loan_id`)
-- 核心字段：mob（账龄）、dpd_bucket（该月末档位）、is_delinquent、is_bad_month、out_prncp
```

**典型应用场景**：
- 报表与 BI 的数据底座（星型模型对 BI 工具最友好）
- 需要"按时间切片看状态"的场景（月末余额、月末逾期分布、Vintage）
- 需要**口径可追溯**的场景（改一个 ADS 指标不影响 DWD）

**面试追问**："为什么不做 SCD2？" →
SCD2 的前提是"同一实体的属性会随时间变化且有变更记录"。
本数据是**放款时点的静态快照**，没有真实的属性变更序列 ——
硬做 SCD2 只能**造假数据**，反而不如月末快照真实可校验。

### 2.9 PowerShell

**是什么**：Windows 上的自动化脚本语言。本项目用它做**一键流水线**。

**项目里怎么用**：`06_ops/shell/run_pipeline.ps1` 顺序调用 8 个 Python 模块，
任一步非 0 退出就中止；并把每一步的耗时打出来。

**最小例子**：

```powershell
# 只保留骨架，看编排思路
$PY = Join-Path $ROOT '.venv\Scripts\python.exe'
$steps = @(
  @{ Name = '01 prepare_raw'; Mod = 'src.prepare_raw'; Optional = $false },
  @{ Name = '02 ods_load';    Mod = 'src.ods_load';    Optional = $false },
  @{ Name = '06 dws_snapshot';Mod = 'src.dws_snapshot';Optional = $true  }
)
foreach ($s in $steps) {
  & $PY -m $s.Mod
  if ($LASTEXITCODE -ne 0) {
    if ($s.Optional) { Write-Host "[WARN] $($s.Name) failed - continuing" }
    else { Write-Host "[FAIL] $($s.Name) - aborting"; break }
  }
}
```

**两个踩过的坑（值得单独记）**：

1. **`.ps1` 只写 ASCII**：Windows PowerShell 5.1 会把无 BOM 的 UTF-8 脚本按 GBK 读，
   中文可能把引号"吃掉"，报 `ParserError: The string is missing the terminator`。
   **中文提示由 Python 侧输出**，PowerShell 只负责编排。
2. **`$ErrorActionPreference='Stop'` 与原生命令的 stderr**：
   `mysqladmin ping -p<pw>` 会在 stderr 打一条密码警告，
   在 `Stop` 模式下可能被提升为终止错误，于是**健康的 MySQL 被判成"没在跑"**。
   修法是探测函数内临时把 `ErrorActionPreference` 调回 `Continue`。

**典型应用场景**：
- Windows 上编排多步任务（本项目）
- 日常运维：起容器、跑校验、打包日志
- **生产上这类编排会换成调度平台**（DolphinScheduler / Airflow）——
  本项目的脚本只是它的"最小可用替代"

**面试追问**："你们用什么调度？" →
诚实答："学习项目里我用 PowerShell 脚本编排 8 步、带失败中止；
生产上我会用 Airflow/DolphinScheduler 配 DAG ——
**但我很清楚脚本编排缺什么**：依赖管理、重试策略、补数、可视化的失败定位。"

### 2.12 数据质量校验框架（自研，`src/dq_check.py`）

**项目里怎么用**：8 条规则展开为 11 项检查，每次跑批自动执行，
**任一 ERROR 级失败就让流水线返回非 0**；结果写进 `dq_check_result` 表（带 `batch_id` 可追溯）。

| 规则 | 级别 | 本项目实测 |
|---|---|---|
| Q1 行数守恒 | ERROR | ODS = DWD = 2,260,668（差 0） |
| Q2 主键唯一（4 张表） | ERROR | 重复 0 |
| Q3 **汇总一致性**（ADS = DWD 重算） | ERROR | (1,348,099, 269,360) 完全一致 |
| Q4 金额非负 | ERROR | 违规 0 |
| Q5 枚举合法 | ERROR | 9 种状态全部登记 |
| Q6 时间合理 | WARN | 违规 0 |
| Q7 分区完整性（月份无空洞） | WARN | 缺失 0 |
| Q8 **无未来信息**（防数据泄漏） | ERROR | 泄漏字段 0 |

**最小例子**（Q3 汇总一致性 —— 最核心的一条）：

```python
# 明细重算 vs ADS 汇总值，必须完全相等
detail = read_sql("SELECT COUNT(*), SUM(is_bad) FROM dwd_loan_perf_fact WHERE is_terminal=1")
ads    = read_sql("SELECT SUM(loan_cnt), SUM(bad_cnt) FROM ads_risk_segment WHERE dim_type='grade'")

```

**典型应用场景**：
- 每次跑批后自动校验（**任务成功 ≠ 数据正确**）
- 上游变更后的快速回归（换数据源、改口径）
- 生产里的"事前拦截"：ERROR 级失败直接阻断下游，不让错数据流出去

**面试追问**："你校了哪几项？" →
按"最值钱的先说"：**汇总一致性**（报表数 = 明细重算数）、
**行数守恒**、**主键唯一**、**无未来信息**（防泄漏）——
前三个保证"数对"，第四个保证"口径合法"。

### 3.1 Spark 3.5.9

**是什么**：分布式计算引擎。核心抽象是 **DataFrame**（分布式表）、
**RDD**（底层数据集）、**Catalyst 优化器**（把 SQL 变成物理计划）、
**AQE**（运行时自适应优化）。两种用法：`spark-sql`（写 SQL）和 **PySpark**（写代码）。

**项目里怎么用**：

| 用法 | 位置 | 说明 |
|---|---|---|
| `spark-sql` 交互/脚本 | `07_bigdata/hive/*.sql` | 建表、装载、复现 ADS 指标 |
| **PySpark 作业** | `07_bigdata/spark/vintage_job.py` | 用 DataFrame API 重写一条链路，证明"能写工程代码" |
| PySpark 校验 | `07_bigdata/check_consistency.py` | 双引擎一致性校验（不抓 CLI 输出） |
| 实验 harness | `08_benchmark/run_experiment.py` | 跑实验 + 自动记录数字 |

**最小例子**：

```bash

```

```sql
CREATE DATABASE IF NOT EXISTS credit_dwh_lc;
USE credit_dwh_lc;
CREATE TABLE dwd_loan_fact_lc (
  loan_id STRING, funded_amnt DECIMAL(14,2), grade STRING, int_rate DECIMAL(8,4)
)
PARTITIONED BY (issue_month STRING)     -- ⭐ 分区列不写在字段列表里
STORED AS ORC;
EXPLAIN EXTENDED SELECT COUNT(*) FROM dwd_loan_fact_lc WHERE issue_month='2018-06';
-- 看 PartitionFilters → 证明分区裁剪下推
```

```python
# ② PySpark 方式：DataFrame API，显式声明窗口帧
from pyspark.sql import Window
from pyspark.sql import functions as F

w = (Window.partitionBy("issue_month", "loan_id").orderBy("mob")
     .rowsBetween(Window.unboundedPreceding, Window.currentRow))   # ⭐ 不用默认 RANGE 帧
snap = snap.withColumn("ever_bad", F.max("is_bad_month").over(w))
(snap.groupBy("issue_month", "mob")
     .agg(F.count(F.lit(1)).alias("exposure_cnt"), F.sum("ever_bad").alias("bad_cnt"))
     .withColumn("bad_rate", F.round(F.col("bad_cnt") / F.col("exposure_cnt"), 6))
     .write.mode("overwrite").format("orc").saveAsTable("credit_dwh_lc.ads_vintage_spark"))
```

**典型应用场景**：
- 数据量超过单机舒适区（本项目是**故意用它做对照实验**，而不是"数据装不下"）
- 多轮迭代计算（特征工程、图计算、机器学习流水线）
- 与数据湖/对象存储集成（S3、HDFS、Iceberg/Hudi）
- **同一套 SQL 同时服务批处理与流处理**（Structured Streaming）

**面试追问**："Spark 比 MySQL 快吗？" →
**在我的量级不一定**。E5 实测：226 万行下两者耗时相当，
但 Spark 每个作业有固定启动开销（实测 `__` 秒）、资源占用高一个量级。
**结论是"有条件推荐"**：数据量超约 `__` 万行、或数据本就在分布式存储上、

### 3.2 Hive Metastore 3.1.3

**是什么**：**元数据服务**。它回答"有哪些库/表/分区、表文件在哪、格式是什么"，
本身**不存数据、也不算数据**。对外通过 thrift 协议在 9083 端口提供服务。

**项目里怎么用**：
- 容器 `bd-metastore`（`apache/hive:3.1.3`），元数据存在 MySQL 容器 `bd-metastore-db` 里
- Spark 通过 `spark.hadoop.hive.metastore.uris=thrift://metastore:9083` 连它
- **表和卷共享**：`spark_warehouse` 卷同时挂给 `bd-spark` 与 `bd-metastore`，
  路径都用 `/opt/spark/warehouse`（**否则"表在元数据里、文件在别处"**）

**最小例子**：

```sql
-- 看元数据里到底记了什么（这是理解 Metastore 的最快方式）
DESCRIBE FORMATTED dwd_loan_fact_lc;
-- Location:  /opt/spark/warehouse/credit_dwh_lc.db/dwd_loan_fact_lc   ← 绝对路径！
-- Table Type: MANAGED_TABLE
-- SerDe:      org.apache.hadoop.hive.ql.io.orc.OrcSerde
```

```powershell
# 验证表是"跨会话持久"的（证明用的真是外部 Metastore，不是内置 Derby）
docker exec -i bd-spark /opt/spark/bin/spark-sql -e "USE credit_dwh_lc; SHOW TABLES;"
```

**典型应用场景**：
- **多引擎共享同一份元数据**（Spark 算、Hive/Presto/Trino 读同一批表）
- 元数据集中管理（权限、审计、血缘的挂载点）
- 生产里的"元数据 / 存储 / 计算三层分离"架构

**面试追问**："Spark 用 Hive 吗？" →
"我用的是**Hive 的元数据与表格式，执行引擎是 Spark**"
（`spark.sql.catalogImplementation=hive` + 外部 Metastore）。
这个区分很重要：分区裁剪、ORC 列存、Hive DDL 语法全都在，
但计算不是 Hive on MR。
**另外有一个版本坑**：Spark 3.5 只支持 HMS 到 **3.1.3**，
连 Hive 4.0.x 会报 thrift `Invalid method name: 'get_table'`。

### 3.3 Hive 表 / 分区 / ORC 列存

**是什么**：
- **分区**：表按某列的值拆成**目录**（`issue_month=2018-06/`），本质是目录结构，不是行数据
- **列存（ORC/Parquet）**：按列存储 + 编码压缩，只读用到的列
- 两者叠加 = **分区裁剪（跳过目录）+ 列裁剪（跳过列）**

**项目里怎么用**：
- `dwd_loan_fact_lc` 按 `issue_month` 分区；`dws_loan_snapshot_lc` 按 `snapshot_month` 分区
- 全部 `STORED AS ORC`
- E1 实验量化"分区裁剪省了多少 IO"；E3 实验量化"列存 vs 行存"

**最小例子**：

```sql
-- 分区裁剪：过滤条件下推到目录层（E1 的核心证据）
EXPLAIN EXTENDED SELECT COUNT(*) FROM dwd_loan_fact_lc WHERE issue_month = '2018-06';
--   PartitionFilters: [isnotnull(issue_month), (issue_month = 2018-06)]
-- ↑ 有这一行，说明 Spark 在"列举文件"阶段就跳过了不匹配的目录

-- 目录长什么样（分区就是目录，一眼就能看懂）
```

```powershell
docker exec bd-spark bash -c "ls /opt/spark/warehouse/credit_dwh_lc.db/dwd_loan_fact_lc | head -3"
# issue_month=2007-06   issue_month=2007-07   ...
```

**典型应用场景**：
- 按时间切片的查询（"只看 2018 年 6 月"）—— 大表最常用的优化
- 宽表的少列分析（137 列只取 5 列）
- 日志/事件类数据（按天分区、列存压缩）

**面试追问**："分区裁剪为什么省的是 IO 而不是计算？" →
因为它作用在**文件列举阶段**：不匹配的目录**根本不打开**。
我在 E1 里做了**同谓词对照**（分区表 vs 非分区表），
输出行数完全相同、扫描文件数差 `__` 倍 —— 这就证明了省的是 IO。

### 3.4 Spark SQL hints（REPARTITION / COALESCE / REBALANCE）

**是什么**：写在 SQL 里的"给优化器的提示"，用来控制**分区数**与**数据分布**。

**项目里怎么用**：

| Hint | 作用 | 用在哪个实验 |
|---|---|---|
| `/*+ REPARTITION(n) */` | **完整 shuffle**，可增可减分区数 | E2 制造小文件（约 200 × 月份数个文件） |
| `/*+ COALESCE(n) */` | **不 shuffle**，只能减少分区 | E2 合并成"每个分区 1 个文件" |
| `/*+ REBALANCE(col) */` | 按列重分区，**AQE 可以拆分其中的倾斜分区** | E4 解决**聚合倾斜**（引擎原生方案） |

**最小例子**：

```sql
-- ① 制造大量小文件（写分区表时，一个 task 对它持有的每个分区值各写一个文件）
CREATE TABLE tmp_files_many PARTITIONED BY (issue_month STRING) STORED AS ORC
AS SELECT /*+ REPARTITION(200) */ * FROM dwd_loan_fact_lc
   WHERE issue_month BETWEEN '2017-01' AND '2017-12';

-- ② 合并：COALESCE 不 shuffle，把上游分区合并掉（每分区 1 个文件）
CREATE TABLE tmp_files_one_per_part PARTITIONED BY (issue_month STRING) STORED AS ORC
AS SELECT /*+ COALESCE(1) */ * FROM tmp_files_many;

-- ③ 聚合倾斜：加一个 hint，让 AQE 去拆倾斜分区
SELECT /*+ REBALANCE(loan_status) */ p.loan_status, COUNT(*)
FROM dwd_loan_fact_lc f JOIN dwd_loan_perf_fact_lc p ON f.loan_id = p.loan_id
GROUP BY p.loan_status;
```

**典型应用场景**：
- 输出文件太多/太小 → `COALESCE` 或控制 `spark.sql.files.maxRecordsPerFile`
- 上游分区不均 → `REPARTITION`
- 明确的聚合倾斜且版本 ≥ 3.2 → 先试 `REBALANCE`（不用自己维护盐）

**面试追问**："文件数是怎么定的？" →
**文件数 ≈ 任务数 × 每个任务持有的分区值数**。
写分区表**不会**按分区列再 shuffle（写阶段只做分区内排序），
所以 `REPARTITION(200)` 会得到**约 200 × 月份数**个文件 —— 比想象的多。

### 3.5 数据倾斜与加盐两阶段聚合

**是什么**：**数据倾斜** = 少数 key 占了大量数据，hash 之后全落到同一个 task，
导致"一个 task 干 47% 的活"，整个 Stage 被它拖住。
**加盐两阶段聚合**是最经典的手工解法。

**项目里怎么用**（E4 是整个阶段三的核心实验）：
- 量化：`loan_status` 里 Fully Paid 占 **47.63%**、倾斜比 **4.29**
- 复现：关掉 AQE 拿到确定性基线，看**最长 task ÷ 中位 task** 的倍数
- 解决：跑 5/10/20 三种盐桶数，找最优
- 验证：**NULL 安全的 FULL OUTER JOIN** 逐行比对加盐前后结果
- 边界：对比 AQE / `REBALANCE` / 手动加盐三种方案

**最小例子**：

```sql
WITH salted AS (
  SELECT f.loan_id, p.loan_status, f.funded_amnt, f.int_rate, p.is_bad,
         -- ⭐ 用 hash(loan_id) 而不是 RAND()：结果确定性，实验可复现
         pmod(hash(f.loan_id), 10) AS salt
  FROM dwd_loan_fact_lc f JOIN dwd_loan_perf_fact_lc p ON f.loan_id = p.loan_id
), stage1 AS (
  -- 阶段 1：盐进入分组键 → 大 key 被拆成 10 份，分散到多个 reducer
  SELECT loan_status, salt,
         COUNT(*) AS part_cnt,
         SUM(funded_amnt) AS part_amnt,
         SUM(funded_amnt * int_rate) AS part_rate_num,   -- ⭐ 保留分子！
         SUM(is_bad) AS part_bad
  FROM salted GROUP BY loan_status, salt
)
-- 阶段 2：去盐再聚合。输入已经从 226 万行降到 10×9 行，再不均也无所谓
SELECT loan_status, SUM(part_cnt) AS loan_cnt,
       ROUND(SUM(part_amnt), 2) AS total_amnt,
       SUM(part_rate_num) AS rate_numerator, SUM(part_bad) AS bad_cnt
FROM stage1 GROUP BY loan_status;
```

```sql
-- 正确性验证：不一致行数必须为 0（NULL 安全连接！）
SELECT COUNT(*) AS total_rows,
       SUM(CASE WHEN a.loan_cnt <> b.loan_cnt THEN 1 ELSE 0 END) AS cnt_mismatch
FROM e4_base_result a
FULL OUTER JOIN e4_salted_result b
  ON a.loan_status = b.loan_status
 AND COALESCE(a.purpose,'__NULL__') = COALESCE(b.purpose,'__NULL__');
```

**典型应用场景**：
- 大表按热点维度聚合（按状态、按省份、按商户）
- 大表 JOIN 大表且其中一个 key 严重倾斜
- **兜底手段**：Spark 2.x、Hive on MR 上没有 AQE 时，加盐几乎是唯一选择

**面试追问**："AQE 不是能自动处理吗？" →
三个层次答：
① AQE 的 `skewJoin` **只管 JOIN，不管 `GROUP BY`**；
② 就算 JOIN，它还有 `max(256MB, 5×中位分区)` 的双重阈值 ——
我这个数据量根本达不到，**默认阈值下它不认为这是倾斜**（实测把阈值调到 8MB 才生效）；
③ 聚合倾斜可以用 **`REBALANCE` hint + AQE**（3.2+ 默认开启），
这是"引擎原生加盐"，我会优先试它，手写加盐作为不支持的版本上的兜底。

### 3.9 Flink 1.20.4

**是什么**：真正的**流处理引擎**（Event Time 语义、Watermark、状态、Exactly-Once）。
与 Spark Structured Streaming 的区别：Flink 是**逐条流式**、延迟更低；
Spark 是**微批**。

**项目里怎么用**（第 19 步，可砍）：
- 只覆盖三个核心点（不贪多）：**Event Time + Watermark**、**滚动窗口聚合**、**幂等输出**
- 如果 pyflink 环境搞不定 → **降级为 Python + kafka-python 消费者**，
  把窗口聚合与幂等自己实现一遍（面试讲的是**语义**，不是环境）

**最小例子**（降级方案的思路，比 pyflink 更好读）：

```python
"""日粒度滚动窗口聚合 + 幂等写入（Python 消费者版）。

⭐ 三个要点：① 用事件自带时间做窗口 ② 容忍迟到数据 ③ 幂等写入
"""
from collections import defaultdict
from datetime import datetime, timedelta, timezone
import json

from kafka import KafkaConsumer
import pymysql

WATERMARK = timedelta(seconds=5)        # 允许迟到 5 秒
CN = timezone(timedelta(hours=8))       # ⭐ 统一北京时间，避免批流对账差一天

conn = pymysql.connect(host="127.0.0.1", port=3307, user="root",
                       password="root123456", database="credit_dwh", charset="utf8mb4")
consumer = KafkaConsumer("loan_issue_events", bootstrap_servers=["localhost:29092"],
                         value_deserializer=lambda b: json.loads(b.decode()), group_id="g1")

window = defaultdict(lambda: [0, 0.0])   # biz_date -> [笔数, 金额]
max_seen = datetime.min.replace(tzinfo=CN)

for msg in consumer:
    e = msg.value
    ts = datetime.fromisoformat(e["event_time"]).astimezone(CN)
    max_seen = max(max_seen, ts)
    biz_date = ts.date().isoformat()
    window[biz_date][0] += 1
    window[biz_date][1] += float(e["funded_amnt"])

    # 水位线判定：只有"足够安全"的窗口才落库（迟到数据会被并入 T+1 重算）
    for d in [d for d in window if datetime.fromisoformat(d).replace(tzinfo=CN) < max_seen - WATERMARK]:
        cnt, amt = window.pop(d)
        with conn.cursor() as cur:       # ⭐ 幂等：按主键 UPSERT，重复消费不重复计数
            cur.execute("""INSERT INTO ads_loan_daily_realtime (biz_date, loan_cnt, funded_amnt)
                           VALUES (%s,%s,%s)
                           ON DUPLICATE KEY UPDATE
                             loan_cnt = loan_cnt + VALUES(loan_cnt),
                             funded_amnt = funded_amnt + VALUES(funded_amnt)""",
                        (d, cnt, round(amt, 2)))
        conn.commit()
```

**典型应用场景**：
- 秒级/毫秒级实时指标（实时大屏、风控告警、实时推荐特征）
- 事件驱动架构（订单、支付、埋点）
- 有状态流处理（会话窗口、CEP 复杂事件）

**面试追问**："Event Time 和 Processing Time 有什么区别？" →
Processing Time 是"处理这台机器的时间"，乱序/延迟会让结果不一致；
Event Time 是"事件真实发生的时间"，配 **Watermark** 容忍迟到数据，
重跑同一批数据能得到同样结果（可复现）。
**批流对账的差异，八成来自时区/日界**（我在对账报告里专门记了这一条）。

## §4 技术怎么协作：两次"跑批"分别发生了什么

### 4.1 阶段二：`run_pipeline.ps1` 一次完整跑批

| 步骤 | 模块 | 用到的技术 | 产出 |
|---|---|---|---|
| 01 | `src.prepare_raw` | Python + gzip 流式 + pandas 分块 + pyarrow | `loans_full.parquet`（338 MB） |
| 02 | `src.ods_load` | pandas 分块 + SQLAlchemy/`to_sql` | `ods_loan_raw` 2,260,668 行 |
| 03 | `src.dwd_clean` | pandas 类型解析（`%b-%Y`、`term`、`emp_length`） | `dwd_loan_fact` + 派生字段 |
| 04 | `src.dwd_derived` | pandas + 状态映射（`config.DPD_MAP`） | `dwd_loan_perf_fact`（含 `is_terminal`/`is_bad`） |
| 05 | `src.dim_build` | pandas 分箱（收入/评级/利率）+ 日期维 | 3 张维表 |
| 06 | `src.dws_snapshot` | pandas 逐月生成 + PyMySQL **批量写** + 索引管理 | 快照 44,718,091 行（**可跳过**） |
| 07 | `src.ads_metrics` | **纯 SQL**（窗口函数/自关联） | 4 张 ADS 表 |
| 08 | `src.dq_check` | SQL 断言 + 落库留痕 | 11 项检查全通过，`dq_check_result` |

**一句话**：pandas 负责"把数据洗干净"，SQL 负责"把口径算对"，PowerShell 负责"按顺序跑、出错就停"。

### 4.2 阶段三：从迁移到结论

| 环节 | 用到的技术 | 关键产出 |
|---|---|---|
| 导出 | Python 子进程 + `mysql --batch`（**不经 pandas**） | `exchange/*.tsv`，NULL=`\N` |
| 建表装载 | Hive DDL + Spark 读 CSV(TSV) + 动态分区覆盖 | `credit_dwh_lc` 4 张 ORC 表 |
| 一致性门槛 | PySpark + JSON 基准值 | `consistency_result.csv`（7/7 一致） |
| 口径复现 | Spark SQL（含 `grade='ALL'`、最近 12 个观测月） | 4 张 ADS 表逐行一致 |
| E1–E3 | Spark SQL + hints + 事件日志 + 文件统计 | 分区裁剪/小文件/列存三份记录 |
| E4 | 加盐两阶段 + AQE 三态 + `REBALANCE` | 倾斜报告（最长÷中位、最优桶数） |
| E5 | PySpark 作业 + MySQL 计时 + 阶梯样本 | **引擎选型结论**（阈值 + 固定开销） |
| 工程化 | pytest/ruff/CI + 血缘 + SLA | 口径回归防线 |

**一句话**：阶段三的重点不是"学会 Spark"，而是**用一套可复现的测量方法，得出一个能被追问的结论**。

## §6 选型对照：为什么是它，而不是 X

> 面试里"为什么不用 X"往往比"为什么用 Y"更能体现判断力。

| 我用的 | 常见的替代 | 为什么本阶段不用替代 |
|---|---|---|
| **MySQL** 存数仓 | PostgreSQL / ClickHouse / Doris | 阶段二要的是"事务 + 约束 + 索引"的教学闭环；ClickHouse 这类列存 OLAP 更适合大宽表聚合，但没有主键约束与事务语义，教不了"主键顺序影响写入"这一课 |
| **pandas** 做清洗 | Polars / DuckDB | 生态最广、资料最多；226 万行完全在舒适区。DuckDB 在"直接用 SQL 查 Parquet/CSV"上更优雅，但没有"练 SQL 与建表"的收益 |
| **Parquet** 做交换 | CSV / TSV / Avro | CSV 无 schema、体积大；**阶段三反而故意用 TSV 做交换**（要显式 schema、要流式、要 NULL 可判）——**不同场景选不同格式，这本身就是判断力** |
| **Spark** 做分布式 | Hive on MR / Flink 批 / Trino | MR 慢且已过时；Trino 是查询引擎（不擅长写入加工）；Flink 批的能力不如 Spark 成熟。Spark 生态最全、SQL 兼容性最好 |
| **Hive Metastore** 管元数据 | 内嵌 Derby / 自带 catalog | Derby 只能单会话（重启表就没了）；外部 Metastore 才能体现"元数据/存储/计算三层分离" |
| **ORC** 做列存 | Parquet | 两者都在用（Parquet 是默认交换格式）；ORC 在 Spark 里对低基数列编码更优，且 Hive DDL 语法更自然 |
| **Kafka** 做消息 | RabbitMQ / Pulsar | Kafka 是"数据管道"的事实标准（保留期、多消费者、与 CDC/Flink 生态天然集成）；RabbitMQ 更适合任务队列 |
| **Debezium** 做 CDC | 自研 binlog 解析 / Canal | Debezium 是标准方案，生态成熟（直接出 Connect 事件）；Canal 在国内常用但生态与文档不如它 |
| **PowerShell** 做编排 | Airflow / DolphinScheduler | 单机学习项目引入调度平台是**过度设计**；但我在文档里明确写了"生产上我会用调度平台，并且清楚脚本编排缺什么" |

## §7 我明确没用的技术（诚实边界）

> **知道什么不做，和知道什么要做一样重要。** 这一段是面试的加分项。

| 没用 | 原因 |
|---|---|
| **HDFS / YARN** | 单机 Docker 里跑 HDFS 只增加故障面，不增加实验结论（方案 A 已覆盖全部五个实验） |
| **Iceberg / Hudi / Delta Lake** | 数据湖表格式解决的是"ACID + 时间旅行 + schema 演进"，本项目没有多写入方并发与增量快照的需求；引入它会让"实验变量"变多 |
| **Airflow / DolphinScheduler** | 8 步流水线用脚本足够；缺的是 DAG/重试/补数，我**明确知道缺什么** |
| **Atlas / DataHub / Great Expectations** | 单机项目引入重型平台是过度设计；我用 YAML + SQL 覆盖了核心场景（血缘、四类 SLA） |
| **Kubernetes** | 单机学习环境的目的是理解组件，不是练编排 |
| **机器学习 / 特征平台** | **本项目是数据工程，不是算法建模** —— 定位要说清楚，别硬蹭 |
| **真实实时数据源** | 没有就是没有。第 19 步明确标注"**历史数据回放**"，验证的是架构与口径一致性，不冒充实时性能 |

## §8 面试速查卡

### 8.1 每个技术一句话

| 技术 | 一句话（可直接背） |
|---|---|
| pandas | "226 万行 CSV 的分块清洗与类型标准化，页脚剔除、dtype 固定、Parquet 落地。" |
| Parquet/ORC | "列存：只读需要的列。E3 里量化了 TextFile/Parquet/ORC 的体积与查询耗时差异。" |
| MySQL | "13 张表的数仓本体；靠**主键顺序与写入顺序同序**把快照写入从 5,379 提到 38,032 行/秒。" |
| SQL 窗口函数 | "用 `MAX(is_bad_month) OVER (... ROWS ...)` 取'曾核销'标志，避免累计不良率重复计数。" |
| 维度建模 | "申请时点/表现期**物理分表**防泄漏；月末快照替代 SCD2；客户维降级为申请人画像维。" |
| Hive Metastore | "元数据与计算分离。它存的是**绝对路径**，所以计算侧必须能看到同一个路径。" |
| Spark | "同一套口径在 Spark 上重写一遍并**逐行比对**；再用五个对照实验量化性能差异。" |
| 分区 + ORC | "分区裁剪省的是 **IO 不是计算** —— 我用同谓词的非分区表做了对照组证明这一点。" |
| 数据倾斜 | "`loan_status` 最大 key 占 47.63%、倾斜比 4.29；用确定性加盐两阶段聚合把最长÷中位从 `__` 降到 `__` 倍。" |
| AQE | "skewJoin 只管 JOIN、且有 256MB 阈值；聚合倾斜要用 `REBALANCE` 提示。" |
| Kafka/Debezium | "binlog（ROW 格式）→ Debezium → Kafka topic；下游按主键 UPSERT 保证幂等。" |
| Flink | "Event Time + Watermark + 滚动窗口；批流对账的差异八成来自时区日界。" |
| pytest/CI | "把算错过的口径写成单测 —— 口径再被改错时 CI 直接红，而不是等报表出数。" |
