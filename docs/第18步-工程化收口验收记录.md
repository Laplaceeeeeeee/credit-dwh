## 3. 单测清单（34 条）与"为什么是这几条"

| 测试类 | 条数 | 固化的是什么口径 |
|---|---|---|
| `Test不良口径` | 8 | 不良 = Charged Off + Default（含政策外核销）；`Current` 不是不良；脏数据不抛异常 |
| `Test终态口径` | 6 | 不良率分母只算终态；状态枚举与不良集合的子集关系 |
| `Test加权平均利率` | 4 | 必须按金额加权（简单平均会失真）；空/含 NULL 不崩 |
| `TestDPD档位` | 10 | `loan_status -> DPD 档位` 映射（迁徙率的分组基础） |
| `Test倾斜比公式` | 5 | ⭐ 阶段三新增：`share × n_keys` |
| `Test行数守恒` | 1 | ODS = DWD = 2,260,668，差 **0** |

**⭐ 其中 3 条不是普通测试，而是"把踩过的坑固化成防线"：**

1. `test_不良率分母必须排除非终态` —— 当初漏了这条，把不良率从 **19.98% 算成 11.9%**
   （`Current` 占 38.85%，稀释了分母）。
2. `test_恒等式写法是错的` —— 在按 key 分组的查询里用 `COUNT(DISTINCT key)`
   自算"平均占比"，该表达式**恒等于 1**，于是"倾斜比"退化成占比本身（0.4763），
   会得出"这里没有倾斜"的错误结论。E4 差点因此误判。
3. `test_ODS与DWD行数必须相等` —— v2 写的 `assert ods - dwd == 32` 是**误判**，
   那 32 行是散布在文件里的**页脚**（预处理阶段就剔除了，见
   `05_quality/数据质量校验报告.md` Q1）。**与实测不符的断言会让 CI 永远红着，
   最后没人再看 CI** —— 所以这条必须按实测写成 0。

## 4. 与指导书模板不一致的实测修正（6 处，全部按实测处理并已回写）

| # | 指导书/模板的写法 | 实测结论 | 处理 |
|---|---|---|---|
| 1 | `pytest.ini` 只有 markers/testpaths/addopts | CI 里跑的是**裸 `pytest`**（不是 `python -m pytest`），此时 pytest 只把 `tests/` 插进 `sys.path` → `from src.metrics import ...` 会 `ModuleNotFoundError` | 加 **`pythonpath = .`**，让本地命令与 CI 命令**完全一致** |
| 2 | CI 的 ruff 目标含 `09_realtime/` | 第 19 步未开工、目录不存在，**ruff 对不存在的路径直接报错退出** → 照抄必红 | 去掉 `09_realtime/` 并在 workflow 里注释说明，第 19 步落地后加回 |
| 3 | `lineage.yaml` 模板：`dim_applicant / dim_product / dws_loan_snapshot_m` 从 `dwd_loan_fact` 读；`ods_loan_raw -> dwd_loan_fact` | 代码里 `src/dim_build.py`、`src/dws_snapshot.py`、`src/ods_load.py`、`src/dwd_clean.py` **都直接 `read_clean()` 读同一份干净 Parquet** —— 是扇出，不是串接 | 按实测重写血缘边，并在图下写"读图须知"解释设计取舍（生产里通常串接） |
| 4 | SLA §2.2 的"数据量波动"SQL：两个都读同一张全表的子查询相除 | 该比值**恒等于 1.0**，永远返回 OK —— 是**假监控**（与第 2 条 `COUNT(DISTINCT key)` 同一类错误） | 改成按放款月的真实参照窗口（近 7 月均值） |
| 5 | SLA 表里"比率容差 1e-6"（附录 B-8 同） | MySQL `div_precision_increment=4` 使两侧差异上界为 **5e-5**，1e-6 **永远无法通过**；附录 B-39 的实测结论与之自相矛盾 | 统一为 **5e-5 + 平局判据**，并在 SLA 文档里写明"为什么不是放宽容差" |
| 6 | `gen_lineage.py` 模板只从 `downstream` 连边 | **外部节点的出边全部漏画**（`file:` / `kafka:` / `calendar:` / `export:` 共 12 个节点在图上成了孤岛）；另外中文标签"消毒"成 node id 后**可能撞 id**（`report:分层风险画像` 与 `report:逾期月报` 这类），撞了会**静默合并两个节点** | 补上外部节点的出边；外部 id 改为 `n_ext_<kind>_<序号>` 保证唯一 |

> 推送失败的排查经过（值得记下来，因为花了不少时间，而且最后发现是两件不同的事）：
>
> 1. `git push` 报 `Failed to connect to 127.0.0.1 port 7897` —— 本机 git 配了
>    `http.proxy=http://127.0.0.1:7897`（本地代理软件），而当时**该端口没有进程在监听**。
> 2. 启动代理后**仍然失败**：`TLS connect error: error:00000000:lib(0)::reason(0)`。
>    逐层排查得到两个**互相独立**的结论：
>    - **本机 schannel 不可用**：`curl` 即使**不走代理**也报
>      `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`，
>      `git -c http.sslBackend=schannel` 报同一个错 → **不是网络问题**，是 TLS 凭据层的问题；
>    - **`github.com` 这一个域名被重置**：用 Python 亲手做 `CONNECT + TLS` 握手，
>      结果是 `pypi.org` / `api.github.com` / `raw.githubusercontent.com` **全部成功**，
>      而 `github.com` / `codeload.github.com` **每次都失败**（`SSLEOFError` / 连接重置）；
>      同时 `github.com:443` **直连**也超时（实测 `20.205.243.166:443` 无响应）。
>      → 说明代理在**规则模式**下把 `github.com` 分流成了**直连**，被重置。
> 3. 当时判断"修法在代理侧"（切 Global / 改 `github.com` 分流规则 / 换节点）——
>    **但这个判断后来被证明只对了一半**：真正的最后一公里是**凭据**，不是网络。
>
> **最终怎么推上去的（2026-09-22 补记）**：
> ```powershell
> # 网络侧其实早就通了 —— 直连就行，把 git 里配的本地代理清掉即可
> git -c http.proxy= -c https.proxy= ls-remote origin      # 能列出 refs 就说明网络没问题
> git -c http.proxy= -c https.proxy= push origin main      # 89c28d3..72da108  main -> main
> ```
> 两处**都不是网络问题**的真凶：
> ① 第一次被 GitHub **原子拒绝**：`refusing to allow a Personal Access Token to create or
>    update workflow '.github/workflows/ci.yml' without 'workflow' scope`
>    → PAT 缺 `workflow` 权限（提交里碰到 `.github/workflows/**` 就必须有它），
>    加 scope 后重推即可；**三个"看似网络故障"的坑，其实是代理未开、PAT 缺 scope、git 没配 credential.helper**。
> ② 本机 git **没配 `credential.helper`**，所以每次都要手输凭据。
>
> **推上去后实测**：`CI / lint-and-test` 对 `72da108` 的 run
> [`35698960325`](https://github.com/Laplaceeeeeeee/credit-dwh/actions/runs/35698960325) = `success`，
> 首页 badge = `passing`。若以后 runner 上红了，**优先怀疑 B-46（`pythonpath`）与 B-47（ruff 路径）**。

   `docs/SLA与监控.md` 里定义的是**判据**（可执行 SQL），不是自动化任务。

   在血缘图里是**虚线 + 标注"规划中"**，**表并不存在**。
