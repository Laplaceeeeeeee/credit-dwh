## §1 先看懂你要搭什么

### 1.1 五个角色，各干一件事

阶段三要用到 **4 个常驻容器**（第 19 步的实时链路再加 3 个，那部分可以砍）：

| 容器名 | 镜像 | 它是干什么的 | 用一个类比 |
|---|---|---|---|
| `credit-dwh-mysql` | `mysql:8.0` | **阶段二的数据仓库本体**（13 张表，226 万行） | 已经建好的**书库** |
| `bd-metastore-db` | `mysql:8.4` | Hive 的**元数据库**：存"有哪些库、哪些表、表在哪、有哪些分区" | 书库的**目录卡片柜** |
| `bd-metastore` | `apache/hive:3.1.3` | **Hive Metastore 服务**：对外提供"查目录"的接口（端口 9083） | **图书管理员**（拿着目录柜回答你的问题） |
| `bd-spark` | `apache/spark:3.5.9-…` | **Spark Master**：接活、派活；提供 Web UI（8080） | **包工头** |
| `bd-spark-worker` | `apache/spark:3.5.9-…` | **Spark Worker**：真正干活的进程 | **工人** |

> 🔑 **最容易混的一点**：`bd-metastore-db` 和 `credit-dwh-mysql` 是**两个独立的 MySQL**。
> - `credit-dwh-mysql` 存的是**数据**（贷款明细、指标）；
> - `bd-metastore-db` 存的是**元数据**（"`dwd_loan_fact_lc` 这张表在哪个目录、用什么格式"）。
>
> 它们长得像，但性质完全不同：**删了前者的数据仓库就没了；删了后者的表还在磁盘上，
> 只是"没人知道它叫什么"了**。

### 1.2 它们之间怎么说话（端口是重点）

```
你的 Windows 宿主机
   │
   │  PowerShell / 浏览器 / Python(venv)
   │
   ├─ localhost:3307  ───────────► credit-dwh-mysql    （阶段二的库，宿主端口是 3307！）
   ├─ localhost:8080  ───────────► bd-spark            （Spark Master Web UI）
   ├─ localhost:7077  ───────────► bd-spark            （Spark Master 提交作业）
   ├─ localhost:4040  ───────────► bd-spark            （作业运行时的 UI）
   ├─ localhost:9083  ───────────► bd-metastore        （Hive Metastore 的 thrift 接口）
   └─ localhost:18080 ───────────► （可选）History Server，回看已结束作业的 UI

Docker 内网 credit-dwh-net（容器之间互相用"服务名"通信）
   bd-spark ──thrift://metastore:9083──► bd-metastore ──jdbc──► bd-metastore-db
   bd-spark ──文件读写──► 卷 spark_warehouse（仓库目录 /opt/spark/warehouse）
   bd-metastore ──文件可见性──► 同一个卷 spark_warehouse
```

**三条必须记住的规则**：

1. **宿主用 `localhost:端口`，容器之间用 `服务名:端口`。**
   在容器里写 `localhost:9083` 指的是"容器自己"，不是 Metastore。
2. **阶段二的 MySQL 在宿主机上的端口是 `3307`**（映射到容器内的 3306）。
   写 `3306` 连不上是新手最常犯的错。
3. **`spark_warehouse` 这个卷必须同时挂给 `bd-spark` 和 `bd-metastore`，而且路径要一样。**
   原因见下一节。

### 1.3 为什么"元数据"和"数据文件"必须能对上

这是阶段三**第一个真正的坑**，理解了它，后面 90% 的"表建了却读不到"都能自己解决。

```
你在 Spark 里执行：CREATE DATABASE credit_dwh_lc;
        │
        ▼
Spark 把请求发给 Metastore（"帮我建个库"）
        │
        ▼
Metastore 决定这个库的**物理位置**：
        /opt/spark/warehouse/credit_dwh_lc.db        ← 注意：这是**绝对路径字符串**
        │
        ▼
Metastore 把这个路径**当成字符串存进元数据库**（它自己不去建目录）
        │
        ▼
Spark 收到回复，去 **自己的文件系统** 里写 /opt/spark/warehouse/credit_dwh_lc.db
```

看到问题了吗：**Metastore 只是"记账"，真正写文件的是 Spark**。
所以如果 Spark 容器里**没有** `/opt/spark/warehouse` 这个目录（或者它指向别的地方），
结果就是：

- 建表成功 ✅（元数据里记下了）
- 写数据失败或写到了别处 ❌
- 之后 `SELECT` 报 `Table not found` / 目录为空

**解法（本指导书采用）**：两个容器**挂同一个卷、用同一个路径**：

```yaml
volumes:
  - spark_warehouse:/opt/spark/warehouse     # bd-spark 里也这么写
  - spark_warehouse:/opt/spark/warehouse     # bd-metastore 里也这么写
```

> 🔑 **面试价值**：这就是"**元数据 / 存储 / 计算三层分离**"最直白的体现。
> 你能讲清"元数据里存的是绝对路径，所以计算侧必须能看到同一个路径"，
> 比背"Hive 有元数据服务"要有说服力得多。

## §2 Docker 新手速成（只看够用的部分）

> 如果你已经熟悉 Docker，直接跳到 §3。

### 2.1 五个词，五分钟

| 词 | 说明 | 类比 | 本项目的例子 |
|---|---|---|---|
| **镜像 image** | 一个只读的"安装包/模板" | 光盘 | `apache/spark:3.5.9-…` |
| **容器 container** | 镜像跑起来的实例，可读可写 | 装好的机器 | `bd-spark` |
| **卷 volume** | Docker 管理的**持久化存储**，删容器不删它 | 外接硬盘 | `spark_warehouse`、`metastore_db` |
| **绑定挂载 bind mount** | 把宿主机目录直接挂进容器 | 共享文件夹 | `F:\…\credit-dwh` → `/workspace` |
| **网络 network** | 容器之间的虚拟局域网，可用服务名互访 | 内网 | `credit-dwh-net` |

**为什么要用卷**：容器被删掉后，容器内的文件系统也没了。
所以"数据"必须放在卷（或绑定挂载）里，才能在你 `docker compose down` 之后还在。

### 2.2 ⭐ 容器内路径 vs Windows 路径（新手第一大坑）

绑定挂载的写法是 `宿主机路径:容器内路径`：

```yaml
volumes:
  - ../:/workspace
```

含义：把 **compose 文件所在目录的上一级**（也就是项目根 `credit-dwh/`）
挂到容器里的 `/workspace`。

于是下面这张对照表就成立了 —— **背下来，能省你两小时**：

| Windows 上的文件 | 在 `bd-spark` 容器里看到的是 |
|---|---|
| `F:\BUPT\Internship_Preparation\credit-dwh\07_bigdata\hive\01_ddl.sql` | `/workspace/07_bigdata/hive/01_ddl.sql` |
| `F:\BUPT\Internship_Preparation\credit-dwh\08_benchmark\_results\` | `/workspace/08_benchmark/_results/` |
| `F:\BUPT\Internship_Preparation\credit-dwh\src\utils.py` | `/workspace/src/utils.py` |

**三条推论（都是实战结论）**：

1. **`spark-submit` / `spark-sql -f` 里必须写容器内路径**，写 `F:\...` 一定报
   `No such file or directory`。
2. **相对路径的基准是 compose 文件所在目录，不是你的当前目录** ——
   所以 compose 放在 `07_bigdata/` 里时，挂项目根要用 `../:/workspace`。
   如果写成 `./:/workspace`，容器里 `/workspace` 就等于 `07_bigdata/`，
   那么 `/workspace/07_bigdata/hive/…` 会因为多了一层而**找不到**。
3. **容器里写出来的文件，在 Windows 上能直接看到**（因为它是绑定挂载，不是卷）。
   这正是我们把实验结果写到 `08_benchmark/_results/` 的原因 ——
   你在资源管理器里就能打开。

### 2.3 四个常用命令（先记住这四条就够）

```powershell
# ① 看容器在不在跑（-a 连没跑的也显示）
docker ps
docker ps -a

# ② 看容器日志（排错第一步；--tail 只看最后 N 行；-f 持续跟随）
docker logs bd-metastore --tail 50
docker logs -f bd-metastore

# ③ 进容器里执行命令（-it 才能交互）
docker exec -it bd-spark bash
#    进去以后可以用 ls / pwd / cat；exit 退出

# ④ 宿主机上直接跑容器里的命令（脚本里大量用这种）
docker exec bd-spark ls /opt/spark/warehouse
```

> 💡 **`docker exec` 与 `docker run` 的区别**：
> `exec` 是"在**已经在跑的**容器里执行命令"（我们的日常都用它）；
> `run` 是"用镜像**新起一个**容器"（只在临时做实验时用）。

### 2.4 ⚠️ 三种"停"与"删"，别搞错（会丢数据）

| 命令 | 做什么 | 数据会丢吗 | 什么时候用 |
|---|---|---|---|
| `docker compose stop` | 停止容器，**保留**容器与卷 | ❌ 不会 | 临时不用（比如做实验时腾内存） |
| `docker compose down` | 停止并**删除容器和网络**，**保留**卷 | ❌ 不会 | 想彻底重来一遍配置（改 compose 后常用） |
| `docker compose down -v` | 上面基础上**连卷一起删** | ✅ **会丢** | ⚠️ 只有"我要把所有数据清空重来"时才用 |
| `docker volume rm spark_warehouse` | 直接删那个卷 | ✅ **会丢** | 同上，更危险 |

> 🚨 **新手最惨的一种事故**：想"重启一下环境"，顺手敲了 `down -v`，
> 结果 Hive 仓库和 Metastore 元数据全没了，几十个小时的导入白做。
> **记住：改配置用 `down`（不带 `-v`）；要清空数据才用 `down -v`。**
>
> ⚠️ 特别注意：**`bd-metastore-db` 的元数据在 `metastore_db` 卷里**。
> 卷还在，表就还在；卷没了，就要重新跑一遍 DDL 与导入。

### 2.5 怎么读一个 compose 文件

```yaml
services:                     # ← 要跑哪些"服务"（=容器）
  metastore-db:               # ← 服务名，也是容器之间互相访问用的域名
    image: mysql:8.4          # ← 用哪个镜像
    container_name: bd-metastore-db   # ← 容器叫什么（docker logs 用这个名字）
    environment:              # ← 传给容器的环境变量
      MYSQL_ROOT_PASSWORD: root123456
    ports:
      - "9083:9083"           # ← "宿主机端口:容器端口"
    volumes:
      - metastore_db:/var/lib/mysql       # ← "卷名:容器内路径"（持久化）
      - ./conf/hive-site.xml:/hive_custom_conf/hive-site.xml:ro
      #      ↑宿主机相对路径      ↑容器内路径                ↑只读
    depends_on:               # ← 启动顺序（不保证"就绪"，只保证"先起"）
      metastore-db:
        condition: service_healthy        # ← 等健康的 healthcheck 通过再起
    healthcheck:              # ← 健康检查（给 depends_on 用）
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-proot123456"]
```

**三个容易忽略的点**：

1. `ports` 只有**需要从宿主机访问**时才写。容器之间直接用服务名 + 容器内端口。
2. 绑定挂载的路径是**相对 compose 文件所在目录**的。
3. `depends_on` + `condition: service_healthy` 只是"等它健康"，
   **不代表业务就绪** —— 比如 MySQL 健康了，Metastore 可能还在初始化 schema。
   所以 §7 的"分层验收"不能省。

## §3 开工前的自检

**目的**：先把"机器够不够、盘够不够、Docker 活没活"确认掉。
这三件事任何一个不对，后面都会以一个**看起来像配置错误**的方式炸掉。

```powershell
# 找一份能用的 PowerShell，并进入项目根目录
cd F:\BUPT\Internship_Preparation\credit-dwh

# ① CPU 逻辑核心数（本机实测 28）
"CPU 逻辑核心: $env:NUMBER_OF_PROCESSORS"

# ② 物理内存（Get-CimInstance 被策略拦住就开任务管理器看）
try { "内存 GB: " + [math]::Round((Get-CimInstance Win32_ComputerSystem).TotalPhysicalMemory/1GB,1) }
catch { "权限受限 -> 任务管理器 → 性能 → 内存" }

# ③ 各盘剩余空间（Docker 数据目录所在的盘最关键）
Get-PSDrive -PSProvider FileSystem |
  Select-Object Name, @{N='FreeGB'; E={[math]::Round($_.Free/1GB,1)}} | Format-Table

# ④ Docker 在不在跑
docker info --format '{{.ServerVersion}}'

# ⑤ Docker 已经吃掉多少（镜像/容器/卷/构建缓存）
docker system df

# ⑥ 阶段二的库在不在（注意端口 3307，不是 3306）
docker ps --filter "name=credit-dwh-mysql" --format "{{.Names}}  {{.Status}}  {{.Ports}}"
```

**判断标准**：

| 检查项 | 必须满足 | 不满足怎么办 |
|---|---|---|
| 逻辑核心 | ≥ 4 核（本机 28，很富裕） | — |
| 物理内存 | **≥ 12 GB** 才能跑方案 A | < 12 GB 走 §12 降级 L2（单容器 + Derby） |
| Docker 数据盘剩余 | **≥ 30 GB** | 见下面"盘满警告" |
| `docker info` | 打印出版本号 | 启动 Docker Desktop，等托盘图标变绿 |
| 阶段二 MySQL | `Up (healthy)`，`0.0.0.0:3307->3306` | `docker start credit-dwh-mysql` |

> 🚨 **`docker info` 报这个错，99% 是"没启动 Docker Desktop"**：
> ```
> failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine;
> check if the path is correct and if the daemon is running:
> open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified.
> ```
> **这不是命令写错了**，去启动 Docker Desktop 就行。

> ⚠️ **盘满警告（本项目真实踩过）**：阶段二跑全量快照时，
> Docker 的虚拟磁盘涨到 74 GB，把系统盘撑到只剩 2 GB，**Docker daemon 直接起不来**。
> 阶段三会再增加镜像 6–10 GB、Hive 仓库 2–4 GB、TSV 交换文件约 5 GB。
> **开工前先确认 Docker 数据目录所在盘 ≥ 30 GB**：
> Docker Desktop → `Settings → Resources → Advanced → Disk image location`。

**顺手确认 venv 可用**（后面导出数据要用它，不能用系统 Python）：

```powershell
& .\.venv\Scripts\python.exe -c "import pandas,pymysql,sqlalchemy,pyarrow; print('venv OK')"
# 如果报 ModuleNotFoundError: pyarrow
& .\.venv\Scripts\python.exe -m pip install -r requirements.txt pyarrow
```

### 4.2 `.env`：把镜像 tag 集中到一个地方

**为什么**：镜像 tag 会变（尤其这次 Bitnami 目录迁移之后）。
放在 `.env` 里，换镜像只改这一个文件，`compose` 一行都不用动。

**`07_bigdata/.env`**：

```ini
# ⭐ 本机实测可用的组合（Docker Desktop 已配国内镜像源）
SPARK_IMAGE=apache/spark:3.5.9-scala2.12-java11-python3-ubuntu
HIVE_IMAGE=apache/hive:3.1.3
METASTORE_DB_IMAGE=mysql:8.4
```

> ⚠️ **tag 必须是你预检通过的**（§5）。上面这三个是**本机实测可用的值，不是永恒有效**。
> ⚠️ 注意官方 Spark 镜像的 tag 是**多段式**：
> `<版本>-scala<X>-java<Y>-python3-[r-]<发行版>`。
> 写成 `apache/spark:3.5.9` 大概率不存在。

### 4.3 `conf/hive-site.xml`：告诉 Metastore"仓库放哪"

**`07_bigdata/conf/hive-site.xml`**：

```xml
<?xml version="1.0"?>
<configuration>
  <!-- Metastore 侧：新建库/表的默认物理位置。
       必须与 Spark 侧 spark.sql.warehouse.dir 一致，且两个容器都挂同一卷 -->
  <property>
    <name>hive.metastore.warehouse.dir</name>
    <value>/opt/spark/warehouse</value>
  </property>
  <!-- 单机学习环境：不做用户/角色鉴权（生产上当然不能这么干） -->
  <property>
    <name>hive.metastore.execute.setugi</name>
    <value>true</value>
  </property>
</configuration>
```

> 💡 **它不是"可选优化"，而是"防止元数据与文件对不上"的关键配置**。
> 如果这里写 `/opt/hive/data/warehouse` 而 Spark 那边配 `/opt/spark/warehouse`，
> 就会出现"元数据说表在 A，文件却在 B"的诡异现象。

### 4.4 `conf/spark-defaults.conf`：Spark 的默认参数

**`07_bigdata/conf/spark-defaults.conf`**：

```properties
# ============================================================
# 1) 元数据：用外部 Hive Metastore，而不是内置 Derby
# ============================================================
spark.sql.catalogImplementation   hive
spark.hadoop.hive.metastore.uris  thrift://metastore:9083
spark.sql.warehouse.dir           /opt/spark/warehouse

# ⭐⭐ Metastore client 版本：两条路（本机实测结论）
#   支持矩阵：0.12.0–2.3.9 与 3.0.0–3.1.3（**Hive 4.x 不在内**，连了报 thrift get_table）
#
#   ① 【推荐先试】什么都不用配 —— 用 Spark 内置的 Hive client 直连 HMS 3.1.3。
#      实测：SHOW DATABASES 4.4 秒返回；建库/建表/分区/插入/查询全部正常。
#      ⚠️ 代价：client(2.3.9) 与 server(3.1.3) 版本不一致，"可用但不推荐生产使用"。
#
#   ② 【要版本严格对齐时】
#      · jars=maven 首次走 Ivy 解析 —— 实测在容器里跑 7 分钟仍未完成，
#        且缓存落在容器可写层 /root/.ivy2，容器重建即丢（必须给它挂命名卷）。
#      · 更稳的是 jars=path + 宿主机预下载 jar 目录挂进容器。
#
# spark.sql.hive.metastore.version    3.1.3
# spark.sql.hive.metastore.jars       maven
# spark.sql.hive.metastore.jars       path
# spark.sql.hive.metastore.jars.path  file:///opt/hive-jars/3.1.3/*.jar

# ============================================================
# 2) 存储格式与压缩
# ============================================================
spark.sql.sources.default         parquet
# Spark 的 ORC 默认压缩本来就是 snappy，这里显式写出便于阅读
spark.sql.orc.compression.codec   snappy

# ============================================================
# 3) 执行与并行度（E1–E5 的实验基准）
# ============================================================
spark.sql.adaptive.enabled            true
spark.sql.adaptive.skewJoin.enabled   true
spark.sql.shuffle.partitions      20

# ============================================================
# 4) 时区（批流对账要靠它，见第 19 步）
# ============================================================
spark.sql.session.timeZone        Asia/Shanghai
```

> 💡 **关于 `jars=maven`（本机实测的坑）**：它会走 **Ivy 首次解析**，
> 实测在容器里跑 **7 分钟仍未完成**；而且 Ivy 缓存落在容器**可写层** `/root/.ivy2`，
> **容器一重建就没了**。所以：
> - 先用**内置 client**（什么都不配）把环境跑通 —— 实测可用；
> - 需要版本严格对齐时，用 `jars=path` + 宿主机预下载 jar（可复现、不依赖首次联网）：
>   ```properties
>   spark.sql.hive.metastore.jars        path
>   spark.sql.hive.metastore.jars.path   file:///opt/hive-jars/3.1.3/*.jar
>   ```
> - 坚持用 `maven` 的话，**必须给 `/root/.ivy2` 挂一个命名卷**，否则每次重建容器都要重下。

## §6 写 compose 文件（逐段解释）

**`07_bigdata/docker-compose-bigdata.yml`**（复制时**不要改注释**，它们解释了每个字段的用意）：

```yaml
services:
  # ============================================================
  # ① 元数据库：给 Hive Metastore 存"目录卡片"
  #    注意：它和阶段二的 credit-dwh-mysql 是两个独立的库
  # ============================================================
  metastore-db:
    image: ${METASTORE_DB_IMAGE:-mysql:8.4}
    container_name: bd-metastore-db
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: root123456     # 学习环境，可写明文；生产必须用 secret
      MYSQL_DATABASE: metastore           # 库名就叫 metastore
      TZ: Asia/Shanghai                   # 时区统一，避免日志时间看不懂
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
    volumes:
      - metastore_db:/var/lib/mysql       # ⭐ 元数据落在这个卷里，删容器不丢
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-proot123456"]
      interval: 10s
      timeout: 5s
      retries: 10
    # 注意：没有 ports —— 元数据库只需要被 Metastore 访问，不必暴露给宿主机

  # ============================================================
  # ② Hive Metastore：只提供元数据服务，不做计算
  # ============================================================
  metastore:
    image: ${HIVE_IMAGE:-apache/hive:3.1.3}
    container_name: bd-metastore
    restart: unless-stopped
    # ⭐⭐ 必须加这一行（实配时踩出来的坑）：
    #   镜像默认以 uid=1000(hive) 运行，而命名卷目录属主是 root:root，
    #   于是 HMS 建库时无法创建目录，报：
    #     MetaException(message:Unable to create database path
    #                   file:/opt/spark/warehouse/credit_dwh_lc.db ...)
    #   —— 报错看着像元数据问题，实际是文件权限。
    user: root
    environment:
      SERVICE_NAME: metastore             # 只起 metastore 服务（镜像还支持 hiveserver2）
      DB_DRIVER: mysql                    # 告诉 schematool 用 mysql 方言
      HIVE_CUSTOM_CONF_DIR: /hive_custom_conf   # 这个目录里的文件会被当配置读
      # ⚠️ 光设 DB_DRIVER 不够：JDO 四个参数必须通过 SERVICE_OPTS 传进去
      SERVICE_OPTS: >-
        -Djavax.jdo.option.ConnectionDriverName=com.mysql.cj.jdbc.Driver
        -Djavax.jdo.option.ConnectionURL=jdbc:mysql://metastore-db:3306/metastore?createDatabaseIfNotExist=true&useSSL=false&allowPublicKeyRetrieval=true
        -Djavax.jdo.option.ConnectionUserName=root
        -Djavax.jdo.option.ConnectionPassword=root123456
      # 全新安装首次设 "false"（让它建 METASTORE 自己的表）；
      # ⭐ 之后每次重建容器都要改成 "true"，否则 schematool 会重复初始化而报错。
      # （SKIP_SCHEMA_INIT 是内部变量，由 IS_RESUME 覆盖，设了没用）
      IS_RESUME: "true"
    ports:
      - "9083:9083"                       # thrift 端口，Spark 靠它连
    depends_on:
      metastore-db:
        condition: service_healthy        # 等元数据库健康再起
    volumes:
      # ⭐⭐ 与 spark 挂同一个卷、同一个路径（原因见 §1.3）
      - spark_warehouse:/opt/spark/warehouse
      - ./conf/hive-site.xml:/hive_custom_conf/hive-site.xml:ro
      # ⚠️ 必须挂 JDBC 驱动，镜像不自带
      - ./jars/mysql-connector-j-8.0.33.jar:/opt/hive/lib/mysql-connector-j-8.0.33.jar:ro

  # ============================================================
  # ③ Spark Master：接活、派活
  # ============================================================
  spark:
    image: ${SPARK_IMAGE:-apache/spark:3.5.9-scala2.12-java11-python3-r-ubuntu}
    container_name: bd-spark
    restart: unless-stopped
    user: root                            # 官方镜像默认非 root，挂载卷写不进去
    command: >
      bash -c "/opt/spark/sbin/start-master.sh"
    environment:
      SPARK_NO_DAEMONIZE: "true"          # ⭐ 关键：让 master 留在前台，否则容器立刻退出
      SPARK_MASTER_HOST: spark            # ⭐ 让 worker 用服务名找回 master（别让它自己猜 IP）
      SPARK_MASTER_PORT: "7077"
      SPARK_MASTER_WEBUI_PORT: "8080"
      TZ: Asia/Shanghai
    ports:
      - "8080:8080"                       # Master Web UI（浏览器看）
      - "7077:7077"                       # 提交作业用
      - "4040:4040"                       # 作业运行时的 Application UI
    volumes:
      # ⭐ 挂项目根目录：容器内 /workspace/07_bigdata/... 与 /workspace/08_benchmark/... 都成立
      - ../:/workspace
      - spark_warehouse:/opt/spark/warehouse
      - ./conf/spark-defaults.conf:/opt/spark/conf/spark-defaults.conf:ro
      - ./conf/hive-site.xml:/opt/spark/conf/hive-site.xml:ro
    cpus: "4"                             # ⭐ 限制资源：E5 选型结论要能对账（见 §6.1）
    mem_limit: 4g                         # ⚠️ Docker VM 只有 7–8 GB 时改成 2 / 1500m（见 §6.1）

  # ============================================================
  # ④ Spark Worker：真正干活的
  # ============================================================
  spark-worker:
    image: ${SPARK_IMAGE:-apache/spark:3.5.9-scala2.12-java11-python3-r-ubuntu}
    container_name: bd-spark-worker
    restart: unless-stopped
    user: root
    command: >
      bash -c "/opt/spark/sbin/start-worker.sh spark://spark:7077"
    environment:
      SPARK_NO_DAEMONIZE: "true"
      SPARK_WORKER_CORES: "6"             # worker 向 master 申报自己有几个核
      SPARK_WORKER_MEMORY: "3g"           # ⚠️ Docker VM 只有 7–8 GB 时改成 4 / 2g（见 §6.1）
      SPARK_WORKER_WEBUI_PORT: "8081"     # 注意：不映射到宿主机，避免和 Flink 的 8081 冲突
      TZ: Asia/Shanghai
    depends_on:
      - spark
    volumes:
      - ../:/workspace
      - spark_warehouse:/opt/spark/warehouse
      - ./conf/spark-defaults.conf:/opt/spark/conf/spark-defaults.conf:ro
      - ./conf/hive-site.xml:/opt/spark/conf/hive-site.xml:ro
    cpus: "6"
    mem_limit: 5g

# ============================================================
# 卷：容器删了它们还在（数据能活下来的原因）
# ============================================================
volumes:
  metastore_db:        # Hive 的元数据（mysql 数据目录）
  spark_warehouse:     # Hive 表的数据文件（ORC/Parquet），两个容器共享
```

### 6.1 为什么一定要写 `cpus` 和 `mem_limit`

E5 要做"MySQL vs Spark 谁快"的对比。如果容器不限制资源，
Docker Desktop 默认会让它们**共享宿主机全部 28 核** ——
那你测出来的就不是"引擎差异"，而是"资源差异"，**结论直接作废**。

限制之后，你才能理直气壮地说：
"MySQL 我给了 X 核，Spark 我给了 Y 核，两边可比。"
（`docker stats --no-stream` 也能对上账。）

#### ⭐ 如果你的 Docker 虚拟机内存只有 7–8 GB（本机就是这样）

**关键认知：宿主机的内存 ≠ Docker 虚拟机能用的内存。**
本机实测：宿主机 **15.8 GB**，而 Docker Desktop 虚拟机只拿到 **7.64 GB**。
而宿主机当时只剩 6.2 GB 空闲 —— **把 Docker 调到 12 GB 会让 Windows 自己开始换页**，
所以正确做法不是"改 Docker 设置"，而是**把阶段三缩容**：

| 项 | 指导书默认 | 缩容版（本机实配） |
|---|---|---|
| `SPARK_WORKER_MEMORY` / `mem_limit` | 3g / 5g | **2g / 2800m** |
| `SPARK_WORKER_CORES` / `cpus` | 6 / 6 | **4 / 4** |
| Spark master | — / 4g | **2 cpus / 1500m** |
| Metastore / 元数据库 | 1.5g / 1g | **1500m / 1g** |
| driver / executor memory | 不显式设置 | **1500m / 2g**（显式写死，避免默认 1g driver 在大 shuffle 时 OOM） |

实测空转合计约 **1.86 GB**（4 个容器），余量充足：

```
bd-metastore       MEM 504.3 MiB / 1.465 GiB
bd-spark-worker    MEM 209.3 MiB / 2.734 GiB
bd-spark           MEM 279.0 MiB / 1.465 GiB
bd-metastore-db    MEM 491.3 MiB / 1 GiB
```

> ⚠️ **配套纪律**：跑 E1–E5 的重任务前先 `docker stop credit-dwh-mysql` 腾内存
> （第 13 步导出 TSV 时需要它，导完就可以停）。
>
> 🔑 **为什么缩容而不是降级到 L2（单容器 + Derby）**：
> 五个实验考察的是**分区裁剪、文件布局、列存编码、shuffle 分布、引擎开销** ——
> 这些与"内存给了多少"无关；而**外部 Hive Metastore 是架构认知的核心**，
> 值得保住。**降容不降架构**，这才是正确的取舍。

### 6.2 三个新手最容易写错的字段

| 字段 | 错误写法 | 后果 | 正确写法 |
|---|---|---|---|
| 项目根挂载 | `./:/workspace`（compose 在 `07_bigdata/` 时） | 容器里 `/workspace/07_bigdata/...` 找不到文件 | **`../:/workspace`** |
| 卷的路径 | 两个容器挂同一卷但**路径不同** | 表建了却读不到（§1.3） | 两边都写 `/opt/spark/warehouse` |
| `SPARK_NO_DAEMONIZE` | 不写 | 容器起来就退出（看起来像"启动失败"） | `"true"` |
| **Metastore 的 `user`** | 不写（默认 hive 用户） | ⭐ 建库报 `Unable to create database path ...`（文件权限） | **`user: root`** |

### 7.4 验收第 3 层：Metastore 在监听 9083 吗

**这是整个环境最关键的一个信号** —— 建表失败时，第一个要查的就是它。

```powershell
# 看日志有没有 ERROR / Exception / 是否已启动
docker logs bd-metastore 2>&1 | Select-String -Pattern "Starting Hive Metastore|ERROR|Exception" |
  Select-Object -Last 10
# 期望能看到：Starting Hive Metastore Server
# ⚠️ 日志里 SLF4J / log4j 的告警是噪音，不算 ERROR（过滤一下再看）

# ⭐⭐ 确认 9083 在监听：不要用 ss / netstat！
#    apache/hive 镜像里**两个都没装**，命令会直接输出 NOT LISTENING —— 是**假阴性**，
#    会让你在"明明已经起来了"上白查半天。
# 方式一（最直观）：宿主侧真实 TCP 连接（端口已发布到宿主）
try { $c = New-Object Net.Sockets.TcpClient; $c.Connect('127.0.0.1',9083); "9083 OK"; $c.Close() }
catch { "9083 FAIL: $($_.Exception.Message)" }

# 方式二（不依赖任何工具）：直接读 /proc/net/tcp
#   9083 = 0x237B；最后一列状态 0A = LISTEN
docker exec bd-metastore grep -i 237B /proc/net/tcp
docker exec bd-metastore grep -i 237B /proc/net/tcp6   # ⭐ 别漏 tcp6，本机就落在 v6 表里
```

> ⚠️ **首次启动要等 1–3 分钟**（它要先初始化 schema），别刚起来就建表然后怪它不行。
> 💡 顺手确认 schema 已初始化（应有几十张表）：
> ```powershell
> docker exec bd-metastore-db mysql -uroot -proot123456 -N -e `
>   "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='metastore';"
> # 本机实测：74
> ```

**常见报错与含义**：

| 报错 | 含义 | 怎么办 |
|---|---|---|
| `ClassNotFoundException: com.mysql.cj.jdbc.Driver` | JDBC 驱动没挂进去 | 检查 `07_bigdata/jars/` 里的文件是否存在、compose 里的挂载路径是否对得上 |

| 什么都不报，但 9083 没监听 | 容器还在初始化 / 内存不足 | 等 1–3 分钟；看完整日志 `docker logs bd-metastore` |

> 其实 **`docker compose` 是支持直接写的**，这里只是给你一个更保险的写法。

### 10.2 改了配置之后，怎么让改动生效

| 改了什么 | 要做什么 | 会丢数据吗 |
|---|---|---|
| `conf/spark-defaults.conf`（只读挂载） | 重启 Spark 相关容器：`docker compose ... restart spark spark-worker` | ❌ |
| `conf/hive-site.xml` | 重启 metastore 与 spark | ❌ |
| `.env`（换镜像 tag） | `docker compose ... up -d`（会重建变化的容器） | ❌（卷还在） |
| `docker-compose-bigdata.yml` 里加了服务 | `docker compose ... up -d` | ❌ |
| **换了 Metastore 的镜像版本** | ⚠️ `down`（**不带 -v**）→ **删 `metastore_db` 卷** → `up -d` | ✅ **元数据会清空**，要重跑建库建表 |

> 🚨 **最后一条特别提醒**：换 Metastore 大版本时，**旧 schema 会带来一串更难查的报错**，
> 所以必须清空元数据。这不是数据丢了（ORC 文件还在卷里），
> 但你要重新执行一遍 `01_ddl.sql` 与导入 —— **所以换版本之前先想清楚**。

### 10.3 启动顺序有讲究吗

`depends_on` 已经处理了大部分顺序（元数据库 → Metastore → Spark → Worker）。


### 10.4 什么时候该清理（省磁盘）

```powershell
docker system df                        # 看谁在占空间
docker image prune -a                   # 删没被使用的镜像（⚠️ 下次要重新拉）
```

## §11 常见报错急救

> 按**报错原文**索引。看到相似的报错，先跳到对应行。

### 11.1 Docker 层面

| 报错原文（关键片段） | 原因 | 修复 |
|---|---|---|
| `open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified` | Docker Desktop 没启动 | 启动它，等托盘变绿 |
| `error during connect: ... This error may indicate that the docker daemon is not running` | 同上 | 同上 |
| `port is already allocated` | 端口被占用（常见：9083/8080 被别的服务占） | `netstat -ano \| findstr :9080` 找出占用进程；或改 compose 里的宿主端口 |
| `manifest unknown` / `pull access denied` | 镜像 tag 不存在（比如用了已下架的 bitnami tag） | 回 §5.1 预检，换官方镜像 |
| `no space left on device` | 磁盘满了 | 按 §10.4 清理；确认 Docker 数据盘剩余 ≥ 30 GB |
| `error while creating mount source path ... file exists` | 绑定挂载的源可能是个文件而非目录 | 检查 `07_bigdata/conf/` 下的文件名是否与你写的一致 |

### 11.2 Spark 层面

| 报错原文 | 原因 | 修复 |
|---|---|---|
| 容器 `Exited (0)`，日志很短 | `SPARK_NO_DAEMONIZE` 没设或没生效 | 设 `"true"`，或把 command 改成 `bash -c "... && tail -f /dev/null"` |
| `No such file or directory: /workspace/07_bigdata/...` | 用了 Windows 路径，或挂载点不对（`./` vs `../`） | 容器内一律用 `/workspace/...`；确认挂的是**项目根**（§2.2） |
| `Table or view not found: credit_dwh_lc.xxx` | 元数据没连上（其实在用 Derby），或你没 `USE` 那个库 | 查 `spark.hadoop.hive.metastore.uris`；SQL 里先 `USE credit_dwh_lc` 或写全名 |
| `Unsupported Hive Metastore version` | `spark.sql.hive.metastore.version` 写了不支持的版本 | 写 `3.1.3`（Spark 3.5 只支持到 3.1.3） |
| `TApplicationException: Invalid method name: 'get_table'` | ⭐ 给 Spark 3.5 配了 **Hive Metastore 4.0.x** | 换成 `apache/hive:3.1.3`（Hive 4.0.1 移除了那个 thrift 方法） |
| `INSERT OVERWRITE ... PARTITION` 把整表清空了 | `partitionOverwriteMode` 默认是 STATIC | SQL 里加 `SET spark.sql.sources.partitionOverwriteMode=dynamic;` 与 `SET hive.exec.dynamic.partition.mode=nonstrict;` |
| `java.lang.OutOfMemoryError: Java heap space` | worker 内存不够（4471 万行快照最容易撞） | 提高 `SPARK_WORKER_MEMORY` / `mem_limit`；给 Docker Desktop 加内存；或缩小范围先跑通 |

### 11.3 Hive Metastore 层面

| 报错原文 | 原因 | 修复 |
|---|---|---|
| `ClassNotFoundException: com.mysql.cj.jdbc.Driver` | JDBC 驱动没挂 | 确认 `07_bigdata/jars/` 有 jar，且 compose 挂载路径一致 |
| ⭐⭐ `MetaException(message:Unable to create database path file:/opt/spark/warehouse/xxx.db, failed to create database xxx)` | **文件权限**：Metastore 默认以 `uid=1000(hive)` 运行，而卷目录属主是 `root:root`，建库时创建不了目录。**看着像元数据问题，实际是权限** | 给 `metastore` 服务加 **`user: root`**（或把卷目录 chown 给 1000:1000） |
| `Table 'metastore.BUCKETING_COLS' doesn't exist` | schema 没初始化 | 全新安装首次设 `IS_RESUME: "false"`；**之后重建容器改 `"true"`** |
| `Communications link failure` / `Connection refused`（Metastore → MySQL） | 元数据库没起来，或服务名写错 | `docker inspect bd-metastore-db --format '{{.State.Health.Status}}'`；URL 里应是 `metastore-db:3306` |
| Metastore 起来了，但建表后 `SELECT` 读不到数据 | ⭐ 两个容器挂的**不是同一个卷/路径** | 两边都必须 `spark_warehouse:/opt/spark/warehouse` |
| ⭐ 日志已有 `Starting Hive Metastore Server`，但 `ss -tlnp \| grep 9083` 显示 `NOT LISTENING` | **镜像里没装 `ss`/`netstat`** —— 是"工具不存在"，不是"端口没监听"（假阴性） | 用宿主侧 `TcpClient` 连 127.0.0.1:9083，或 `grep -i 237B /proc/net/tcp` **与 tcp6**（见 §7.4） |

### 11.4 Windows / PowerShell 层面

| 报错原文 | 原因 | 修复 |
|---|---|---|
| `ParserError: The string is missing the terminator: "` | `.ps1` 是 UTF-8 **无 BOM**，Windows PowerShell 5.1 按 GBK 读，中文把引号搞坏了 | **脚本内只用 ASCII**（本项目的一贯做法），或存成 UTF-8 with BOM |
| `UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'` | 控制台编码是 GBK，打印 ✅ 就炸 | 用 venv 的 Python（`src/utils.py` 导入时已自动改成 UTF-8）；或先 `$env:PYTHONIOENCODING='utf-8'` |
| `bash: /workspace/xxx.sh: /bin/bash^M: bad interpreter` | `.sh` 被存成了 CRLF | 存成 LF；或仓库里加 `.gitattributes`：`*.sh text eol=lf` |
| 重定向出来的文件乱码 | PowerShell 5.1 的 `>` 默认写 UTF-16 | 用 Python 写文件（本项目导出 TSV 就是这么做的），或 `Out-File -Encoding utf8` |

## §12 环境搞不定时的降级阶梯

**规则：环境总耗时超过 8 小时，立刻降一级。** 不要优化环境，要保住实验。

| 级别 | 方案 | 放弃什么 | 还能做什么 |
|---|---|---|---|
| **L0（推荐）** | 官方镜像 + 外部 Hive Metastore + Spark 集群 | 无 | 第 12–20 步全部 |
| **L1** | **自建 Spark 镜像**（Dockerfile 从官方 tar 包构建） | 无（只是镜像来源不同） | 同上 |
| **L2** | **单容器 + 内嵌 Derby**，`local[*]` 模式 | "元数据服务独立"、"分布式执行" | ⭐ **E1–E5 全部照做**（分区表/ORC/倾斜/基准都在） |
| **L3** | **不用 Docker**：宿主 `pip install pyspark` + Java 17，`local[8]` | 容器化/Linux 那条线 | 同样能完成 E1–E5（第 19 步实时链路砍掉） |

**L2 的关键细节**（否则容器一重建表就没了）：把 Derby 元数据与仓库目录
都放到**绑定挂载的项目目录**里：

```properties
spark.sql.catalogImplementation  hive
spark.sql.warehouse.dir          /workspace/07_bigdata/warehouse
spark.driver.extraJavaOptions    -Dderby.system.home=/workspace/07_bigdata/derby
```

> 🔑 **为什么降级不可耻**：我们的五个实验考察的是
> **分区裁剪、文件布局、列存编码、shuffle 分布、引擎开销** ——
> 这些性质**由引擎与存储格式决定，与"元数据服务是否独立部署"无关**。
> 降级损失的只是"三层分离"的架构体验，**实验结论一条都不受影响**。
