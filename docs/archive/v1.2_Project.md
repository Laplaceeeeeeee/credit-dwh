### 〇.2 🚨 本地数据实测修正（2026-09-12 补充，**必读**）

在编写配套指导书时，对你的 `data/accepted_2007_to_2018Q4.csv.gz` 做了实测核验。**发现 5 个会直接影响设计的事实**，已全部落入本文档与指导书：

| # | 实测发现 | 对设计的影响 | v1.1 的处理 |
|---|---|---|---|
| 1 | 文件**真实行数 2,260,700**（含 1 行页脚共 2,260,701），151 列 | ✅ 与公开口径一致，简历可放心写 226 万 | 简历数字**已改为实测值** |
| 2 | 最后一行是**页脚文本** `Total amount funded in policy code 2: ...`，非数据 | 不处理会产生 1 行脏数据，行数守恒校验失败 | 读取必须 `skipfooter=1, engine="python"` |
| 3 | **`member_id` 列整列为空**（2,260,700 行非空值 = 0） | ❌ **"客户维 + 一人多贷"的设计不成立** | **`dim_customer` 改为 `dim_applicant`**（申请人画像维，粒度 = 一笔贷款，主键 = `loan_id`） |
| 4 | **32 行记录 `issue_d` 与 `loan_status` 同时为空** | DWD 行数 ≠ ODS 行数，需登记差异 | DWD 标 `REJECT` 不写入；**行数守恒 = ODS 2,260,700 − 32 = DWD 2,260,668** |
| 5 | `loan_status` 完整分布已知：Fully Paid 1,076,751 / Current 878,317 / Charged Off 268,559 / … | 口径与预期不良率可直接校验 | **不良 = 269,360 笔；终态 = 1,348,099 笔；终态不良率 ≈ 19.98%**（若算出 ~11.9%，说明漏了 `is_terminal=1`） |

> ⚠️ **第 5 条特别重要**：878,317 笔 `Current`（占 38.85%）**仍在还款中**。
> 若不限定终态，不良率会被稀释到约 11.9% —— **这是信贷指标里最经典的口径错误**，也是面试的高频追问点。现在你有了一个可对照的预期值。

> ✅ **好消息**：`id` 列 2,260,700 行**完全唯一、无重复**，主键设计成立。

**关于 `member_id` 的面试话术（新增亮点）**：
> "这份数据的会员 ID 列整列为空，无法识别'同一客户的多笔贷款'。我**没有**用 `annual_inc + addr_state` 之类去拼一个伪客户 ID —— 那会造成错误关联、让客户级统计失真。
> 我把客户维降级为**申请人画像维**，粒度是一笔贷款，并在文档里写明'客户级分析与一人多贷不可做'。
> 这属于数据边界，不是实现缺陷 —— 我认为说清边界比硬凑一个维度更负责。"

## 一、开工前必须想清楚的六件事

### 1.1 这个项目到底在做什么（一句话）

> **把一份原始的信贷放款流水，加工成一套能回答"这笔贷款会不会逾期""哪批客户质量在恶化""风控策略改完有没有效果"的数据底座。**

**注意**：你做的是**数据工程/数仓**，不是机器学习建模。区别在于——
- ❌ 不是：训练一个模型预测违约（那是算法岗，你不投）
- ✅ 是：把数据**分层加工、建成指标、保证口径一致、能支撑分析**

面试官要看的是"你会不会建数仓、口径清不清楚"，而不是"你的 AUC 多少"。

### 1.4 ⭐ v1.1 新增：三条铁律升级为五条

| # | 铁律 | 原因 |
|---|---|---|
| 1 | **先跑通最小闭环，再优化** | 新手最大失败模式是"设计太完美，永远跑不起来" |
| 2 | **每一层都要能验证** | 数仓的核心是**数据可信**，不是代码漂亮 |

| 5 | 🆕 **每个产出物都要有数字** | "行数 X 万、耗时 Y 分、一致率 100%" —— 没有数字就没有说服力 |

### 1.5 ⚠️ 最重要的一条：避免"数据泄漏"

信贷数据里有个经典陷阱：**很多字段是"放款后才知道的"**（如已还期数、最后还款状态、回收金额）。

> **如果把这些字段当成"放款时的信息"使用，指标就完全错了。**

**做法**：在设计阶段就明确划分"申请时点信息" vs "表现期信息"，并在文档里写清楚（见 §3.3）。

这一条如果你能在面试中主动讲出来，**面试官会立刻判断你"懂业务"**——这是区分"学生项目"和"真实工程思维"的分水岭。

> ⚠️ **v1.1 提醒**：这个亮点在 v1.0 的简历段落里**完全没体现**，等于白做。v1.1 已把它写进简历模板（§7.2）。

### 1.6 🆕 第二条同等重要：认清数据的边界（v1.1 新增）

你下载的是 `accepted_2007_to_2018Q4.csv.gz` —— **只包含"已批准并放款"的贷款**。这带来三个必须承认的边界：

| 边界 | 后果 | 正确做法 |
|---|---|---|
| **无拒绝样本** | "批准率""通过率"**算不出来**（分母不存在） | **删除此类指标**，不写进简历 |
| **幸存者偏差** | 你观测的是"被批准的人"的表现，不代表全客群 | 在文档和面试中**主动说明影响范围** |
| **无政策/宏观数据** | 无法证明"逾期上升是因为策略放松" | 只陈述**数据内可验证**的结论（见 §6.2） |

> 🔑 **主动说出"我这份数据有什么做不到"，比编一个漂亮结论更能体现专业度。**
> 面试官听到"我识别到数据集仅含放款样本，因此剔除了批准率类指标" —— 这一句的含金量高于任何一张图。

## 三、第二步：数据探查与数仓设计（约 20 小时）

### 3.1 数据探查（EDA）要产出的东西

一份 **《数据探查报告》**（Markdown，4–6 页）：

| 板块 | 内容 |
|---|---|
| 数据概览 | 行数、列数、字段清单与含义 |
| 主键检查 | 是否有唯一键？是否重复？ |
| **字段分类** | 申请时点信息 / 表现期信息 / 标签（**为 §1.5 防泄漏做准备**） |
| 缺失值分布 | 每个字段缺失率，标出 >50% 的字段 |
| 取值分布 | 关键字段枚举值（如 `loan_status` 有哪些取值） |
| 异常值 | 金额为负、日期越界、年龄不合理等 |
| 时间跨度 | 最早/最晚放款日期，判断能否做趋势分析 |
| 🆕 **行数与体量实测** | 真实行数、裁剪后内存占用 —— 用于简历数字与引擎选择论证 |

**必查项（具体做法见指导书 §3）**：

```sql
-- ① 主键唯一性
SELECT id, COUNT(*) FROM ods_loan_raw GROUP BY id HAVING COUNT(*) > 1;

-- ② 关键字段枚举（决定你的指标口径）
SELECT loan_status, COUNT(*) FROM ods_loan_raw GROUP BY loan_status ORDER BY 2 DESC;

-- ③ 时间跨度
SELECT MIN(issue_d), MAX(issue_d) FROM ods_loan_raw;
```

> ⚠️ LendingClub 的 `loan_status` 取值很多（Fully Paid / Charged Off / Current / Late (31-120 days) / In Grace Period…）。
> **"什么算逾期"完全取决于你怎么归类这些取值**——这就是"口径"，面试必问。

✅ **产出物**：`01_eda/数据探查报告.md`

### 3.2 分层架构设计

```
┌─────────────────────────────────────────────────┐
│  ADS  应用层   ← 直接给分析/报表用的指标表        │
│        如：逾期率月报、Vintage 矩阵、迁徙率矩阵    │
├─────────────────────────────────────────────────┤
│  DWS  汇总层   ← 按主题做轻度汇总（宽表）          │
│        如：月末贷款快照表、客户级汇总、月度汇总     │
├─────────────────────────────────────────────────┤
│  DWD  明细层   ← 清洗后的明细，一行一业务事实      │
│        如：贷款事实表、客户维表、产品维表          │
├─────────────────────────────────────────────────┤
│  ODS  原始层   ← 原样落地，不做加工（便于回溯）    │
│        如：原始放款流水                            │
└─────────────────────────────────────────────────┘
```

| 层 | 存在意义 | 一句话解释（面试要能说） |
|---|---|---|
| **ODS** | 数据可回溯 | "原始数据原样保存，出问题时能查源头" |
| **DWD** | 清洗 + 规范化 | "统一口径、处理脏数据，形成一行一事实的明细" |
| **DWS** | 减少重复计算 | "按主题预汇总，避免每次分析都从明细算" |
| **ADS** | 面向应用 | "直接产出报表/看板需要的指标表" |

### 3.3 维度建模设计

**要设计的表（v1.1 修订版）**：

| 表类型 | 表名 | 说明 | 粒度 | v1.1 变化 |
|---|---|---|---|---|
| **事实表** | `dwd_loan_fact` | 贷款放款事实（**申请时点口径**） | 一行 = 一笔贷款 | — |
| **事实表** | `dwd_loan_perf_fact` | 贷款表现事实（**表现期末口径**） | 一行 = 一笔贷款的最新表现 | 🆕 与申请时点**物理分离**，从结构上杜绝泄漏 |
| **快照事实表** | `dws_loan_snapshot_m` | 月末贷款状态快照 | 一行 = 一笔贷款 × 一个观测月末 | 🔄 **替代 v1.0 的 SCD2 拉链表** |
| **维度表** | `dim_applicant` | 🆕 申请人画像维（年收入、地区、FICO 等申请时点属性） | 一行 = 一笔贷款 | 🔄 **替代 v1.0 的 `dim_customer`**（`member_id` 整列为空，无客户识别键） |
| **维度表** | `dim_product` | 产品维（期限、利率档、评级） | 一行 = 一个产品组合 | — |
| **维度表** | `dim_date` | 日期维（年月、季度、星期） | 一行 = 一天 | — |

**必须做的设计决策（面试会问）**：

| 决策点 | 你要给出的答案 |
|---|---|
| 星型 vs 雪花 | **星型**（维度不进一步范式化，查询更快、更易理解） |
| 事实表类型 | **事务事实表**（每笔贷款）+ 🆕 **周期快照事实表**（月末状态） |
| 是否要拉链表 | 🔄 **本项目用周期快照，不用 SCD2** —— 理由见 §3.4 |
| 分区策略 | 按 **放款月份** 分区（便于增量与历史回溯） |

### 3.4 🔄 v1.1 重大修订：用"月末快照事实表"替代 SCD2 拉链表

**v1.0 的做法及问题**：
> v1.0 要建 `dim_customer_scd2`，记录客户评级/收入的历史变化。但 LendingClub 是**单次快照数据**，`annual_inc`、`grade` 都是**放款时点值**，没有历史切片。你无法构造真实的"属性变更"序列，只能人为造假数据来演示 —— 一旦被问"你的 SCD2 数据从哪来的"，杀伤力极大（拉链表瞬间从"懂数仓"变成"背概念"）。

**v1.1 的做法：月末快照事实表（Periodic Snapshot Fact Table）**

| 字段 | 说明 |
|---|---|
| `loan_id` | 贷款 ID |
| `snapshot_month` | 观测月末（如 `2019-01`） |
| `mob` | 账龄 = 观测月 − 放款月 |
| `out_prncp` | 期末未偿本金 |
| `total_rec_prncp` | 累计已收本金 |
| `dpd_bucket` | 该观测月末的逾期档位 |
| `is_delinquent` | 该月末是否逾期（0/1） |

**为什么它更好（面试话术）**：

> "我原本打算做客户属性拉链表，但发现这份数据是**放款时点的静态快照**，不存在真实的属性变更序列，硬做出来是假的。
> 我改成了**月末快照事实表**：按 `放款月 − 观测月` 的差值计算账龄 MOB，记录每笔贷款在每个观测月末的未偿余额和逾期档位。
> 它同样是**周期快照事实表**这一标准数仓模式，同样解决'历史状态如何追踪'的问题，但**数据是真实的、可校验的** —— 而且它天然支撑了 Vintage 与迁徙率分析。"

**附加价值**：月末快照表是 **Vintage（§4.2）和迁徙率（§4.3）的计算基础**，比拉链表更贴业务。

> ✅ **保留 SCD2 知识**：面试若问"拉链表怎么做"，你依然要能答（见 §7.4 面试话术）。但**项目里不放假数据**。

### 3.5 关键字段设计（防泄漏的落地）

| 字段类别 | 代表字段 | 存放位置 | 使用规则 |
|---|---|---|---|
| **申请时点信息** | `issue_d`、`loan_amnt`、`term`、`int_rate`、`grade`、`purpose`、`annual_inc`、`emp_length`、`home_ownership` | `dwd_loan_fact` + 维表 | ✅ **可用于风险分层、客群分析** |

## 四、第三步：定义指标体系与口径（约 8 小时）—— ⭐ 银行最看重

### 4.1 指标口径表（v1.1 修订：删除批准率）

| # | 指标 | 定义 | 计算逻辑 | 备注 |
|---|---|---|---|---|
| 1 | **放款金额 / 笔数** | 统计期内成功放款的总额/笔数 | `SUM(loan_amnt)` / `COUNT(1)` | — |
| 2 | **不良率（逾期率）** | ⚠️ 必须明确"什么算不良" | `loan_status IN ('Charged Off','Default')` 计为不良 | 口径见 §4.4 |
| 3 | **逾期天数分档（DPD bucket）** | 按逾期天数分档 | Current / 1-30 / 31-60 / 61-90 / 90+ | — |
| 4 | **平均借款金额** | 总金额 / 笔数 | `SUM/COUNT` | — |
| 5 | **加权平均利率** | 按金额加权（**不是简单平均**） | `SUM(loan_amnt*int_rate)/SUM(loan_amnt)` | 面试常考"为什么加权" |
| 6 | **Vintage 逾期率** | ⭐ 按放款月份分组，看账龄 MOB 维度 | 见 §4.2 | 风控核心方法 |
| 7 | **迁徙率（Roll Rate）** | 从上期档位迁徙到下期档位的比例 | 见 §4.3 | — |
| 8 | 🆕 **期末未偿余额（EAD）** | 观测月末的未偿本金合计 | `SUM(out_prncp)` by 月末 | 银行核心口径之一 |
| ~~9~~ | ~~**批准率**~~ | ❌ **v1.1 删除** | 拒绝样本无关联键，分母不成立 | 见 §1.6 |

### 4.2 ⭐ Vintage 分析（风控核心方法）

**概念**：把**同一放款月份**的贷款作为一批（vintage），观察它们在**不同账龄（MOB, Month on Book）**下的表现。

**为什么要这么做**（面试必答）：
> 不同月份放款的政策不同、客群不同。**直接比较不同月份的总逾期率会误导**——因为老批次账龄长、暴露更充分。Vintage 分析把账龄对齐，才能公平比较"哪批客户质量更差"。

**表结构**：

| 放款月 | MOB1 逾期率 | MOB3 | MOB6 | MOB12 |
|---|---|---|---|---|
| 2018-01 | 0.8% | 1.5% | 2.3% | 3.1% |
| 2018-02 | 0.9% | 1.8% | … | … |

**计算思路**：
```
账龄 MOB = 观测月 − 放款月
按 放款月 + MOB 分组，统计该组内不良笔数 / 总笔数
在 dws_loan_snapshot_m 上做（每月快照 → 可精确算每个 MOB 的逾期状态）
```

### 4.3 迁徙率分析（Roll Rate）

**概念**：本期处于某档位的贷款，下期迁徙到各档位的比例。

| 期初档位 | → Current | → 1-30 | → 31-60 | → 核销 |
|---|---|---|---|---|
| Current | 95% | 4% | 0.8% | 0.2% |
| 1-30 | 60% | 25% | 12% | 3% |
| 31-60 | 30% | 20% | 35% | 15% |

**用途**：预测未来不良、评估催收效果。

**实现要点**：在 `dws_loan_snapshot_m` 上做**自关联（self-join）**，连接条件为 `本月.loan_id = 下月.loan_id AND 下月.snapshot_month = 本月.snapshot_month + 1个月`。

> ⚠️ **诚实提醒**：迁徙率严格意义上需要**逐月**的逾期状态。LendingClub 的 `loan_status` 只是**单一最终状态**，无法还原真实的历史逐月迁徙。**v1.1 的正确做法**：
> - 方案 A（推荐）：基于 `snapshot_month` 用**规则推导**状态（如按 `last_pymnt_d` 距今月数推算 DPD 档位），并在文档中**明确标注为"规则推导，非原始逐月状态"**
> - 方案 B：只做"最终状态分布迁移"（放款时 `grade` 档 → 最终 `loan_status`），更保守但 100% 真实
>
> 🔑 **主动标注推导假设 = 加分；假装有逐月数据 = 减分。**

|--------|---------|---------|-----------|---------|--------|

### 5.4 增量加工（阶段二就用 SQL 实现，不等 Hive）

**为什么在阶段二做**：这是面试必问"全量 vs 增量"，而**逻辑与引擎无关** —— 用 MySQL 分区表一样能讲清楚。

| 概念 | 落地方式（阶段二） |
|---|---|
| **分区** | MySQL 按 `issue_month` 做**分区表**（或至少建索引 + 分区键列）；若用 PostgreSQL 用原生分区 |
| **增量识别** | 以 `issue_d` 为水位（watermark）：只处理 `issue_d > 上次水位` 的数据 |
| **水位管理** | 建 `etl_watermark` 表记录每次跑的 `max(issue_d)` 与时间戳 |
| **幂等** | 重跑同一天不产生重复数据（先删后插 / `UPSERT` / `MERGE`） |
| **回补（backfill）** | 支持指定 `biz_date` 重跑历史分区 |

**面试话术**：
> "我把 ODS→DWD 做成按放款月分区的增量加工，用水位表记录上次处理到哪个月，重跑时先按分区删除再插入保证幂等。全量重跑一次约 X 分钟，增量只需 Y 秒（当月数据量小）。"

### 5.5 数据质量校验（代码化，不只是文档）

v1.0 把校验规则写在文档里 —— **v1.1 要求写成可执行的断言脚本**。

| 校验项 | 规则 | 实现方式 | 严重级别 |
|---|---|---|---|
| **行数守恒** | ODS 行数 ≥ DWD 行数（差值需能解释） | 计数比对 + 差异原因登记 | ERROR |
| **主键唯一** | `dwd_loan_fact.id` 唯一 | `GROUP BY ... HAVING COUNT(*)>1` = 0 | ERROR |
| **汇总一致性** ⭐ | DWS/ADS 汇总值 = DWD 明细重算值 | 双向重算比对 | ERROR |
| **金额非负** | `loan_amnt >= 0` | 条件计数 = 0 | ERROR |
| **枚举合法** | `loan_status` 在允许集合内 | `NOT IN (...)` 计数 = 0 | ERROR |
| **时间合理** | `issue_d <= 当前日期` | 条件计数 = 0 | WARN |
| 🆕 **分区完整性** | 每个放款月分区都有数据，无空洞 | 月份序列比对 | WARN |
| 🆕 **无未来信息** ⭐ | `dwd_loan_fact` 中**不含**任何表现期字段 | **字段名黑名单校验** | ERROR |

> 🔑 **最后一条是 v1.1 的杀手锏**：用**自动化校验**保证"申请时点表里不可能混进表现期字段"。面试时讲出来，等于告诉面试官"我把数据治理做成了机制，不是靠自觉"。

### 6.3 常见技术坑与解法

| 坑 | 症状 | 解法 |
|---|---|---|
| **内存不足** | 读 374MB gz 时进程被杀 | 分块读取（`chunksize`）或先裁剪列；只保留需要的 ~40 列 |
| **日期格式混乱** | `issue_d` 是 `"Dec-2018"` | **显式指定格式** `%b-%Y` 解析，不靠自动推断 |
| **利率是字符串** | `"13.56%"` 无法计算 | 去 `%` 转 float |
| **缺失值策略不清** | 到处填 0 导致指标失真 | **按字段分别决策并在文档记录** |
| **JOIN 后行数变多** | 维表有重复键 | JOIN 前检查维表主键唯一性 |
| **口径前后不一** | 不同脚本算法不同 | **统一从口径字典取定义** |
| 🆕 **时区/月份边界** | 月末快照跨月错位 | 统一用 `date` 类型 + 自然月，禁止用"30天"近似 |
| 🆕 **中文字符集** | MySQL 存中文乱码 | 建库建表统一 `utf8mb4` |

### 8.4 ⭐ 数据倾斜实验（E4）的完整设计

**为什么要专门做一个实验**：数据倾斜是 Hive/Spark 面试的**第一高频追问**，而 90% 的候选人只能背概念（"加盐打散、两阶段聚合"），没有数字。你要有数字。

**四步实验法**：

| 步骤 | 做什么 | 产出 |
|---|---|---|
| **1. 先量化倾斜** | 统计 key 分布，找出最大 key 的占比 | "最大 key 占 X%，是均匀分布的 Y 倍" |
| **2. 复现问题** | 不加处理直接跑，记录 task 耗时分布 | "最长 task 是平均的 Z 倍，总耗时 T1" |
| **3. 加盐处理** | 加随机后缀 → 局部聚合 → 去盐 → 全局聚合，桶数取 5/10/20 各跑一遍 | 耗时曲线：T1 > T(5) > T(10) ? T(20) |
| **4. 找最优点** | 分析"桶数增加→局部聚合开销增加"与"倾斜缓解"的权衡点 | "10 桶最优，因为并行度/数据量的比值是……" |

**本项目可用的天然倾斜 key**（基于实测数据分布）：

| 候选 key | 分布情况 | 倾斜程度 | 适用实验 |
|---|---|---|---|
| `loan_status` | Fully Paid 47.6% / Current 38.9% | **极高**（前 2 个值占 86%） | ⭐ **首选，天然 2-3 个超级热点** |
| `grade` | 7 个值，A–G | 中等 | 适合演示 group-by 倾斜 |
| `issue_month` | 约 140 个月份 | 低 | 更适合做分区裁剪实验 |
| `purpose` | 14 个值 | 中等 | 备选 |

> 🔑 **`loan_status` 是最好的实验对象**：它的取值分布天然就是"两个超级 key + 一长串小 key"，
> 这正是数据倾斜的教科书形态。你不需要造数据，**真实数据本身就倾斜** —— 这个事实讲出来很有说服力。

**加盐两阶段聚合的 SQL 骨架**（详细实现见指导书第 14 步）：

```sql
-- 第一阶段：加盐做局部聚合（salt 取 0..N-1）
WITH salted AS (
  SELECT
    CONCAT(loan_status, '_', CAST(FLOOR(RAND() * 10) AS INT)) AS salted_key,
    loan_status,
    loan_amnt,
    is_bad
  FROM dwd_loan_fact_lc f
  JOIN dwd_loan_perf_fact_lc p ON f.loan_id = p.loan_id
),
stage1 AS (
  SELECT salted_key, loan_status,
         COUNT(*) AS cnt, SUM(is_bad) AS bad_cnt
  FROM salted GROUP BY salted_key, loan_status
)
-- 第二阶段：去盐做全局聚合
SELECT loan_status,
       SUM(cnt) AS cnt,
       SUM(bad_cnt) AS bad_cnt,
       ROUND(SUM(bad_cnt) / SUM(cnt), 6) AS bad_rate
FROM stage1
GROUP BY loan_status;
```

**必须验证**：加盐前后的结果**完全一致**（这是实验有效性的前提，也是口径一致性的证明）。

### 8.5 主线 B：实时数仓设计（Kafka + Flink + CDC）

#### 8.5.1 先明确一个诚实的边界

**本项目没有真实的实时数据源。** LendingClub 是 2007–2018 的历史离线数据，不存在流。

因此实时链路的设计**必须诚实**，否则面试一问就穿。正确的做法是把实时链路定位为：

> **"用真实历史数据回放（replay）模拟实时场景，验证批流一体的架构与口径一致性。"**

这句话好在三点：**说了实话、体现了架构能力、避免了"我做了个假项目"的质疑**。

#### 8.5.2 两条实时链路的选型（建议都做，成本不高）

| 链路 | 源 | 通道 | 计算 | 目标 | 演示什么 |
|---|---|---|---|---|---|
| **链路 1：CDC 同步**（真实感更强） | MySQL（阶段二产出） | Debezium → Kafka | — | Kafka → MySQL/Doris | 数据库变更实时捕获，是**银行做增量同步的主流方案** |
| **链路 2：事件流计算** | 放款事件回放脚本 | Kafka | Flink | MySQL/Doris | 实时指标计算、窗口聚合、状态管理 |

> 🔑 **链路 1 的价值高于链路 2**。因为银行/券商数据岗的真实日常就是"把核心系统的数据实时同步到数仓/数据湖"，
> 而 Debezium CDC + Kafka 正是这个场景的标准答案。**能讲清 CDC 的 exactly-once 与幂等写入，比会写 Flink 窗口算子更值钱。**

#### 8.5.3 实时指标设计（与离线口径严格对齐）

| 实时指标 | 窗口 | 与离线的关系 |
|---|---|---|
| 当日放款笔数/金额 | 滚动 1 天 | 与 ADS 日粒度对齐 |
| 当日各评级放款占比 | 滚动 1 天 | 与 `ads_risk_segment` 对齐 |
| 近 5 分钟放款速率 | 滑动 5 分钟 / 1 分钟 | 纯实时新增，离线无对应 |

**Flink 侧要覆盖的技术点**（面试会逐个问）：

| 技术点 | 说明 | 面试追问 |
|---|---|---|
| **时间语义** | Event Time vs Processing Time | 为什么用 Event Time？ |
| **Watermark** | 处理乱序数据 | 水位线设多少？延迟数据怎么办？ |
| **窗口** | 滚动/滑动/会话窗口 | 为什么用滚动不用滑动？ |
| **状态管理** | KeyedState / 状态后端 | 状态多大？怎么做 checkpoint？ |
| **Exactly-Once** | Checkpoint + 两阶段提交 | 端到端精确一次怎么保证？ |
| **幂等写入** | 主键 UPSERT | 重复消费怎么不重复计数？ |
| **背压** | Backpressure 监控 | 消费跟不上生产怎么办？ |

> ⚠️ **不要试图把上面 7 点全部做出来。** 选 **3 个**做扎实（建议：Event Time + Watermark、窗口、幂等写入），
> 其余能讲清原理即可。**做 3 个能答细节的，胜过做 7 个只会名词的。**

#### 8.5.4 ⭐ 批流对账（本主线最有价值的产出）

**做什么**：同一天的放款笔数/金额，离线链路算一遍、实时链路算一遍，**逐日比对差异**。

**为什么这是加分项**：
> 跨链路口径一致性是数据治理的深水区。大多数候选人做离线就只做离线、做实时就只做实时，
> **很少有人会去验证两条链路算出的数字是否一样** —— 而这恰恰是真实生产环境最容易出事故的地方。

**对账规则设计**：

| 检查 | 规则 | 容忍度 | 不一致时的排查方向 |
|---|---|---|---|
| 笔数一致 | `abs(离线 - 实时) = 0` | 0 笔 | 重复消费、漏消费 |
| 金额一致 | 差异率 < 0.01% | 浮点误差 | 精度类型（DECIMAL vs DOUBLE） |
| 时区/日界 | 同一天的定义一致 | 必须一致 | UTC vs 北京时间 —— **这是最常见的坑** |
| 迟到数据 | T+1 重算后差异收敛 | 观察 1 个周期 | Watermark 设置过小 |

**产出**：`批流一致性对账报告.md`，含差异趋势图与每条差异的归因。
