## 零、开工前必须想清楚的五件事

### 0.1 这个项目到底在做什么（一句话）

> **把一份原始的信贷放款流水，加工成一套能回答"这笔贷款会不会逾期""哪批客户质量在恶化""风控策略改完有没有效果"的数据底座。**

**注意**：你做的是**数据工程/数仓**，不是机器学习建模。区别在于——
- ❌ 不是：训练一个模型预测违约（那是算法岗，你不投）
- ✅ 是：把数据**分层加工、建成指标、保证口径一致、能支撑分析**

这个区分很重要，因为你面试的是**数据开发岗**，面试官要看的是"你会不会建数仓、口径清不清楚"，而不是"你的 AUC 多少"。

### 0.2 为什么必须选信贷方向

**同样的工作量，但一个是练习、一个是履历。**

### 0.4 三条铁律

| # | 铁律 | 原因 |
|---|---|---|
| 1 | **先跑通最小闭环，再优化** | 新手最大失败模式是"设计太完美，永远跑不起来" |
| 2 | **每一层都要能验证** | 数仓的核心是**数据可信**，不是代码漂亮 |
| 3 | **从第一天就写文档** | 最后再补文档 → 一定补不出来 → 面试讲不清 |

### 0.5 ⚠️ 最重要的一条：避免"数据泄漏"

信贷数据里有个经典陷阱：**很多字段是"放款后才知道的"**（如已还期数、最后还款状态、回收金额）。

> **如果把这些字段当成"放款时的信息"使用，指标就完全错了。**
> **做法：在设计阶段就明确划分"申请时点信息" vs "表现期信息"，并在文档里写清楚。**

这一条如果你能在面试中主动讲出来，**面试官会立刻判断你"懂业务"**——这是区分"学生项目"和"真实工程思维"的分水岭。

## 三、第三步：数仓设计（约 10 小时）—— ⭐ 最体现专业度的一步

> **这一步决定你的项目是"作业"还是"作品"。** 面试官主要看这里。

### 3.1 分层架构设计

```
┌─────────────────────────────────────────────────┐
│  ADS  应用层   ← 直接给分析/报表用的指标表        │
│        如：逾期率月报、放款趋势、风控策略效果      │
├─────────────────────────────────────────────────┤
│  DWS  汇总层   ← 按主题做轻度汇总（宽表）          │
│        如：客户级汇总、月度资产汇总                │
├─────────────────────────────────────────────────┤
│  DWD  明细层   ← 清洗后的明细，一行一业务事实      │
│        如：贷款事实表、客户维表、产品维表          │
├─────────────────────────────────────────────────┤
│  ODS  原始层   ← 原样落地，不做加工（便于回溯）    │
│        如：原始放款流水                            │
└─────────────────────────────────────────────────┘
```

**每层的作用（面试要能讲）**：

| 层 | 存在意义 | 一句话解释 |
|---|---|---|
| **ODS** | 数据可回溯 | "原始数据原样保存，出问题时能查源头" |
| **DWD** | 清洗 + 规范化 | "统一口径、处理脏数据，形成一行一事实的明细" |
| **DWS** | 减少重复计算 | "按主题预汇总，避免每次分析都从明细算" |
| **ADS** | 面向应用 | "直接产出报表/看板需要的指标表" |

### 3.2 维度建模设计

**要设计的表（建议最小集合）**：

| 表类型 | 表名示例 | 说明 | 粒度 |
|---|---|---|---|
| **事实表** | `dwd_loan_fact` | 贷款放款事实 | 一行 = 一笔贷款 |
| **事实表** | `dwd_repay_fact` | 还款表现事实（若数据支持） | 一行 = 一期还款 |
| **维度表** | `dim_customer` | 客户维（年收入、地区、职业等） | 一行 = 一个客户 |
| **维度表** | `dim_product` | 产品维（期限、利率档、评级） | 一行 = 一个产品组合 |
| **维度表** | `dim_date` | 日期维（年月、季度、星期） | 一行 = 一天 |

**必须做的设计决策（面试会问）**：

| 决策点 | 你要给出的答案 |
|---|---|
| 星型 vs 雪花 | 推荐**星型**（维度不进一步范式化，查询更快、更易理解） |
| 事实表类型 | 事务事实表（每笔贷款） |
| 是否要拉链表 | ⭐ **要做**——客户信息会变（收入/评级更新），拉链表能记录历史（见 3.4） |
| 分区策略 | 按 **放款月份** 分区（便于增量与历史回溯） |

### 3.3 关键字段设计（以 LendingClub 为例）

| 字段类别 | 代表字段 | 归属层 |
|---|---|---|
| 申请时点信息 | `issue_d`（放款月）、`loan_amnt`、`term`、`int_rate`、`grade`、`purpose`、`annual_inc`、`emp_length`、`home_ownership` | DWD 事实表 + 维表 |
| 表现期信息 | `loan_status`、`total_rec_prncp`、`total_rec_int`、`last_pymnt_d`、`out_prncp` | DWD（**标注为表现期**） |
| 派生标签 | `is_bad`（是否不良）、`dpd_bucket`（逾期天数分档） | DWD/ADS |

### 3.4 拉链表（SCD2）—— ⭐ 加分项

**为什么要做**：客户评级/收入会变化，普通表只留最新值，**拉链表能回答"这个客户在放款时是什么评级"**。

| 字段 | 说明 |
|---|---|
| `cust_id` | 客户 ID |
| `attr_value` | 属性值（如信用评级） |
| `start_date` | 生效日期 |
| `end_date` | 失效日期（当前有效填 `9999-12-31`） |
| `is_current` | 是否当前有效 |

**面试价值**：能主动讲出拉链表，说明你懂"历史追溯"，这是数仓的核心能力之一。

## 四、第四步：定义指标体系与口径（约 6 小时）—— ⭐ 银行最看重

> **银行数据岗的核心竞争力是"口径清楚"。** 这一步的产出，是你面试时最能体现业务理解的部分。

### 4.1 必做的指标口径表

| 指标 | 定义（需你明确写出） | 计算逻辑 |
|---|---|---|
| **放款金额 / 笔数** | 统计期内成功放款的总额/笔数 | `SUM(loan_amnt)` / `COUNT(1)` |
| **不良率（逾期率）** | ⚠️ **必须明确"什么算不良"** | 例如：`loan_status IN ('Charged Off','Default')` 计为不良 |
| **逾期天数分档（DPD bucket）** | 按逾期天数分档 | 如 Current / 1-30 / 31-60 / 61-90 / 90+ |
| **批准率** | 批准笔数 / 申请笔数 | 若数据只有放款样本，需说明局限 |
| **平均借款金额** | 总金额 / 笔数 | — |
| **加权平均利率** | 按金额加权（不是简单平均） | `SUM(loan_amnt*int_rate)/SUM(loan_amnt)` |
| **Vintage 逾期率** | ⭐ 按放款月份分组，看账龄 MOB 维度 | 见 §4.2 |
| **迁徙率（Roll Rate）** | 从上期档位迁徙到下期档位的比例 | 见 §4.3 |

### 4.2 ⭐ Vintage 分析（风控核心方法）

**概念**：把**同一放款月份**的贷款作为一批（vintage），观察它们在**不同账龄（MOB, Month on Book）**下的表现。

**为什么要这么做**（面试必答）：
> 不同月份放款的政策不同、客群不同。**直接比较不同月份的总逾期率会误导**——因为老批次账龄长、暴露更充分。Vintage 分析把账龄对齐，才能公平比较"哪批客户质量更差"。

**表结构**：
| 放款月 | MOB1 逾期率 | MOB3 | MOB6 | MOB12 |
|---|---|---|---|---|
| 2018-01 | 0.8% | 1.5% | 2.3% | 3.1% |
| 2018-02 | 0.9% | 1.8% | … | … |

**SQL 思路**（伪代码）：
```
按 放款月 + 账龄月 分组，统计该组内不良笔数 / 总笔数
账龄 = 观测月 - 放款月
```

### 4.3 迁徙率分析（Roll Rate）

**概念**：本处于某档位的贷款，下期迁徙到各档位的比例。

| 期初档位 | → Current | → 1-30 | → 31-60 | → 核销 |
|---|---|---|---|---|
| Current | 95% | 4% | 0.8% | 0.2% |
| 1-30 | 60% | 25% | 12% | 3% |
| 31-60 | 30% | 20% | 35% | 15% |

**用途**：预测未来不良、评估催收效果。

### 4.4 口径表模板（照此填写）

```
| 指标名 | 业务含义 | 计算公式 | 数据来源 | 口径说明 | 负责人 |
|--------|---------|---------|---------|---------|--------|
| 不良率 | 不良贷款占比 | 不良笔数/总笔数 | dwd_loan_fact | 不良定义为 Charged Off + Default；不含 Current | — |
```

> 🔑 **这份"口径表"是银行数据岗最真实的日常工作产物。** 面试时拿出来讲，说服力极强。

### 5.3 ⭐ 数据质量校验（很多人跳过，但你必须有）

| 校验项 | 规则 | 为什么重要 |
|---|---|---|
| **行数守恒** | ODS 行数 ≥ DWD 行数（差值需能解释） | 证明没丢数据也没凭空多 |
| **主键唯一** | `dwd_loan_fact.id` 唯一 | 防止重复计算 |
| **汇总一致性** | DWS/ADS 汇总值 = DWD 明细重算值 | ⭐ **最核心的校验** |
| **金额非负** | `loan_amnt >= 0` | 业务合理性 |
| **枚举合法** | `loan_status` 在允许集合内 | 防止脏数据流入指标 |
| **时间合理** | 放款日期 ≤ 当前日期 | 逻辑正确性 |

> 🔑 **主动做数据质量校验，是"学生作业"和"工程项目"的分界线。** 面试时讲这个，比讲"我用了几种算法"有效得多。

### 5.4 常见技术坑与解法

| 坑 | 症状 | 解法 |
|---|---|---|
| **内存不足** | 读大文件时进程被杀 | 分块读取（`chunksize`）或先裁剪列 |
| **日期格式混乱** | `issue_d` 是 "Dec-2018" 这种 | 显式指定格式解析，不要靠自动推断 |
| **利率是字符串** | "13.56%" 无法计算 | 去 `%` 转 float |
| **缺失值策略不清** | 到处填 0 导致指标失真 | **按字段分别决策并在文档记录** |
| **JOIN 后行数变多** | 维表有重复键 | JOIN 前检查维表主键唯一性 |
| **口径前后不一** | 不同脚本算法不同 | **统一从口径字典取定义** |

### 8.2 数据倾斜（面试高频追问）

**现象**：某个 key 的数据量远大于其他 key，导致个别 task 跑得极慢。

| 处理手段 | 适用 |
|---|---|
| `MAP JOIN`（小表广播） | 一大一小的表 JOIN |
| 加盐打散（key 加随机前缀） | 大表 JOIN 大表且热点 key |
| 两阶段聚合 | GROUP BY 热点 key |
| 调小文件合并 | 大量小文件 |

**面试表述**：
> "在按客户 ID 聚合时发现个别客户数据量占 30%，导致长尾 task。我采用了加盐打散分两阶段聚合，将耗时从 X 分钟降到 Y 分钟。"

### 10.2 八个常见失败模式

| # | 失败模式 | 后果 | 对策 |
|---|---|---|---|
| 1 | **追求完美设计，迟迟不动手** | 永远没有产出 | **先跑通最小闭环** |
| 2 | **跳过 EDA 直接建表** | 后期大量返工 | EDA 必须做 |
| 3 | **不做数据质量校验** | 指标不可信，面试被问穿 | 至少做行数守恒+汇总一致 |
| 4 | **把表现期字段当申请时点用** | 指标逻辑错误（数据泄漏） | 设计阶段就分类标注 |
| 5 | **口径前后不一致** | 同一个指标两个数 | **统一从口径字典取** |
| 6 | **只用 Python 不写 SQL** | 银行要的是 SQL 能力 | SQL 脚本必须单独留档 |
| 7 | **陷入环境搭建** | 浪费数周 | 2 周跑不通换云平台 |
| 8 | **不写文档** | 面试讲不清 | 从第一天就记 |
