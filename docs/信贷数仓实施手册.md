## 第二部分 · 核心原理（面试要能讲清）

> 这一部分是全项目的**思想内核**。代码可以照抄，但这些判断必须自己讲得出来。

### 2.A 数仓为什么要分层

```
┌─────────────────────────────────────────────────┐
│  ADS  应用层   ← 直接给分析/报表用的指标表        │
├─────────────────────────────────────────────────┤
│  DWS  汇总层   ← 按主题轻度汇总（宽表/快照）      │
├─────────────────────────────────────────────────┤
│  DWD  明细层   ← 清洗后的明细，一行一业务事实      │
├─────────────────────────────────────────────────┤
│  ODS  原始层   ← 原样落地，不做加工（可回溯）      │
└─────────────────────────────────────────────────┘
```

| 层 | 存在意义 | 一句话解释（面试要说这个） |
|---|---|---|
| ODS | 数据可回溯 | "原始数据原样保存，出问题时能查源头" |
| DWD | 清洗 + 规范化 | "统一口径、处理脏数据，形成一行一事实的明细" |
| DWS | 减少重复计算 | "按主题预汇总，避免每次分析都从明细算" |
| ADS | 面向应用 | "直接产出报表/看板需要的指标表" |

**更本质的回答**：
> 分层不是为了"看起来专业"，而是为了**解耦**。
> 业务逻辑变了只改 DWD，口径变了只改 ADS，ODS 永远不动。
> 这样每一层都能被独立验证，出错时能快速定位在哪一层。

### 2.B ⭐ 数据泄漏：本项目的核心亮点

**信贷数据的经典陷阱**：很多字段是**放款后才知道的**。

| 字段类别 | 例子 | 什么时候知道 |
|---|---|---|
| **申请时点信息** | `loan_amnt`、`grade`、`annual_inc`、`purpose`、`dti` | 申请那一刻 |
| **表现期信息** | `loan_status`、`out_prncp`、`total_rec_prncp`、`last_pymnt_d` | **放款后** |

**如果把它们混用，指标就完全错了。**

#### 三道防线（本项目怎么做的）

| 防线 | 手段 | 在哪实现 |
|---|---|---|
| **一** | **DDL 物理分表** —— 表现期字段只进 `dwd_loan_perf_fact` | `sql/ddl/01_schema.sql` |
| **二** | **代码白名单** —— `config.APPLY_COLS` 只挑申请时点字段 | `src/config.py` |
| **三** | **自动校验** —— Q8 用 `config.LEAKAGE_BLACKLIST` 扫表结构 | `src/dq_check.py` |

> 🔑 **面试话术**：
> "我不是靠自觉避免数据泄漏，是靠**表结构约束和自动化校验** ——
> 字段黑名单校验一旦发现申请时点表里出现 `out_prncp` 这类表现期字段就直接 fail。"

**区分原则**：看字段语义是"申请那一刻的画像"还是"放款后的表现"。

> ⚠️ **易错点**：`dti`、`revol_util` 是**申请时点**信息（来自放款时征信快照），
> 不属于表现期。只有带 `last_` 前缀的（如 `last_fico_range_low`）才是拉取时点信息。
> 曾经把 `purpose` 误列入黑名单，会导致 Q8 误报 —— 这类边界要逐个核实。

### 2.C 指标口径：银行最看重的能力

#### C1. 不良率 —— 必须限定"终态"

**这是信贷指标里最经典的口径错误。**

| 口径 | 公式 | 全量实测值 |
|---|---|---|
| ✅ **正确（终态口径）** | `SUM(is_bad)/COUNT(*) WHERE is_terminal=1` | **19.9807%** |
| ❌ 错误（不限定终态） | `SUM(is_bad)/COUNT(*)` | 11.9155% |

**为什么差 8 个百分点**：`Current`（仍在还款，占 38.85%）被算进了分母。
等于把"**还没到期的正常贷款**"当成"**没出问题的贷款**"，系统性低估风险。

> 🔑 面试被问"不良率怎么算"，答"不良笔数/总笔数"是**不及格**的，
> 必须说清**分母要限定终态**及原因。

#### C2. 加权平均利率 —— 不能简单平均

```sql
-- ✅ 正确：按金额加权
SUM(funded_amnt * int_rate) / SUM(funded_amnt)
-- ❌ 错误：简单平均（让 1 千元与 4 万元贷款同权）
AVG(int_rate)
```

#### C3. 累计不良率 —— 不能用 `SUM(is_bad_month)`

`is_bad_month` 是"该月末是否处于核销状态"的**逐月标记**。
一笔贷款在 MOB15 被核销后，MOB15~24 的快照**都是 1**，
直接 `SUM` 会把同一笔**重复计数**，导致累计不良率随 MOB 虚高。

```sql
-- ✅ 正确：取"曾核销"标志
MAX(is_bad_month) OVER (
  PARTITION BY issue_month, loan_id ORDER BY mob
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
) AS ever_bad
-- ❌ 错误
SUM(is_bad_month)
```

**口径自检**：累计不良率必须随 MOB **单调不减**。
校验 SQL：`sql/dq/check_vintage_monotonic.sql`（期望返回 0 行）。

#### C4. 口径要放在一处（口径字典的代码化）

所有口径常量集中在 `src/config.py`：

| 常量 | 内容 |
|---|---|
| `BAD_STATUSES` | 什么算不良 |
| `TERMINAL_STATUSES` | 什么算终态 |
| `DPD_MAP` | 状态 → DPD 档位 |
| `LEAKAGE_BLACKLIST` | 表现期字段黑名单 |

> **改口径只改这一处**，避免"同一个指标两个数"。

### 2.D ⭐ 历史追踪：为什么用月末快照而不是 SCD2 拉链表

**v1.0 的原设计**：建 `dim_customer_scd2` 拉链表，记录客户评级/收入的历史变化。

**为什么放弃**：本数据集是**放款时点的静态快照**，`annual_inc`、`grade` 都是**放款时点值**，
没有历史切片。**无法构造真实的属性变更序列** —— 硬做只能造假数据。
一旦被问"你的 SCD2 数据从哪来的"，杀伤力极大。

**改用：月末快照事实表（周期快照）**

| 字段 | 说明 |
|---|---|
| `snapshot_month` | 观测月末 |
| `mob` | 账龄 = 观测月 − 放款月 |
| `dpd_bucket` | 该月末的逾期档位 |
| `out_prncp` | 期末未偿本金 |

**为什么它更好**：
1. 它是**标准数仓模式**（周期快照事实表），不是妥协
2. **数据真实可校验** —— 不需要造假
3. **天然支撑 Vintage 与迁徙率** —— 比拉链表更贴业务

> 🔑 **面试话术**：
> "我原本打算做客户属性拉链表，但发现这份数据是**放款时点的静态快照**，
> 不存在真实的属性变更序列，硬做出来是假的。
> 我改成了**月末快照事实表** —— 同样是标准数仓模式，同样解决历史状态追踪，
> 但**数据是真实的、可校验的**，而且它天然支撑了 Vintage 分析。"

### 2.E 数据边界：比结论更重要

**每一份分析都必须说清"我证明不了什么"。**

| 边界 | 影响 | 处理 |
|---|---|---|
| **仅含放款样本** | 幸存者偏差，全客群不可外推 | 删除批准率；结论限定"已放款客群" |
| **`member_id` 整列为空** | 无客户识别键，客户级分析不可做 | 降级为申请人画像维，**不拼伪 ID** |
| **无逐月还款状态** | 迁徙率的档位为**规则推导** | 明确标注，且说明"方向可信、数值谨慎" |
| **无策略与宏观数据** | 无法归因风险变化 | 只陈述**数据内可验证**的事实 |

#### ⚠️ 避免过度归因（最容易翻车的地方）

| ❌ 错误写法 | 为什么错 |
|---|---|
| "2018 年逾期率上升，**可能与客群下沉或政策放松有关**" | 本数据**无法验证**。面试官一问"你怎么证明"就翻车 |

| ✅ 正确写法（两段式） |
|---|
| **① 数据内可证**："该批次 C–E 级占比从 X% 升至 Y%，加权平均利率从 A% 升至 B%" |
| **② 明确边界**："至于驱动因素是准入调整还是外部环境，**当前数据无法区分**" |

> 🔑 **说清"我不能证明什么"，比给出一个漂亮的因果更专业。**

### 第 1 步 · 预处理：剔除页脚 ⭐ 新增步骤，不可跳过

**为什么单独做这一步**

原设计让每个脚本读取时用 `skipfooter=1` 跳页脚。**实测发现两个致命问题**：

**问题一：`skipfooter` 与 `chunksize`/`nrows` 互斥**（pandas 2.2.2 与 3.0.5 均如此）

```python
pd.read_csv(p, chunksize=100_000, skipfooter=1, engine="python")
# ValueError: 'skipfooter' not supported for iteration
```

`skipfooter` 只能用于**一次性全量读取**，而全量读只能用 python 引擎（226 万行要 20–40 分钟）。
**也就是说：原设计下所有分块脚本一行都跑不起来。**

**问题二：页脚不止 1 行，而是 33 行，且散布在文件中部**

```
行  421096   Total amount funded in policy code 1: 6417608175,,,,...
行  421097   Total amount funded in policy code 2: 1944088810,,,,...
...          共 16 对，间隔约 10~23 万行出现一次
行 1651666   Loans that do not meet the credit policy,,,,...      ← 章节标题
行 2260700   Total amount funded in policy code 1: 1465324575,,,,...
行 2260701   Total amount funded in policy code 2: 521953170,,,,...
```

这个文件**不是一份导出，而是多个年度分段拼接**而成，段间夹着章节标题与汇总行。

**做什么**：`src/prepare_raw.py`（一次扫描，解决四个问题）

| 解决什么 | 怎么做 |
|---|---|
| 33 行页脚 | 全文件扫描，按"`id` 必须是纯数字"判定剔除 |
| 14 个全空列 | 整体剔除（151 → 137 列） |
| 分块 dtype 漂移 | 首块探测 schema，**固定 dtype** 传给每次读取 |
| `id` 存成 float | 主键**强制 string**（避免精度隐患与 `.0` 后缀） |

**产出**

| 文件 | 内容 |
|---|---|
| `data/clean/loans_full.parquet` | 2,260,668 行 × 137 列（338 MB） |
| `data/clean/loans_sample.parquet` | 200,000 行（调流程用） |
| `data/clean/footer_line.txt` | **33 行页脚原文留证** |
| `data/clean/clean_meta.json` | 行数/列数/页脚行号 |

**性能对照**

| 方案 | 耗时 | 能否分块 |
|---|---|---|
| ❌ 每次 `skipfooter` | 20–40 分钟 | ❌ |
| ✅ 一次预处理 + 读 Parquet | **80–90 秒** | ✅ |

**验收标准**

- [ ] `loans_full.parquet` 行数 = **2,260,668**
- [ ] `footer_line.txt` 有 **33 行**
- [ ] `clean_meta.json` 中 `footer_lines_skipped=33`、`clean_rows_full=2260668`
- [ ] `id` 是 **string** 类型且全为纯数字

| 星型 vs 雪花 | **星型** | 查询更快、更易理解 | 雪花：JOIN 层级多，分析无收益 |

#### ⚠️ 三个 DDL 陷阱（都踩过）

| 陷阱 | 现象 | 解决 |
|---|---|---|
| **MySQL 保留字** | `year_month` 报 `ERROR 1064` | **所有列名加反引号** |
| **排序规则冲突** | JOIN 时报 `ERROR 1267 Illegal mix of collations` | 全库统一 `utf8mb4_0900_ai_ci` |
| **主键顺序** | 快照表插入吞吐从 40k 掉到 5k 行/秒 | 主键用 `(snapshot_month, loan_id)`，**与插入顺序一致** |

**主键顺序那条展开说**：

数据是**按观测月批量写入**的。若主键是 `(loan_id, snapshot_month)`，
同一笔贷款的不同月份记录在聚簇索引里分散在很远的位置 → 随机 I/O + 页分裂。

改成 `(snapshot_month, loan_id)` 后，逐月插入变成**顺序追加**：

| 主键 | 吞吐 | 480 万行耗时 |
|---|---|---|
| `(loan_id, snapshot_month)` | 5,379 行/秒（**持续衰减**） | 26 分钟 |
| **`(snapshot_month, loan_id)`** | **38,032 行/秒（恒定）** | **2.1 分钟** |

> 🔑 **这是一个很好的面试素材**：说明你理解"聚簇索引的物理顺序影响写入性能"，
> 而不只是会写 SQL。

### 第 6 步 · DWS 月末快照

**做什么**：`src/dws_snapshot.py`

为每笔贷款生成从放款月到观测月的逐月快照。

**核心逻辑**

```
对每个观测月 M：
  ├─ 取所有 issue_month < M 的贷款
  ├─ mob = M − issue_month（账龄）
  ├─ 推导该月末 DPD 档位
  └─ 记录 out_prncp / 累计已收本金
```

#### ⚠️ 四个必须注意的实现细节

| # | 坑 | 后果 | 解决 |
|---|---|---|---|
| 1 | 手工拼 `mi//12`, `mi%12` 算月份 | **12 月边界算错** | 用 `pd.DateOffset(months=...)` |
| 2 | `Int64` 的 NA 参与比较 | NA 在 mask 时**不覆盖**，坏账被判成 `CURRENT` | **先 `fillna(-1)` 再比较** |
| 3 | 不限制 `mob` 上限 | 行数上亿 | 设 `MOB_MAX` |
| 4 | 主键顺序与插入顺序不一致 | 吞吐从 40k 掉到 5k 行/秒 | 主键 `(snapshot_month, loan_id)` |

**第 2 条展开**：实测有 **148 笔**贷款 `last_pymnt_d` 为空（从未还款）。
若不处理，`months_since_last_pymnt` 为 NA，比较得到 NA，mask 不覆盖 →
被静默判成 `CURRENT`（= 未曾逾期）。**这些恰恰是最该关注的坏账。**

**规模对照（实测）**

| `MOB_MAX` | 快照行数 | 说明 |
|---|---|---|
| 12 | 25,209,835 | 首年表现窗口 |
| **24** | **44,718,091** | **本项目采用**（覆盖 2 年期贷款完整生命周期） |
| 36 | 59,158,566 | 边际收益低 |

**性能优化（重要）**

灌数前**先删二级索引**，灌完再重建：

| 做法 | 480 万行耗时 |
|---|---|
| 边插边维护 4 个索引 | 26 分钟 |
| **删索引→灌数→重建** | **4.2 分钟**（灌数 2.1 分 + 索引 2.1 分） |

**验收标准**

- [ ] `(snapshot_month, loan_id)` 唯一，无重复
- [ ] 抽 3 笔贷款，快照序列的 `mob` **连续递增**
- [ ] `snapshot_month` 格式正确（**抽查 12 月/1 月边界**）
- [ ] 行数与 `MOB_MAX` 的预估一致
- [ ] 文档中**明确标注**"DPD 档位为规则推导，非原始逐月状态"

> 我宁可写清'这是推导的、早期 MOB 会滞后'，
> 也不想让一个看起来漂亮的数字失去可信度。
>
> 同样，某批次逾期率上升，我能证明的是'该批次 C–E 级占比从 X% 升到 Y%'，
> 但**我不能证明是准入策略放松导致的** —— 那需要申请侧和策略变更数据。

> 🔑 **语气很重要**：上面没有一处是"我的项目不完善"式的检讨，
> 全是"我识别了边界并做了处理"的工程判断。
> **主动声明边界叫专业，自我检讨叫不自信。**

#### C2. 为什么不用 SCD2 拉链表

> "我原本打算做客户属性拉链表，但发现这份数据是**放款时点的静态快照**，
> `annual_inc`、`grade` 都是放款时点值，不存在真实的属性变更序列，
> 硬做出来是假的。
> 我改成了**月末快照事实表** —— 它是标准数仓模式（周期快照事实表），
> 同样解决'历史状态怎么追踪'，但**数据是真实的、可校验的**，
> 而且它天然支撑了 Vintage 与迁徙率分析。"

#### C3. 为什么算不良率必须限定终态

> "不良率的分母必须限定**终态**贷款，也就是已结清或已核销的。
> 因为 `Current` 状态的贷款**仍在正常还款**，把它们放进分母，
> 等于把'还没到期的贷款'当成'没出问题的贷款'。
>
> 我实测过差异：限定终态是 **19.98%**，不限定是 **11.92%** ——
> **低估了 8 个百分点**。这是信贷指标里最经典的口径错误。"

#### C4. 遇到的最大技术问题（性能优化）

> "快照表最初写入很慢，480 万行要 26 分钟，而且**吞吐持续衰减** ——
> 从 40,000 行/秒一路掉到 5,000 行/秒。
>
> 我分析下来根因是**主键顺序与插入顺序不匹配**：
> 主键是 `(loan_id, snapshot_month)`，但数据是**按观测月批量写入**的。
> 这样同一笔贷款的不同月份记录在 InnoDB 聚簇索引里分散在很远的位置，
> 造成随机 I/O 和页分裂。
>
> 我把主键改成 `(snapshot_month, loan_id)`，让逐月插入变成聚簇索引的**顺序追加**；
> 同时灌数前先删掉二级索引、灌完再重建。
> 结果 480 万行从 **26 分钟降到 4.2 分钟**，吞吐稳定在 38,000 行/秒不再衰减。"

> 🎯 **这一段展示的是**：能定位性能问题根因（不只看表面）、
> 理解数据库物理存储、有量化对照。**层次远高于"我会写 SQL"。**

#### C5. 为什么这个数据量其实不需要分布式

> "226 万行、137 列，全量读进内存约 6.8 GB，**单机完全可以承载**。
> 我用数仓分层不是为了扛量，而是为了**让口径可复用、让每个指标有唯一可信来源、
> 让 ODS 可回溯** —— 这三件事和体量无关。
> 阶段三我会把同一套口径迁到 Hive 分区表做对照实验，
> 量化单机与分布式的差异，明确这个数据量的**引擎选择边界**。"

> 🔑 主动说出"我这个量级不需要分布式"，反而证明你有**成本意识和工程判断力**。
