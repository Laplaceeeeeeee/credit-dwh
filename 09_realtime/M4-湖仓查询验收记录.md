# M4 · 湖仓查询验收记录（第二个引擎直读同一份存储）

> **验收时间**：2026-09-24
> **结论**：**✅ M4 通过** —— Spark 直接读 Flink 正在流写的同一份 Paimon 存储，
> 并验证了**读算分离**、**快照隔离**与**时间旅行**
> **定位**：按技术决策文档，M4 是**可砍项**；但它决定"湖仓"这个词能不能落地 ——
> 不能被独立引擎直读，就只是"我往一个目录里写了 parquet"

---

## 1. 为什么"湖仓"必须由第二个引擎来证明

湖仓相对"数仓 + 数据湖两套"的核心卖点是：
**一份存储，多个引擎各自读写，中间不需要 ETL 搬运。**

所以 M4 要证明的不是"我能再查一遍"，而是三件具体的事：

| # | 要证明的 | 怎么证 |
|---|---|---|
| 1 | 两个引擎读**同一份存储**，结果一致 | Spark 直读 Paimon，与 Flink 侧数字对齐 |
| 2 | **读算分离**：写着能读、读着能写 | Flink 持续流写期间，Spark 读到刚写入的变更 |
| 3 | **快照隔离 + 时间旅行** | 同一时刻既读最新快照、又按 snapshot id 读历史快照 |

---

## 2. 为什么选 Spark（而不是 StarRocks / Doris / Trino）

- **不新增镜像**：阶段三已经拉过 `apache/spark:3.5.9-scala2.12-java11-python3-ubuntu`（1.86 GB）；
- **版本能严格对齐**：见 §3；
- StarRocks / Doris 确实更接近"OLAP 直读湖"的典型生产形态，但要多拉 1–2 GB 镜像并额外吃内存，
  而 Docker VM 只有 7.64 GB（当前实时栈已占用约 4 GB）。**这是资源约束下的取舍，不是"Spark 更好"。**

## 3. ⚠️ 一个容易拿错制品的坑（B-23）

```
paimon-spark-3.5         -> 版本只到 1.3.2     （Scala 2.13 线）
paimon-spark-3.5_2.12    -> 有 1.4.1 / 1.4.2  （Scala 2.12 线）✅
```

Spark 3.5 用的是 **Scala 2.12**，所以必须用带 `_2.12` 后缀的制品。
拿成不带后缀的那个，版本会停在 1.3.2 —— **与写入端（Paimon 1.4.2）版本不一致**，
属于"能装上但语义不保证"的危险状态。

## 4. 实测结果

### 4.1 两个引擎读同一份存储，数字一致

Spark 通过 Paimon 的 Spark catalog 直读（注意 Spark 侧是
`spark.sql.catalog.paimon=org.apache.paimon.spark.SparkCatalog`，
**不是** Flink 那种 `CREATE CATALOG` 语法）：

| Spark 读到的 | 值 | Flink 侧 / 离线侧 |
|---|---|---|
| `paimon.rt.rt_loan_month_agg` | **139 / 2,260,668 / 34,004,208,600.00** | 完全一致 ✅ |
| `paimon.rt.rt_loan_fact_latest` | **2,260,668 / 34,004,208,600.00** | 完全一致 ✅ |
| 抽样 `2007-06` | 24 / 91,850.00 | 一致 ✅ |

### 4.2 ⭐ 读算分离 + 快照隔离 + 时间旅行（一次查询同时验证）

Flink 作业**全程没有停**（持续流写）。改一行 MySQL，然后在**同一次 Spark 查询**里读两种视图：

| 视图 | `issue_month='2007-06'` | 总笔数 |
|---|---|---|
| **LATEST**（最新快照） | **25 / 93,084.56** | **2,260,669** |
| **`VERSION AS OF 5`**（历史快照） | **24 / 91,850.00** | **2,260,668** |

这一次查询同时证明了三件事：

1. **写入的变更被读者看到了**（25 vs 基线 24）—— 没有做任何导出/搬运；
2. **读者拿到的是稳定快照**：两个视图在同一时刻都能读出完整、自洽的结果，
   **没有出现"读到半个写入"的状态**；
3. **历史版本可回读**：`VERSION AS OF 5` 稳定返回改动前的值 ——
   这对"这份指标在那一刻长什么样"的审计/复现是刚需。

### 4.3 ⭐ 可见性延迟 ≈ 10 秒 —— 由 checkpoint 间隔支配

| 项 | 实测 |
|---|---|
| MySQL 提交 | `23:00:41.262`（北京）= `15:00:41.262` UTC |
| 该变更出现在 Paimon 快照里 | 快照 id=9，`commit_time = 15:00:51.098` UTC |
| **可见性延迟** | **≈ 9.8 秒** |

**根因**：Paimon 的快照提交**绑定在 Flink checkpoint 上**，我们的
`execution.checkpointing.interval = 10s` —— 所以"能被查询引擎看到"的延迟量级
就是 checkpoint 间隔。

**这和 M1 的 310 ms 不是矛盾，而是两件事**：
- 310 ms 是"变更到达 Kafka"；
- 9.8 s 是"变更**可被查询引擎看到**"（等下一次 checkpoint 提交快照）。

> 面试价值：这一条把"实时"这个词拆开了 ——
> **入队快 ≠ 可查快**。要压可见性延迟就该调小 checkpoint 间隔，
> 代价是更频繁的提交与更多小文件。能主动说出这个权衡，比说"我的链路是实时的"有信息量。

### 4.4 收敛核对（净零）

清理测试数据后，**Spark** 读到的实时侧回到
**139 / 2,260,668 / 34,004,208,600.00**，与离线基线一致 ✅
（M4 全程对源库的改动只有 2 笔 `RT-M4-*` 测试记录，已删除并核对净零。）

## 5. 两个设计取舍

**① warehouse 以 `:ro` 只读挂载给 Spark。**
读者不该写湖；这也顺带避免了"两个引擎竞争写同一张表"这种危险配置
（Paimon 允许多写但需要显式处理冲突，本项目**没有**验证过多写者）。
实测确认：`mount` 显示 `type ext4 (ro,relatime)`，容器内 `touch` 被拒。

**② 用 compose `profiles: ["query"]` 隔离。**
默认 `docker compose up -d` **不会**拉起 Spark（省内存）；
只在做湖仓查询验证时按需启动：

```powershell
docker compose -f docker-compose-streaming.yml --profile query up -d spark-query
```

## 7. 诚实缺口

1. **Spark 是 `local[*]` 单 JVM，不是集群** —— 不能声称多节点查询能力；
   也没有做并发查询压测。
2. **没有和 StarRocks / Doris / Trino 对比** —— 那才是"OLAP 直读湖"的典型生产形态，
   本项目因内存约束没做，**不能声称"验证过 OLAP 引擎直读"**。
3. **没有做同查询的引擎性能对比**（例如同一聚合在 Paimon vs 阶段三 Hive 表上的耗时）——
   因此**不能声称湖仓查询更快**，只验证了"能读、一致、可隔离"。
4. **时间旅行只验了 snapshot id**：Paimon 还有 **tag / branch**（长期保留的命名快照、
   以及写分支），本项目没验证。
5. **只验证了 Spark 读**：写路径仍然只有 Flink 独占，
   **没有验证 Spark 写 Paimon**，也没有验证多写者并发。
6. **可见性延迟只测了 1 次**（9.8 秒那次），没有测不同 checkpoint 间隔下的曲线 ——
   "可见性延迟 ≈ checkpoint 间隔"是**由机制推出的解释**，实测样本只有一个点。
7. **没有验证 Spark 侧对本项目"口径"的一致性**：Spark 读到的是总量与月粒度笔数，
   没有在 Spark 里重算不良率那类复杂口径（那需要表现期字段与更多 join）。
