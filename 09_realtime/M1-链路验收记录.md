## 1. 验收口径

M1 的完成定义（来自技术决策文档）：**改一行 MySQL，能测到它出现在 Paimon 里，并给出端到端延迟。**

因此本记录必须回答三件事：
1. 链路是否真的通了（不是"作业 RUNNING"就算）；
2. 延迟是多少，怎么测的（**测量方法本身要有说服力**）；
3. 对源库有没有副作用（**必须净零**，否则离线对账基准就毁了）。

## 3. 实测结果

### 3.1 端到端延迟 ⭐

测量方法（刻意设计，见 §4）：

```
latency = sink_ts(Paimon 落库时刻) - op_ts(binlog 变更时刻)
```

| 记录 | MySQL 提交时刻（`NOW(3)`） | Paimon `sink_ts` | 端到端延迟 |
|---|---|---|---|
| RT-TEST-0011…0015（5 笔） | `12:45:22.392` | `12:45:22.700`–`22.705` | **≈ 308–313 ms** |

- **主口径 ≈ 310 ms（亚秒级）**：用 MySQL 的毫秒级提交时刻与 Paimon 的落库时刻直接相减。
- **保守上界 705 ms**：`sink_ts - op_ts`（`op_ts` 只有秒级精度，故这个差值偏大）。
- ⚠️ 真实数字落在 310–705 ms 之间；受 `op_ts` 秒级精度限制无法更精。**不要写成"310 ms 精确值"。**

### 3.2 事件时间窗口（D3 的证明）⭐

| window_start | window_end | write_cnt | funded_sum |
|---|---|---|---|
| 2026-09-24 12:28:00 | 2026-09-24 12:29:00 | 5 | 15,000.00 |
| 2026-09-24 12:45:00 | 2026-09-24 12:46:00 | 5 | 16,500.00 |

- 两个窗口都**正确发射**，计数与金额与插入值完全吻合。
- ⭐ **窗口不会凭空关闭**：12:28 那批数据插入后，窗口一直不发射 ——
  因为 Watermark = `max(op_ts) - 5s`，没有新数据就永远跨不过窗口右界。
  直到 12:45:22 插入新记录把 Watermark 推过 12:29:00，12:28 的窗口才发射。
  **这既是"坑"也是"事件时间语义真的在工作"的证据**（面试可讲）。
- 12:47:30 插入的记录，其 [12:47, 12:48) 窗口在验收时仍**未关闭**（Watermark 尚未越过 12:48），符合预期。

## 4. 为什么这样测延迟（方法论）

**错误做法**：外部轮询"什么时候能在 Paimon 里查到"。
测到的其实是 `sql-client 启动时间 + 查询时间`（实测单次约 **4–6 秒**），
把亚秒级的链路延迟完全淹没 —— 会得出"延迟 5 秒"的错误结论。

**正确做法**：在链路内部打时间戳。
`rt_loan_fact_latest` 表刻意多了 `sink_ts` 列（`CURRENT_TIMESTAMP` 在流模式下逐条求值），
于是延迟 = `sink_ts - op_ts`，**没有任何观测开销**，且可以看分布（min/avg/max）。

⚠️ `TIMESTAMPDIFF` 的两个坑（实测）：
- **不支持 `MILLISECOND`** → `ParseException`（Flink 只接受 SECOND / MICROSECOND / FRAC_SECOND 那一组）；
- **`MICROSECOND` 实际按秒截断**：888 秒的差值返回 `888000`（=888×1000），
  而 0.705 秒的差值返回 **0**。所以**不能**用它做毫秒级测量，
  这就是主口径改用 MySQL `NOW(3)` 与 `sink_ts` 直接相减的原因。

## 5. 踩到的坑（本阶段排错手册，编号续阶段三）

| # | 现象 | 根因 | 对策 |
|---|---|---|---|
| **B-1** | `docker manifest inspect <tag>` 全部超时，误判成"镜像拉不到" | **它不走 `registry-mirrors`**，直连 `registry-1.docker.io` | 预检必须用 `docker pull`：**能拉才算数** |
| **B-2** | CDC 连接器 jar 只有 0.4 MB，脱离 Maven 不可用 | `flink-connector-mysql-cdc` 是**瘦 jar** | 用 **`flink-sql-connector-mysql-cdc`**（shaded，20.7 MB） |
| **B-3** | CDC 跑起来报找不到 JDBC 驱动类 | shaded jar **不含 MySQL 驱动**（GPL 许可） | 另配 `mysql-connector-j`（直接复用阶段三那份） |
| **B-4** | 源表不声明主键 → `chunk.key-column is required`；声明主键 → `sink doesn't support update/delete changes` | CDC 源**始终**产出变更流；append-only 的 json sink 接不住 | Kafka sink 用 **`debezium-json`**（changelog 格式，由镜像自带的 `flink-json` 提供，**无需额外 jar**） |
| **B-5** | 想在 Kafka 源上用 `op` 元数据列做过滤 → `Invalid metadata key 'op'` | Kafka 源只暴露 `value.*` 前缀的格式元数据 | 改让窗口直接吃 changelog（语义更严谨，见 B-14） |
| **B-6** | `CREATE CATALOG paimon` 报 `ClassNotFoundException: org.apache.hadoop.conf.Configuration` | Paimon 的 Flink 连接器即使走本地文件系统也依赖 Hadoop | 加 **`paimon-hadoop-uber`**（与 Paimon 同版本），不要用停在 Hadoop 2.8.3 的 `flink-shaded-hadoop-2-uber` |
| **B-7** | 50 MB 的 jar 下载"成功"但只有 11 MB，且无法解压 | `Invoke-WebRequest` 报传输错误时**已落盘一个看似正常的截断文件** | 大文件用 `curl --retry-all-errors -C -`，并**校验 Content-Length 与 zip 完整性** |
| **B-8** | 一个写错的作业让集群后续作业全部 `NoResourceAvailableException` | **Flink 默认重启策略是无限重试**，失败作业一直占着 slot | 必须有界：`restart-strategy.fixed-delay.attempts: 3` |
| **B-9** | Paimon sink 报 `Sink materializer must not be used with Paimon sink` | Flink 默认给 upsert 目标插 sink 物化器，而 Paimon sink 原生支持 upsert | `table.exec.sink.upsert-materialize: NONE`（集群级 + 作业级都写） |
| **B-10** | Kafka 源报 `UnknownTopicOrPartitionException`，源协调器反复挂掉 | 主题不存在（M1a 用 `latest-offset` 且源库未变更时，sink **不会**创建主题） | **显式建主题**：`kafka-topics.sh --create` |
| **B-11** | 一次脚本提交出两个作业、互相抢 slot | **sql-client 里每个 `INSERT` 是一个独立作业** | 用 **`EXECUTE STATEMENT SET`** 合成一个（顺带源只读一次） |
| **B-12** | ⭐⭐ Paimon 写入稳定失败：`Mkdirs failed to create .../bucket-0`、`... .parquet (Permission denied)`、`Failed to create directory for shared state` | **权限主体不一致**：`docker top` 显示 Flink 守护进程是 **uid 9999(flink)**，而 **`docker exec` 默认是 root** → sql-client 以 root 建出的目录 `root:root 755`，TaskManager 写不进去。**不是 Hadoop 的 bug，不是文件系统的问题，也不是 Windows 的事** | 用 `init/02_prepare_volumes.ps1` 把 `/warehouse` 与 `/opt/flink/checkpoints` chown 给 `flink`，并且**所有 sql-client 调用都加 `-u flink`** |
| **B-13** | 延迟测量恒等于 0 | `TIMESTAMPDIFF(MICROSECOND, ...)` 按秒截断，且 `MILLISECOND` 不被支持 | 改用 MySQL `NOW(3)` 与 `sink_ts` 直接相减 |
| **B-14** | 窗口表长时间不产出，怀疑作业有问题 | **事件时间窗口不会凭空关闭**：Watermark 不前进则不发射 | 这不是 bug —— 插入新数据推进 Watermark 即可；面试可当"证明语义正确"的素材 |
| **B-15** | 用 PowerShell 读 `.env` 出现乱码，且注释行与 `KEY=VALUE` 行看起来"合并"了 | 未加 `-Encoding UTF8`；GBK 误解码把 UTF-8 汉字的尾字节当 GBK 首字节，**顺手吞掉换行符** | 读 UTF-8 一律 `-Encoding UTF8`；`docker compose config` 可验证文件本身没坏 |
| **B-16** | 自证检查报 `.ps1` 含 12 个非 ASCII 字节 | 我在脚本注释里写了中文与 emoji，违反 B-52 | `.ps1` 一律纯 ASCII；阶段三那条规则现在由机器断言强制 |

## 6. 诚实缺口（面试不要说过头）

1. **端到端延迟只有一个批次（5 笔）的样本**，且 `op_ts` 秒级精度限制了上限。
   要给分布必须灌更多样本来测 —— M2 做。
2. **没有做故障演练**：kill 作业后能否不丢不重、Exactly-Once 边界，**都还没验**（M2 的活）。
3. **没有做批流对账**：`docs/SLA与监控.md` §5.3 的两条规则仍未实现（M3 的活）。
4. **数据规模极小**：只走了 15 条变更，**没有任何吞吐/压力数据**，
   不能声称"链路能扛多少 TPS"。
5. **单机单 broker 单 slot**：不是集群，不能写"高可用""生产级"。
6. **`cdc` 账号是 `mysql_native_password`**（为绕开公钥交换，见 `init/01_create_cdc_user.sql`），
   这是**便利性决定**，生产环境应评估用 `caching_sha2_password` + TLS。
7. **窗口指标的语义是"该窗口内发生过变更的贷款（当前状态）"**，不是"变更事件条数" ——
   因为输入是 changelog，UPDATE 会把该行从旧窗口移到新窗口。
   汇报时要说清，别含糊成"每分钟新增放款笔数"。
