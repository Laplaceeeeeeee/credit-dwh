| | 离线侧 | 实时侧 |
|---|---|---|
| 载体 | MySQL `credit_dwh.dwd_loan_fact` | Paimon `rt.rt_loan_month_agg` |

否则比的是两份数据，不是两条链路的指标，对账就失去意义。

## 3. ⚠️ 必须如实说明的偏差：粒度是「放款月」，不是「日」

`docs/SLA与监控.md` §5.3 原文写的判据是"**日粒度**笔数/金额"。
那是为"有日事件"的系统写的。本数据集**没有真正的日粒度**：

```
dwd_loan_fact.issue_date    DATE          COMMENT '放款日期(当月1日)'
dwd_loan_fact.issue_month   CHAR(7)       COMMENT '放款月 YYYY-MM'
```

`issue_date` 一律是"当月 1 日"，业务事实的最小粒度就是放款月（139 个月）。
因此对账按 `issue_month` 做，**不能声称"做过日粒度对账"**。

**已回写 SLA 文档**：说明了偏差、为什么、以及生产环境若事件本身带日粒度时
该规则可直接照用（把 `issue_month` 换成日期分区键），届时还需额外考虑
**时区与"哪一天"的窗口边界**在两侧是否按同一口径算。

## 4. 容差为什么是 0.00（不是 0.01%）

两侧都是**精确十进制求和**（MySQL `DECIMAL(14,2)` vs Flink `DECIMAL` 求和），
理论就该精确相等，实测也是 0.00。所以容差设 0.00：
**一旦出现差异，差异本身就是问题信号，不该被容差吞掉。**

对比 §5.1 的比率列容差 5e-5：那里的差异有明确根因
（MySQL `div_precision_increment=4` 的引擎量化语义），才给了容差。两者性质不同。

> 本轮**没有**出现 5e-5 那类引擎语义差异 —— 因为对账口径只用了
> `COUNT(*)` 与 `SUM(金额)`，没有除法。这是刻意的：**对账口径先避开引擎差异，
> 让差异的含义保持单一**（差异 = 数据/口径问题，不是引擎问题）。

## 5. 实现方式与一个技术选择

**难点**：Python 侧没有 Paimon 读取器，而主键表的 LSM 语义**不能靠直读 parquet 复现**
（去重、合并、快照都发生在引擎层）。所以：

```
Flink batch 读 paimon.rt.rt_loan_month_agg
  → filesystem sink 写 CSV 到 /results/（命名卷）
  → 脚本 docker exec cat 出来
  → 与 MySQL 侧逐月比对
```

这样**读取用的是引擎的正确语义**，而不是自己解析存储文件。
用命名卷而非 bind mount，理由同 warehouse：Windows 文件共享对 JVM 不可靠（B-19）。

`funded_sum` 落 CSV 前 `CAST(... AS STRING)`：避免 DECIMAL 文本化时出现
`1E+3` 这类科学计数（实测 debezium-json 就出现过），让比对是**字符串级精确**。

## 8. 诚实缺口

1. **不是持续对账**：脚本要手动跑，没有调度器、没有告警通道
   （`sla_check.py` 仍未实现，"把判据定时化"这件事没做）。
2. **只对了一个指标**：放款月笔数与金额。阶段三的 `ads_*`（Vintage、迁徙率、分层不良率）
   **还没有实时侧对应物**，所以没对 —— 它们涉及月末快照与表现期字段，
   实时化是另一项工程。
3. **实时侧依赖全量快照能跑成功**：`rt_loan_month_agg` 由 CDC 全量快照 + 增量构建；
   若 binlog 历史被清理（`binlog_expire_logs_seconds` = 30 天）或快照失败，
   **历史部分补不回来**，只能重新快照。本次是单次成功，未做"快照失败后重试"的验证。
4. **容差 0.00 的适用前提**：当前两侧都是精确十进制。若将来引入 `DOUBLE` 累加
   （例如换成近似聚合函数），**必须重新论证容差**，不能沿用。
5. **没有验证长时间运行下的一致性**：只跑了一次对账，没有"跑几小时后再对账"。
6. **没有验证故障后的对账**：M2 的故障演练场景下对账是否仍通过，本轮没测。
7. **规模是单机**：单 broker、单 TM、单 slot；对账本身是批任务，不受实时侧并行度影响，
   但**不能据此声称生产规模下的对账能力**。
