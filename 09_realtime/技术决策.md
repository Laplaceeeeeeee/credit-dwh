## 1. 四条决策（2026-09-24 定）

| # | 决策 | 选择 | 核心理由 | 代价（明确接受） |
|---|---|---|---|---|
| D1 | CDC 接入方式 | **Flink CDC 抓 binlog → Kafka → Flink → Paimon** | 真实变更流（可真实 INSERT/UPDATE 生成事件），且拿到"消息队列"这个实时岗筛选关键词 | 多一个容器、多一跳延迟 |
| D2 | 湖仓表格式 | **只做 Paimon**，把"为什么不用 Iceberg"讲清 | 主键更新 + 流读 + changelog 正是"实时落湖"的标配；省时间省内存 | 不做 Iceberg 对照实验（列为可选 E6） |
| D3 | 时间语义 | **真做事件时间 + Watermark + 允许延迟**，滚动/滑动窗口 | 这是面试最核心的一道题；用处理时间糊过去等于自弃 | 需要额外造乱序/迟到数据来验证 |
| D4 | 部署与资源 | **独立 compose + Paimon 落本地文件系统** | Docker VM 只有 7.64 GB，跑实时链路时停掉 Hive/Spark 四容器即可 | 不接近生产的存算分离形态（MinIO 列为可选） |

### D1 的展开：为什么必须"真 CDC"

旧方案（第 19 步原计划）里有一条降级路径：**用 Python + kafka-python 消费者读 TSV 回放**。
本次**明确放弃这条降级路径**，理由：

- 回放不是 CDC。被追问"binlog 是怎么解析的、全量加增量怎么无缝切换"会直接答不上来；
- 本项目的数据源（`credit-dwh-mysql`）是活的 MySQL，改一行数据就能产生真实 binlog 事件——
  造真实变更流的成本几乎为零，没有理由退化成回放。

### D2 的展开：选型理由要能答三问

被问"为什么用 Paimon 不用 Iceberg"时，答案必须是场景驱动，不是"教程用的"：

1. **为什么选它**：本场景需要**主键更新**（信贷表按 `loan_id` 反复更新）与**流读 / changelog**，
   Paimon 的 LSM 主键表、`partial-update`、`changelog-producer` 正是为此设计；
2. **它什么时候会坏**：小文件会随更新累积 → 依赖 compaction；流读并发与快照过期会让长跑作业失效；
3. **怎么知道它坏了**：文件数、compaction 状态、checkpoint 时长与状态大小（全部要测量并落盘）。

## 2. 第一天硬前置：版本矩阵与镜像可拉性

> ⚠️ **这一节是开工闸门，不通过就不写任何链路代码。**
> 依据是阶段三的教训：第 12 步把"先确认镜像能拉到"放在最前面，
> 而 `apache/hive` 与 `quay.io/debezium/connect` 都曾在这台机器上踩过（后者不在 Docker Hub，本机只镜像 Hub）。

**已确认的环境事实（2026-09-24 实测）**

| 项 | 实测 | 影响 |
|---|---|---|
| Docker daemon | ❌ **未运行**（`dockerDesktopLinuxEngine` 管道不存在） | 预检前必须先启动 Docker Desktop |
| 本地代理 7897 | ✅ LISTENING | 镜像拉取与 git push 都依赖它 |
| 宿主机 / Docker VM | 15.8 GB / **7.64 GB** | 实时链路必须与 Hive/Spark 分时复用，不能共存 |
| GitHub 推送 | ✅ 已通（`43e6642`） | 每步可提交可回退 |

**待实测锁定（不许猜，逐条跑出来再写进本文档）**

1. **Flink 版本**：候选 Flink 1.20.x（阶段三文档里的旧候选是 `flink:1.20.4-scala_2.12-java17`）。
   → 先 `docker manifest inspect <tag>`，再实拉。
2. **Paimon 版本**：候选 1.4.x（公开制品页可见 `paimon-spark-4.0` 的 1.4.1/1.4.2）。
   → **必须与 Flink 主版本严格对齐**，取官方兼容表；`flink-paimon-bundle` 的 Flink 主版本号要对得上。
3. **Flink CDC 版本**：候选 3.6.x（官方文档站存在 `flink-cdc-docs-release-3.6`）。
   → CDC 连接器有两条路线：**Flink CDC source（DataStream/SQL 里用）** vs **Pipeline Connector（整库同步）**。
   本阶段用哪条要写下来（本次倾向 **source**，因为要自己写窗口聚合，Pipeline 会把计算层吃掉）。
4. **Kafka 版本**：候选 `apache/kafka:4.x`。
   → 注意工具脚本在 `/opt/kafka/bin/`（不是 Bitnami 的 `/opt/bitnami/kafka/bin/`，阶段三文档已记过）。

**预检通过判据**：四个 tag 都能 `docker manifest inspect` 成功 + 至少实拉 Flink 与 Kafka 两个镜像成功。
**预检失败判据与降级**：若 `flink-cdc` 相关制品拉不到（依赖 Maven 中央仓或 GitHub Release），
降级为"Kafka + Flink SQL 的 kafka connector 造变更流" —— **但这要在文档里写明是降级，简历里不许写成真 CDC**。

## 6. 与阶段三的连续叙事（这一阶段的真正产出）

简历叙事从：
> 离线数仓（MySQL / Hive / Spark）+ 双引擎一致性

变为：
> 批流一体湖仓（CDC / Flink / Paimon）+ 离线双引擎一致性 + **跨链路（批流）对账**

关键在于**两条链路共用同一套口径**：离线侧由 34 条单测 + CI 固定（`tests/test_metric_definitions.py`），
实时侧复用 `src/metrics.py` 的纯函数做对账判据 —— 这是"别人做不出来"的连续性，
也是"你怎么知道两条链路算的是同一件事"这道题的答案。
