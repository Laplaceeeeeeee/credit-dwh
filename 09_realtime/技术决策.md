## 1. 四条决策（2026-09-24 定）

| # | 决策 | 选择 | 核心理由 | 代价（明确接受） |
|---|---|---|---|---|
| D1 | CDC 接入方式 | **Flink CDC 抓 binlog → Kafka → Flink → Paimon** | 真实变更流（可真实 INSERT/UPDATE 生成事件），且拿到"消息队列"这个实时岗筛选关键词 | 多一个容器、多一跳延迟 |
| D2 | 湖仓表格式 | **只做 Paimon**，把"为什么不用 Iceberg"讲清 | 主键更新 + 流读 + changelog 正是"实时落湖"的标配；省时间省内存 | 不做 Iceberg 对照实验（列为可选 E6） |
| D3 | 时间语义 | **真做事件时间 + Watermark + 允许延迟**，滚动/滑动窗口 | 这是面试最核心的一道题；用处理时间糊过去等于自弃 | 需要额外造乱序/迟到数据来验证 |
| D4 | 部署与资源 | **独立 compose + Paimon 落本地文件系统** | Docker VM 只有 7.64 GB，跑实时链路时停掉 Hive/Spark 四容器即可 | 不接近生产的存算分离形态（MinIO 列为可选） |

### D1 的展开：为什么必须"真 CDC"

旧方案（第 19 步原计划）里有一条降级路径：**用 Python + kafka-python 消费者读 TSV 回放**。
本次**明确放弃这条降级路径**，理由：

- 回放不是 CDC。被追问"binlog 是怎么解析的、全量加增量怎么无缝切换"会直接答不上来；
- 本项目的数据源（`credit-dwh-mysql`）是活的 MySQL，改一行数据就能产生真实 binlog 事件——
  造真实变更流的成本几乎为零，没有理由退化成回放。

### D2 的展开：选型理由要能答三问

被问"为什么用 Paimon 不用 Iceberg"时，答案必须是场景驱动，不是"教程用的"：

1. **为什么选它**：本场景需要**主键更新**（信贷表按 `loan_id` 反复更新）与**流读 / changelog**，
   Paimon 的 LSM 主键表、`partial-update`、`changelog-producer` 正是为此设计；
2. **它什么时候会坏**：小文件会随更新累积 → 依赖 compaction；流读并发与快照过期会让长跑作业失效；
3. **怎么知道它坏了**：文件数、compaction 状态、checkpoint 时长与状态大小（全部要测量并落盘）。

这等于官方标定了支持范围；Paimon 侧则是 `paimon-flink-<主版本>` 的制品命名。

| 组件 | 锁定值 | 依据 |
|---|---|---|
| Flink | **`flink:1.20.5-scala_2.12-java17`** | Docker Hub tags API 实测 tag 存在（1.20.x 共 56 个 tag） |

| Flink CDC | **`flink-sql-connector-mysql-cdc:3.6.0-1.20`** | 制品列表实测；同版本有 `-1.20` 与 `-2.2` 两种构建 |
| Kafka 连接器 | **`flink-sql-connector-kafka:3.4.0-1.20`** | 1.20 线的最新构建（**不是** 5.0.0-2.2 那条） |
| Kafka | **`apache/kafka:4.3.1`** | Docker Hub tags API 实测（最新稳定；4.4.0 还是 rc） |
| MySQL 驱动 | **复用 `07_bigdata/jars/mysql-connector-j-8.0.33.jar`** | 阶段三遗留；⚠️ CDC 的 shaded jar **不含**驱动，必须另配 |

> ✅ **不需要额外 jar 的一项**：Kafka sink/source 用的 **`debezium-json`** 格式
> 由官方 Flink 镜像自带的 `flink-json-1.20.5.jar` 提供
> （实测 `/opt/flink/lib/` 内含 `DebeziumJsonFormatFactory`）。
> 这是个容易多此一举的地方 —— 不必去下 `flink-connector-debezium`。

> **⚠️ 关键排除项：`flink:2.3.0` 不可用。** Docker Hub 上 Flink 最新是 2.3.0，
> 但 Paimon 只发布到 `paimon-flink-2.2` —— **照抄"最新 tag"必然撞墙**。
> 这正是"版本矩阵必须查制品、不能猜"的实例。

**为什么选 1.20 线而不是 2.2 线**（两条线都完整可用，不是被迫的）：

1. **Flink 1.x 是生产与面试的主流**：`1.20` 这个版本号面试官认得，2.x 的生产案例还少；
2. **Paimon 1.4.2 是成熟线**：Paimon 2.0.0 是刚发布的大版本，周边文档与示例可能滞后，
   而本项目时间盒只有三个月，**摩擦成本比"版本新"重要**；
3. 两条线的切换成本很低（一个镜像 + 两个 jar），**这个取舍本身可以写进面试话术**：
   "我评估过 2.2 线，最终因为生态成熟度选了 1.20"。

> ⚠️ **下载大文件不要用 `Invoke-WebRequest`**：它报传输错误时可能已经落盘了一个

> 用 `curl -L --retry 8 --retry-all-errors -C -`，并核对 Content-Length 与 zip 完整性。

**踩到的三个坑（要进排错手册）**

1. ⭐⭐ **`docker manifest inspect` 不走 `registry-mirrors`**。它在配了国内镜像源的机器上
   **必然超时**（直连 `registry-1.docker.io`），报
   `context deadline exceeded`，会被误判成"镜像拉不到"。
   → **能拉才算数**：预检必须用 `docker pull`，不能用 `manifest inspect`。
   （阶段三文档把这个命令写成"最省的预检手段"，是错的，已在本文档更正。）
2. ⭐ **`flink-connector-mysql-cdc` 是瘦 jar（0.4 MB），`flink-sql-connector-mysql-cdc` 才是 shaded jar（20.7 MB）**。
   前者脱离 Maven 依赖树根本不能用，同名族两个制品极易拿错。
3. ⭐ **CDC 的 shaded jar 不含 MySQL JDBC 驱动**（`com/mysql/` 条目数 = 0，
   大概出于 GPL 许可），必须另行提供。本项目直接复用阶段三的
   `mysql-connector-j-8.0.33.jar` —— **少一个下载、多一条"跨阶段复用"的故事**。

**⚠️ 一个尚未验证的风险**：Debezium 期望的 mysql-connector-j 版本与 8.0.33 是否兼容，
要在 M1 第一次真跑 CDC 时暴露。若不兼容，改用与 Debezium 对齐的驱动版本并记录在此。

**顺带发现（写进面试话术的取舍点）**：制品列表里有 `flink-cdc-pipeline-connector-paimon`，
即**官方 CDC → Paimon 直通管道**。本项目**不用它**，理由：
直通管道会把"同步"做完，但**把计算层吃掉了** —— 而本阶段的重点是
"事件时间 + Watermark + 窗口聚合"这道核心题，必须由我自己的 Flink 作业完成。
能说清"我知道有更省事的方案，但因为要保留计算层而不用它"，比会用直通管道更能证明判断力。
