## 3. ⭐ 故障演练抓出的真实缺陷：`latest-offset` 会静默丢数据

### 3.1 第一次演练（`docker kill`，停机 23.8 秒）—— 看起来是好的

| 项 | 实测 |
|---|---|
| 故障判定 | **未观测到**（快照里作业仍显示 RUNNING） |
| 停机期间插入 | 5 笔（合计 4000.00） |
| 结果 | Paimon **10 行 / 5500.00**，5 笔都在 ✅ |
| 窗口计数 | `[13:23]` 5/1500.00、`[13:24]` 5/4000.00 —— 精确 |
| `restored` | 1 |

**但这里有个陷阱**：停机只有 23.8 秒，而 **JM 判定 TM 失效靠的是 50 秒的 `heartbeat.timeout`**，
所以快照里作业状态还是 RUNNING —— **"看起来没坏"不等于没坏**，
恢复的真正起点（JM 判定失效的时刻）没有被观测到。

### 3.2 第二次演练（`docker pause`，停机 50.6 秒，**先观测到故障**）—— 暴露缺陷

| 项 | 实测 |
|---|---|
| `pause` 时刻 | 13:33:16 |
| t=0→45s | 作业仍 RUNNING |
| **t=50.4s** | **作业进入 RESTARTING** ← 恰好等于 JM 的 `heartbeat.timeout`=50s |
| 停机期间插入 | 3 笔（commit `13:34:06.729`） |
| `unpause` | 13:34:06（停机 50.6 秒） |
| 恢复 | unpause 后 **5.1 秒** 两个作业 RUNNING |
| `restored` | 1 |
| **数据** | **Kafka 偏移停在 0，3 笔全部丢失** ❌ |

**根因（Debezium 日志铁证）**：

```
13:34:07,825  Snapshot step 7 - Skipping snapshotting of data
13:34:07,826  Snapshot ended ... currentBinlogPosition=6294
13:34:07,833  Connected to MySQL binlog ... starting at ... restartBinlogPosition=6294
```

`scan.startup.mode = latest-offset` 的语义是"**从启动那一刻的 binlog 末尾开始读**"。
重启时它在 `13:34:07.8` 取了**新位点 6294**，而停机期间的插入发生在 `13:34:06.7`——
**位点在 6294 之前，于是整段被跳过，且不报任何错**。

> ⚠️ **比"确定会丢"更危险的是"不确定"**：两次演练用的是同一份配置，
> 第一次没丢、第二次丢了。也就是说 `latest-offset` 下的行为**不可预测** ——
> 这本身就是它不能用于容错链路的理由。

### 3.3 修复与验证（改用 `scan.startup.mode = initial`）

`initial` 的语义是"**有存储位点就续读，没有才快照**"：
正常情况下从 checkpoint 恢复的位点续读（不丢、不重复快照）；
万一位点丢失则退回全量快照 → 数据重复但由 Paimon 主键表去重，**最坏是慢，不会丢**。

**同一演练重跑（对照组）**：

| 项 | 实测 |
|---|---|
| 故障前 Kafka 偏移 | 2,260,668 |
| `pause` → 故障判定 | t=**40.4s** → RESTARTING（TM 停机 40.7 秒） |
| 停机期间插入 | 3 笔（commit `13:39:16.696`） |
| 恢复后 10 秒内 | 两个作业 RUNNING，**Kafka 偏移 = 2,260,671** ✅ |
| Paimon 实时表 | **2,260,671 行 / 34,004,209,200.00** = 基线 + 600.00 ✅ |
| 3 笔的 `op_ts` | `13:39:16`（正是停机期间的时刻，**语义正确**） |
| 窗口 `[13:39]` | 3 / 600.00 —— **精确，无重复** |
| `restored` | 1（两个作业都是） |

**修复前后是同一演练、只改一个参数**，这就是直接的因果证据。

### 3.4 Exactly-Once 的边界（说清楚，不说过头）

**能证明的**：
- 故障后数据不丢（Kafka 偏移从 2,260,668 → 2,260,671，只补了缺的 3 条）；
- 不重复：两轮演练后窗口计数**精确等于**插入条数（若只有 at-least-once，
  重放会把计数顶上去）；Paimon 主键表另有去重兜底；
- 恢复确实来自 checkpoint（`restored=1` 是直接证据）。

**不能声称的**：
- **没有验证"Kafka 侧事务是否严格只提交一次"** —— 我验的是**端到端结果正确**，
  不是内部事务语义。Paimon 主键去重会**掩盖**重复写入，
  所以"主键表里没有重复行"**不能**作为 exactly-once 的证据（真正灵敏的探针是窗口计数）。
- 单 broker、单 TM、单 slot，**没有验证多副本/多节点下的一致性**。
- 端到端 exactly-once 依赖 Paimon sink 的两阶段提交与 Kafka 事务；
  **我没有单独关掉其中任一项来做对照实验**，所以无法量化"若关掉会怎样"。

## 4. 恢复时间线（可复现的操作时序）

```
docker pause rt-taskmanager        # 故障注入
  → t+50s   JM 判定 TM 失效，作业转 RESTARTING   ← 由 heartbeat.timeout 决定
  → 期间插入数据（模拟真实流量不中断）
docker unpause rt-taskmanager      # 恢复
  → t+5.1s  作业 RUNNING
  → t+10s   停机期间的数据已补发（Kafka 偏移 +3）
```

**关键认知**：恢复不是"重启容器就完了"，而是
**JM 判定失效（≤50s）→ 从 checkpoint 恢复 → 源端按存储位点续读**。
其中**源端续读**这一步就是 §3 里被 `latest-offset` 破坏的地方。

## 5. 乱序 / 迟到数据 vs Watermark（D3 的语义验证）

CDC 无法回填 binlog 时间，所以**直接向 Kafka 注入**指定 `op_ts` 的记录
（先用 `kafka-console-consumer` 抓一条真实消息看清格式，避免格式猜错让作业挂掉）。
注入格式与 Job A 产出的一致，`op_ts` 用 UTC：
`{"before":null,"after":{...,"op_ts":"2026-09-24T05:23:30Z"},"op":"c"}`

| 用例 | 注入的 `op_ts` | 记录级（`rt_loan_fact_latest`） | 窗口级（`rt_loan_change_1min`） |
|---|---|---|---|
| C1 迟到 3 分钟 | 13:23:30（属**已关闭**窗口） | **收到了** ✅ | **未计入**：`[13:23]` 仍是 5 / 1500.00 ✅ |
| C2 "墙上时钟晚 90 秒" | 13:25:30（属**未关闭**窗口） | 收到了 ✅ | **正常计入**：`[13:25]` = 2 / 444.00 ✅ |
| C3 推进水位 | 注入时刻 | 收到了 ✅ | 用于关闭 `[13:25]` |

**结论**：
1. **记录不会丢** —— 无论多迟，主键表照收（它没有窗口语义）；
2. **窗口会丢迟到数据** —— 一旦 Watermark 越过窗口右界，窗口定稿，迟到数据不再改写它；
3. ⭐ **"迟到"是相对 Watermark 判定，不是相对墙上时钟** ——
   C2 按墙上时钟已经"晚了 90 秒"，但因为 Watermark 还没到，它被**正确计入**。
   这正是 allowed-lateness 的本质，也是最容易被误解的一点。

一致性核对：注入后 `latest` 表 14 行 / 7165.00 = MySQL 来源 11 行(5611.00) + Kafka 注入 3 行(1554.00)，**分毫不差**。

## 6. 本轮新增的排错条目（续 B-1…B-16）

| # | 现象 | 根因 | 对策 |
|---|---|---|---|
| **B-17** | ⭐⭐ 重启后停机期间的变更**静默丢失**，不报任何错 | **`scan.startup.mode = latest-offset`** 每次启动都在"当前时刻"取新 binlog 位点 | 容错链路必须用 **`initial`**（有存储位点就续读）。**这是 M2 最重要的产出** |
| **B-18** | ⭐ 故障演练里"作业看起来没坏" | **JM 的 TM 失效判定靠 50 秒 `heartbeat.timeout`**；短于 50 秒的停机不会被判定 | 演练**必须观测到 RESTARTING 才算数**；否则"恢复耗时"是无意义数字 |
| **B-19** | Kafka 间歇不可达，日志报 `all log dirs in /var/lib/kafka/data have failed`，进入崩溃循环 | `/var/lib/kafka/data` 用的是 **Windows bind mount** —— 与 Paimon warehouse 同类问题：Docker Desktop 的 Windows 文件共享**对 JVM 有状态服务不可靠** | 改**命名卷**；⚠️ Kafka 镜像以 **uid 1000(appuser)** 运行，必须先 `chown`（且要在容器启动前用一次性容器做，因为 entrypoint 启动时就会格式化日志目录） |
| **B-20** | `REST API cancel` 发了 202 但作业仍在跑、越积越多 | 作业卡在取消流程里不落地 | 用 **`docker compose restart jobmanager`** 清空作业注册表（比 cancel 确定） |
| **B-21** | 快照期窗口聚合产生超大行（226 万条落进同一个 1 分钟窗口） | 快照记录的 `op_ts` 都是快照时刻 | 不是 bug；**但它恰好等于离线基线**，可当作批流一致的旁证 |

## 7. 诚实缺口

1. **exactly-once 没有做对照实验**（没关掉 Kafka 事务或 Paimon 两阶段提交来对比），
   所以只能称"端到端结果正确"，不能称"内部事务严格只提交一次"。
2. **单 broker / 单 TM / 单 slot**，多节点一致性未验证。
3. **未做长时间稳定性验证**：两次演练之间只隔了几分钟，
   没有验证"跑几小时后恢复是否仍正确"。
4. **C1/C2 的迟到数据是手工注入 Kafka 的**（因为 CDC 无法回填 binlog 时间），
   **不是真实业务流量**，汇报时要说清。
5. **快照期的 226 万行窗口聚合虽然等于离线基线，但只有一次采样**，
   没有做多次/多批次的对账 —— 正式对账属 M3。
6. **没有验证 DDL 变更（加列）后的链路行为**（M1 计划里提过，本轮没做）。
7. **`latest-offset` 缺陷的影响面未被完全界定**：只测了"停机期间插入"这一种情形，
   没有测"停机期间 UPDATE / DELETE"。
