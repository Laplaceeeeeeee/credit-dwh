## 2. ⚠️ 数据陷阱（发现即记录）—— 共 3 个

### 2.1 🔴 页脚不是 1 行，而是 **33 行**，且**散布在文件中部**

这个文件**不是一份单纯的导出**，而是**多个年度分段拼接**而成，段间夹着章节标题与汇总行：

```
行  421096   Total amount funded in policy code 1: 6417608175,,,,...
行  421097   Total amount funded in policy code 2: 1944088810,,,,...
行  528962   Total amount funded in policy code 1: 1741781700,,,,...
...          共 16 对，间隔约 10~23 万行出现一次
行 1651666   Loans that do not meet the credit policy,,,,...      ← 章节标题
行 2260700   Total amount funded in policy code 1: 1465324575,,,,...
行 2260701   Total amount funded in policy code 2: 521953170,,,,...
```

**共 33 行**（16 对汇总行 = 32 行，加 1 行章节标题）。

**后果**（这是本项目最大的坑）：
- 用 `skipfooter=1` **只能删掉最后一行**，另外 **32 行会混进数据**
- 它们落在 `id` 列，值形如 `'Total amount funded in policy code 1: ...'`
- 更糟：pandas 会因此把 `id` 推断成**字符串**，在分块写入 Parquet 时引发
  `ValueError: Table schema does not match schema used to create file`

**处理方式**：`src/prepare_raw.py` 全文件扫描，
按"`id` 首字段必须是纯数字"判定并剔除全部 33 行。
页脚原文留证于 `data/clean/footer_line.txt`。

> 🔑 **这也解释了一个早期的误判**：此前以为"有 32 行记录缺 `issue_d`"，
> 实测证明那 **32 行就是页脚行**，并非真实记录缺字段。
> 因此 DWD 的 `REJECT` 计数为 **0**，不是 32。

### 2.2 🚨 `member_id` 列整列为空（废列）

**实测结果：2,260,668 行中 `member_id` 非空值为 0 —— 该列 100% 为空。**

**影响**：**无法按客户维度聚合**，"客户维 + 一人多贷"的设计**不成立**。

**处理方式**：
- 从设计中**剔除该列**
- 维度表改为 **`dim_applicant`（申请人画像维）**，主键 = `loan_id`，
  粒度 = 一笔贷款，只承载申请时点属性
- ❌ **不采用**用 `annual_inc + addr_state` 拼"伪客户 ID" ——
  那是错误关联，会让"一人多贷"统计失真

### 2.3 共 14 个字段整列为空

除 `member_id` 外还有 13 个：

```
revol_bal_joint, sec_app_fico_range_low, sec_app_fico_range_high,
sec_app_earliest_cr_line, sec_app_inq_last_6mths, sec_app_mort_acc,
sec_app_open_acc, sec_app_revol_util, sec_app_open_act_il,
sec_app_num_rev_accts, sec_app_chargeoff_within_12_mths,
sec_app_collections_12_mths_ex_med, sec_app_mths_since_last_major_derog
```

7 个 `sec_app_*` 是"共同申请人"相关字段，本数据集未采集。
**处理**：预处理阶段整体剔除，151 → **137 列**。

### 2.4 `skipfooter` 与 `chunksize`/`nrows` **互斥**

pandas 2.2.2 与 3.0.5 上均直接抛错：

```
ValueError: 'skipfooter' not supported for iteration     # 与 chunksize
ValueError: 'skipfooter' not supported with 'nrows'      # 与 nrows
```

**处理**：不在每次读取时跳页脚，改为**预处理一次**产出干净 Parquet，
之后全部走 C 引擎读取（顺带把全量读取从 20–40 分钟压到 **80 秒**）。

## 4. `loan_status` 取值分布 ⭐ 口径基础（全量实测）

| loan_status | 笔数 | 占比 | 归入档位 | 是否终态 | 是否不良 |
|---|---|---|---|---|---|
| Fully Paid | 1,076,751 | 47.63% | PAID | ✅ | ❌ |
| Current | 878,317 | **38.85%** | CURRENT | ❌ | ❌ |
| Charged Off | 268,559 | 11.88% | CHARGED_OFF | ✅ | ✅ |
| Late (31-120 days) | 21,467 | 0.95% | DPD_31_120 | ❌ | ❌ |
| In Grace Period | 8,436 | 0.37% | DPD_1_30 | ❌ | ❌ |
| Late (16-30 days) | 4,349 | 0.19% | DPD_1_30 | ❌ | ❌ |
| Does not meet...Status:Fully Paid | 1,988 | 0.09% | PAID | ✅ | ❌ |
| Does not meet...Status:Charged Off | 761 | 0.03% | CHARGED_OFF | ✅ | ✅ |
| Default | 40 | 0.002% | CHARGED_OFF | ✅ | ✅ |
| **合计** | **2,260,668** | 100% | | | |

### ⭐ 口径结论

```
不良 = Charged Off + Default + Does not meet...Charged Off = 269,360 笔
终态 = 上述 + Fully Paid + Does not meet...Fully Paid     = 1,348,099 笔

不良率（终态口径）= 269,360 / 1,348,099 = 19.9807%
```

⚠️ **对比：若不限定终态、把 878,317 笔 `Current` 也算进分母**：

```
错误不良率 = 269,360 / 2,260,668 = 11.9155%
```

**低估了 8.07 个百分点。** 这是信贷指标里最经典的口径错误 ——
把"还没到期的正常贷款"当成"没出问题的贷款"。

> 🔑 **面试高频追问**："不良率怎么算？"
> 答"不良笔数 / 总笔数"是**不及格**的，必须说清**分母要限定终态**及原因。

## 7. 异常值检查（子集实测）

| 检查项 | 结果 | 处理 |
|---|---|---|
| `loan_amnt <= 0` | **0 行** ✅ | — |
| `loan_amnt` 范围 | 1,000 ~ 35,000 | 合理 |
| `annual_inc <= 0` | **2 行** ⚠️ | 标记 WARN，不删除（避免误删真实低收入） |
| `annual_inc` 最大 | **9,000,000** | 极端值，标记不删除 |
| `annual_inc` 分位数 | P50=65,000 / P90=130,000 / P99=260,814 | — |
| `dti` 最大 | **999.00** ⚠️ | **哨兵值**（占位符），非真实比率 → 分析时按 NULL 处理 |
| `issue_d` 解析失败 | **0 行** ✅ | — |
| `last_pymnt_d` 解析失败 | **0 行** ✅ | — |

> ⚠️ **`dti = 999` 是典型的哨兵值**（用一个大数代替 NULL）。
> 若不做处理，会把"缺失"算成"极高负债率"，严重扭曲风险分层。
> 这正是"按字段分别决策缺失处理，而不是到处填 0"的价值。

## 8. 时间跨度与规模

### 8.1 全量时间跨度（实测）

| 字段 | 范围 |
|---|---|
| `issue_d` | **2007-06 ~ 2018-12** |
| `earliest_cr_line` | 1950-01 ~ 2012-11（子集） |
| `last_pymnt_d` | 2015-07 ~ 2019-03（子集） |

### 8.2 ⚠️ 子集的时间局限（重要）

**子集的 `issue_d` 只覆盖 2015-07 ~ 2015-12（半年）**，而非全量的 2008~2018。

原因：文件按年份排序，取前 20 万行等于取了一段连续时间窗口。

**后果**：

| 项 | 影响 |
|---|---|
| 放款趋势图 | **只能反映 2015 下半年**，不能用于跨年趋势结论 |
| Vintage 矩阵 | 只有 6 个批次（2015-07 ~ 2015-12） |
| 比例型指标 | 子集 `Current` 仅占 11.32%，全量为 **38.85%** → **分布完全不同** |

> 🔑 **结论：子集只适合验证流程与口径，比例型指标必须用全量重算。**
> 切换方式：`src/config.py` 中 `MAX_ROWS = None`。

### 8.3 体量实测（写简历用）

| 项 | 值 |
|---|---|
| 子集 DataFrame 内存占用 | 605 MB（200,000 × 137） |
| 推算全量内存占用 | 约 **6.8 GB**（2,260,668 × 137） |
| 全量 Parquet 体积 | 337.6 MB（压缩比约 5×） |

> 💡 **6.8 GB 这个数字很重要**：它说明全量数据**单机可承载**，
> 但要一次性读入必须注意内存。这也是后面"引擎选型"讨论的起点 ——
> **本项目上分布式不是因为扛不住，而是为了验证口径可迁移性**。

## 9. 结论与对后续设计的影响

### 9.1 口径

1. **不良定义** = `Charged Off` + `Default` + `Does not meet...Charged Off`
2. **不良率必须限定 `is_terminal = 1`**，否则低估约 8 个百分点
3. 终态口径全量不良率 = **19.9807%**（269,360 / 1,348,099）

### 9.2 设计决策

| 决策 | 依据 |
|---|---|
| 预处理独立成一步（`prepare_raw`） | 页脚 33 行散布全文 + `skipfooter` 与分块互斥 |
| 主键 `id` 存为 **string** | 避免数值精度隐患与 `.0` 后缀 |
| **不建客户维**，改 `dim_applicant` | `member_id` 整列全空 |
| 剔除 14 个全空列 | 无信息量，只增加体积与噪声 |
| `purpose` 属**申请时点**信息 | 不得放入 `LEAKAGE_BLACKLIST`（曾误列，已修正） |
| `dti` / `revol_util` 属申请时点信息 | 来自放款时征信快照，非表现期 |

### 9.3 必须随结论一起表达的边界

1. 仅含放款样本 → **幸存者偏差**，批准率不可计算
2. 无逐月还款状态 → 迁徙率的 DPD 档位为**规则推导**
3. 子集时间窗口仅半年 → **比例型指标需全量重算**
4. `member_id` 缺失 → **客户级分析不可做**
